## Метод

1. Греп по фразам прежней картины: Managed, MinIO, «уровень 5», «общий
   адаптер», «сетевая попытка», Redis, FastAPI/Celery/Django, LiteLLM,
   «физически», `result_file_missing`, безусловная повторяемость этапов.
2. Независимый ревьюер A: линейное чтение всех документов против новых
   решений; категории CONFLICT, STALE, GAP. Первый запуск остановлен
   владельцем, результаты — второго запуска.
3. Независимый ревьюер B: враждебное чтение нового текста — гонки,
   пропущенные состояния, двусмысленности, факты без источника.
4. Каждая находка P1/P2 и выборочно P3 перепроверена мной по цитатам обеих
   сторон. Идентификаторы ревьюеров сохранены в скобках.

## Проверенные факты

- ADR-0010:312–318 определяет «оригинал создан» как «скачал ли генератор
  файл, проверил тип и размер и положил его в `transfer/output/`» —
  без подтверждения записи в базе генератора.
- ADR-0013:138–141 разрешает запись дескриптора результата любой записью
  исполнителя с `lease_generation = :mine`; запрета перезаписи нет.
- ADR-0011 §5, строка «`running`, вызов начат» — «Дождаться исхода или
  сверка → `succeeded` либо `failed`»; ADR-0014 строка «Локальные рабочие
  файлы» — «Исполнитель, обнаруживший барьер стирания на Job, удаляет свой
  рабочий каталог (механизм выведен мной)».
- ADR-0010:205–208: порядок «скачать → проверить → положить в
  `transfer/output/` → закрыть `ProviderCall`» — `ProviderCall` закрывается
  после `PUT`; ADR-0011 §3 переводит вызов в `succeeded` до скачивания.
- ADR-0012:285: `failure.reason` из группы `generation_failed`, `timed_out`,
  `service_unavailable`; отображения `reason_code` на группы нет ни в одном ADR.
- ADR-0007:98: «Удаление должно охватывать резервные копии и восстановление
  из них»; ADR-0013 делает резервные копии условием первого выпуска и держит
  правило для стёртого текста в них открытым.
- Отклонено B-20: обе фразы ADR-0011 §2, которые ревьюер счёл авторскими
  обоснованиями под пометкой «формулировки владельца», — дословно из решения
  владельца 2026-09-14.

## Решения владельца

Развилки: без ответа текст не приводится к одному прочтению.

| Id | Серьёзность | Вопрос | Варианты и цена |
| --- | --- | --- | --- |
| S-1 (B-4, A-2, A-18) | P1 | `result_payload_unavailable`, когда объект в `transfer/output/` уже записан прежним исполнителем, а подтверждение записи не сохранено. По ADR-0010 оригинал создан — попытка списывается; по ADR-0011 — `failed` и возврат | (а) переопределить в ADR-0010 «оригинал создан» как «запись объекта подтверждена генератором» — возврат попытки, расход у студии, ADR-0010 меняется; (б) backend при `result_payload_unavailable` проверяет объект по дескриптору (у него есть `GET`) и при совпадении принимает оригинал — нужен дескриптор с `call_id` в Result, новая ветвь §4 |
| S-2 (B-3, A-1, B-9, B-10) | P1 | Когда удаляются локальные файлы при стирании. Удаление «при виде барьера» уничтожает скачанные байты начатого вызова и превращает `succeeded` в `result_payload_unavailable` вопреки §5 и ADR-0010:311 | Предложение: рабочие файлы начатого вызова удаляются после доведения исхода по §5; сразу — только ненужные для доведения. Назвать признак барьера (`erase_requested_at` или `content_erased_at`), исполнителя (владелец каталога, не потребитель команд) и момент (например, проверка в задаче продления аренды); удалять и при любом выходе задачи и потере аренды |
| S-3 (B-11, B-8) | P2 | Что такое «осиротевший» рабочий каталог; периодический обход кроме запуска | Предложение: каталог по процессу, `job_id` и поколению аренды; осиротевший — процесс-владелец мёртв; каталог прежнего исполнителя не переиспользуется как «доступный результат». Периодический обход — новое против решения «при запуске» |
| S-4 (A-7) | P2 | Правило удаления в резервных копиях (ADR-0007) при копиях в первом выпуске | Условие первого выпуска наравне с копиями, или явно принятое ограничение первого выпуска |
| S-5 (A-8) | P2 | Отображение `reason_code` генератора и кодов backend на `failure.reason` ADR-0012 | Таблица «код → группа»; старый пробел, новые коды его расширяют |
| S-6 (B-12) | P2 | Что значит «тип» при сверке `result_file_mismatch` | Одно правило для обеих сторон (сигнатура байтов или заголовок), `ContentType` при `PUT` равен типу из дескриптора; иначе годный результат даёт несовпадение и возврат |
| S-7 (A-9) | P2 | RFC 3339 с часовым поясом для `deadline_at`/`created_at` как часть контракта ADR-0011 §6, а не только условие Pydantic | Записать в контракт — backend на TypeScript получает то же правило; или оставить формат открытым до выбора общих схем |
| S-8 (B-7, B-23) | P2 | Критерий «получить повторно у провайдера нельзя» | Предложение: только достоверный признак по контракту маршрута (истёкшая ссылка, документированный ответ); временные ошибки — повтор до `deadline_at`. | S-9 (B-17) | P3 | Контрольная сумма или подпись тела `PUT` | Без неё повреждение в пути видит только backend как `result_file_mismatch` с возвратом; поддержку в Yandex Object Storage документ не утверждает |
| S-10 (A-17, B-14) | P3 | Объект в `transfer/output/` при `failed` по короткому пути и при `result_file_mismatch` | Явное удаление, как у позднего Result, или опора на правило жизненного цикла |
