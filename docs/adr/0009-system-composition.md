# ADR-0009: Состав системы

- **Статус:** принят владельцем 2026-09-09 как первый уровень архитектуры;
  уточнён 2026-09-10 по свип-ревью и 2026-09-11 (форма роутера моделей).
- **Дата:** 2026-09-09, уточнён 2026-09-10 и 2026-09-11.
- **Принимает решение:** владелец проекта.
- **Связи:** [генератор и кабинет](0001-tattoo-generator-and-client-account.md),
  [Yandex Cloud](0004-yandex-cloud-and-generation-harness.md),
  [самостоятельный генератор](0008-independent-generation-service.md).
- **Состояние реализации:** ни одна из частей, кроме публичного сайта,
  не реализована.

## Контекст

Владелец решил не выпускать ничего до утверждения архитектуры всего проекта
и согласовал порядок утверждения сверху вниз:

1. состав системы и обязанности частей (этот ADR);
2. данные и владение ими;
3. контракты между частями;
4. исполнение: языки, библиотеки, база, фоновые задания, запуск;
5. инфраструктура и выпуск.

Каждый уровень фиксируем отдельным ADR после явного согласия владельца.
Провайдер моделей остаётся заменяемой деталью, чтобы его выбор не блокировал
утверждение остальных уровней.

Владелец задал требуемые возможности сервиса: публичный сайт; кабинеты
клиента и мастера; авторизация и роли; клиенты, проекты, эскизы; загрузка
и хранение изображений; фоновые задания; административный интерфейс;
интеграция с внешним генератором. Это исходный список требований; сущность
«проект» из него владелец затем исключил, см. «Следствия».

## Решение

Приложение проектируем по классической схеме frontend и backend: две
самостоятельные части, которые выпускаются независимо и общаются через API.
Нынешний сайт из одной страницы становится основой frontend.

| Часть | Где живёт | За что отвечает |
| --- | --- | --- |
| Frontend (публичный сайт) | `ratedtattoo.ru`, отдельная статическая сборка (React, Vite), публикуется из Yandex Cloud | Публичные секции; гостевая генерация; форма обращения к мастеру; клиентский кабинет. Вызывает API backend. Данных не хранит, секретов не знает |
| Backend (приложение) | Поддомен, например `app.ratedtattoo.ru` | API для frontend; кабинет мастера; административный интерфейс; авторизация и роли (клиент, мастер, администратор); клиенты, эскизы и обращения; загрузка и хранение изображений; фоновые задания; уведомления мастеру; интеграция с генератором |
| Генератор | Самостоятельный внутренний сервис по ADR-0008 | Принимает задание от приложения, готовит описание, вызывает модель через роутер, возвращает результат. Истории эскизов клиента не ведёт, клиентский текст задания хранит только на время выполнения (ADR-0010) |
| Очереди | Yandex Cloud, Россия | Очередь заданий backend → генератор и очередь результатов генератор → backend. Технология — уровень исполнения |
| Хранилища | Yandex Cloud, Россия, по ADR-0004 | База данных backend; отдельная база генератора; объектное хранилище для оригиналов, предпросмотров, загрузок клиентов и передаточной области |
| Внешние сервисы | Вне нашей инфраструктуры | Модели, почта, боты Telegram и MAX. Доступ только с сервера, ключи в хранилище секретов |

Мастер и администратор работают через приложение после входа. Клиент
работает только на сайте: интерфейса приложения он не видит, хотя его
браузер обращается к API на поддомене.

## Рассмотренные варианты

| Вопрос | Отвергнуто | Выбрано и почему |
| --- | --- | --- |
| Сайт внутри приложения | Один сервер отдаёт и сайт, и кабинеты | Сайт отдельно: владелец хочет менять сайт независимо от приложения и не строить «ещё один WordPress» |
| Как сайт связан с приложением | Сайт только ссылается на страницы приложения | Сайт вызывает API: посетитель генерирует эскиз и отправляет заявку, не покидая `ratedtattoo.ru` |
| Где кабинеты | Все кабинеты в приложении | Клиентский кабинет на сайте в фирменном дизайне; мастер и админка в приложении, где готовые служебные интерфейсы закрывают большую часть работы |

## Следствия

- Гостевая и клиентская сессии работают между `ratedtattoo.ru` и поддоменом
  приложения так: cookie сеанса host-only для `app.ratedtattoo.ru` — без
  атрибута `Domain`, с `Secure`, `HttpOnly` и `Path=/`. Frontend её не читает
  и не должен: он лишь шлёт запросы с `credentials: "include"`, а ставит
  и проверяет cookie backend. CORS разрешает единственный источник
  `https://ratedtattoo.ru` и учётные данные, поэтому подстановочный
  `Access-Control-Allow-Origin` здесь недопустим.
- Общий домен `.ratedtattoo.ru` для cookie не нужен и не используется: он
  отправлял бы секрет сеанса на хост статики, которому тот не требуется.
  Оба хоста имеют общий регистрируемый домен, то есть для браузера это один
  сайт, и host-only cookie доходит до API без него. Значение `SameSite`
  и защиту изменяющих запросов определяет уровень контрактов —
  предложено в [ADR-0012](0012-frontend-api-contract.md) (`Lax` и проверка
  `Origin`; принят 2026-09-11).
- Сайт зависит от контракта API приложения. Контракт версионируем;
  изменение API без совместимости требует согласованного выпуска сайта.
- Форма записи переезжает с Formspree на API приложения. Это первый
  шаг, который убирает передачу имени и телефона за рубеж.
- Сайт растёт: экраны входа и регистрации, кабинет с историей эскизов,
  обращение к мастеру. Публикация сайта остаётся статической.
- Статика переезжает с GitHub Pages в Yandex Cloud вслед за backend, так что
  обе части оказываются в российской инфраструктуре. ADR-0005 этому решению
  не противоречит: он уже предлагает сборку в SourceCraft CI/CD и публикацию
  `dist/` в Yandex Object Storage, а GitHub Pages описывает только как
  текущее состояние. Пересмотра требуют три детали выпуска. Открытый вопрос
  ADR-0005 «способ публикации `ratedtattoo.ru`» закрыт на уровне площадки
  (Yandex Cloud); конкретный сервис — предложенный там Object Storage —
  подтверждает уровень инфраструктуры. Проверка «прямого открытия URL
  кабинета» на этапе 4 порядка перехода относится к клиентскому кабинету,
  то есть к маршрутам статического сайта; глубокие ссылки на них при
  статической публикации нужно подтвердить отдельно. Выполнение заданий
  ADR-0005 относит к «харнессу» из ADR-0004, тогда как по этому ADR их
  выполняют backend и генератор. Пайплайн выпуска определяет уровень
  инфраструктуры.
- Роутер моделей — библиотека внутри генератора, а не отдельная часть
  системы (решение владельца 2026-09-11; закрывает пункт A-109 свип-ревью,
  где вариант отдельного сервиса «отпал молча»). Таблица состава выше
  не меняется. Ключи провайдеров, идентификаторы внешних операций и учёт
  вызовов остаются в зоне ответственности генератора; роутер вызывается
  как библиотека. Это не требование одного процесса: ADR-0011 §2
  предусматривает отдельный процесс восстановления, и число исполнителей
  генератора остаётся вопросом уровня 4. Отдельный сервис (LiteLLM Proxy
  или свой) отвергнут: он добавил бы второй синхронный разрыв с оплаченным
  вызовом без результата (API Яндекса отдаёт картинку только `b64_json`,
  ADR-0004), третьего держателя байтов результата вне таблицы прав
  ADR-0010 «Файлы» и цепочки стирания ADR-0011 §5, и потребовал бы замены
  разделов ADR-0010/0011. Граница модуля даёт инкапсуляцию доступа
  к ключам: с ними работает только роутер, остальным модулям генератора
  они через интерфейс не передаются. Изоляции полномочий она не даёт —
  код одного процесса не имеет независимой защиты памяти; изоляция
  генератора от backend обеспечивается отдельными правами исполнения
  и доступом к хранилищу секретов на уровнях 4–5. Исследование роутера
  сравнивает LiteLLM SDK и собственную библиотеку.
- Сущность «проект» из исходного списка владелец после обсуждения
  исключил: клиенту незнакомая абстракция не нужна, модель остаётся
  «клиент → эскизы → версии», обращение к мастеру группирует нужное само.
  Точный набор сущностей и ролей задан в ADR-0010.

## Что решает следующий уровень

Данные и владение ими решены в [ADR-0010](0010-data-and-ownership.md):
сущности клиента, эскиза, версии, загрузки, задания генерации и обращения;
какая часть системы владеет каждой; что генератор получает и что
возвращает. Следующий уровень — контракты между частями.

## Источники

- Решения владельца в обсуждении 2026-09-09: порядок утверждения
  архитектуры; список требуемых возможностей; сайт отдельно от приложения;
  сайт вызывает API; клиентский кабинет на сайте, мастер и админка
  в приложении; итоговая формулировка: классическая схема frontend и backend.
- Решения владельца в обсуждении 2026-09-10, проход 1 по свип-ревью
  [`docs/reviews/2026-09-09-adr-sweep.md`](../reviews/2026-09-09-adr-sweep.md):
  статика переезжает с GitHub Pages в Yandex Cloud вслед за backend; cookie
  сеанса host-only для поддомена backend вместо общего домена, CORS с
  единственным разрешённым источником; очереди и база генератора входят
  в состав системы.
- Решение владельца 2026-09-11 по A-109 после диалектического разбора
  «роутер как отдельный сервис» (тезис и антитезис против ADR-0004,
  0008, 0010, 0011): библиотека внутри генератора. Первое слово владельца
  было «сервис»; после разбора следствий для ADR-0011 §3 и байтов
  результата — «берём библиотеку». Основания записаны в «Следствиях».
- Замечания владельца 2026-09-11 к записи решения (коммит `2e9d1e0`):
  ADR-0011 не требует одного процесса — он закрепляет ответственность
  за сверку и хранение `ProviderCall` за генератором, а §2 предусматривает
  отдельный процесс восстановления; формулировка «в одном процессе»
  вводила отсутствующее ограничение и мешала запуску нескольких
  исполнителей — заменена на «зона ответственности генератора».
  Граница модуля даёт инкапсуляцию доступа к ключам, не изоляцию;
  изоляция — права исполнения и доступ к хранилищу секретов на уровнях 4–5.
  Утверждение о поведении LiteLLM «по умолчанию» снято из задания
  исследования как неподтверждённое для нужных маршрутов изображений;
  вместо него — проверяемое требование к библиотеке.
- Замечания владельца 2026-09-10 после прохода 1 (семь пунктов по
  обоснованиям и согласованности): ADR-0005 не писался под GitHub Pages,
  вместо общего утверждения перечислены конкретные детали выпуска,
  требующие пересмотра.
