# ADR-0012: API backend для frontend

- **Статус:** предложен 2026-09-11 по поручению владельца закрыть вторую
  часть третьего уровня самостоятельно. Все решения в этом документе выведены
  мной из принятых ADR и ждут утверждения владельца; принятым ADR станет
  после его явного «да». Спорные места вынесены в «Открытые решения
  для владельца».
- **Дата:** 2026-09-11.
- **Принимает решение:** владелец проекта.
- **Связи:** [состав системы](0009-system-composition.md),
  [данные и владение](0010-data-and-ownership.md),
  [контракт выполнения генерации](0011-generation-execution-contract.md),
  [вход и гостевой эскиз](0002-sign-in-and-guest-sketch-ownership.md),
  [предпросмотр и обращение](0003-sketch-preview-and-artist-handoff.md),
  [попытки](0006-generation-attempts-and-usage.md),
  [хранение и удаление](0007-sketch-storage-uploads-and-deletion.md).
- **Состояние реализации:** ни один маршрут не реализован; сайт по-прежнему
  шлёт форму записи в Formspree.

## Контекст

ADR-0009 разделил систему на статический сайт и приложение на поддомене
и оставил уровню контрактов значение `SameSite` и защиту изменяющих запросов.
ADR-0011 закрыл обмен backend и генератора и перечислил, что остаётся этому
документу: как клиент передаёт ключ идемпотентности и узнаёт состояние
задания, cookie и CORS по ADR-0009, запрос «открытие версии». ADR-0010 отнёс
к API вопрос, кто задаёт negative prompt. Свип-ревью
[`2026-09-09-adr-sweep.md`](../reviews/2026-09-09-adr-sweep.md) добавило:
прокси или подписанная ссылка для предпросмотра (#26), автор negative prompt
(#27), момент создания записи «Эскиз» (#30), ключ идемпотентности (#32),
обращение гостя без регистрации (B-19).

Этот документ задаёт контракт между сайтом `ratedtattoo.ru` и приложением
на поддомене: форму, субъектов, защиту, ресурсы и ошибки. Мастер
и администратор через этот API не работают: их интерфейсы живут внутри
приложения (ADR-0009). Значения сроков, лимитов и интервалов — уровни 4 и 5.

## Решение в одном абзаце

HTTPS и JSON под префиксом `/api/v1`. Три субъекта — аноним, гость, клиент —
различаются одной host-only cookie сеанса; сессия создаётся первым
изменяющим действием, а не визитом. Изменяющие запросы защищены `SameSite=Lax`
и обязательной проверкой `Origin`; CORS разрешает единственный источник.
Действия, которые нельзя выполнить дважды, несут `Idempotency-Key`
от frontend. Состояние задания клиент узнаёт опросом ресурса; предпросмотр
идёт байтами через backend с проверкой права; «открытие версии» — отдельный
идемпотентный запрос. Обращение без вложения доступно без входа
(рекомендация, ждёт владельца), с эскизом или загрузкой — только клиенту.

## 1. Форма контракта

- **Транспорт.** HTTPS, тела запросов и ответов — JSON в UTF-8, кроме
  загрузки файла (`multipart/form-data`) и выдачи изображений (байты).
- **Префикс и версия.** Все маршруты под `/api/v1/`. Добавление необязательных
  полей и новых маршрутов версию не меняет. Ломающее изменение — удаление
  поля, смена типа, смена смысла кода ошибки — выходит под `/api/v2/`,
  а `/api/v1/` живёт до согласованного выпуска сайта (ADR-0009: изменение
  API без совместимости требует согласованного выпуска).
- **Конверт.** Единый для всех JSON-ответов по правилу проекта
  (`.claude/rules/common/patterns.md`):

      успех:  { "ok": true,  "data": …, "meta": { "next_cursor": … } }
      ошибка: { "ok": false, "error": { "code": "…", "message": "…", "fields": { … } } }

  `meta` присутствует только у списков. `message` — русский текст для
  показа клиенту; `fields` — ошибки по полям при `validation_failed`.
  Байтовые ответы конверта не имеют.
- **Идентификаторы** непрозрачные строки; порядок создания по ним
  не вычисляется. Время — ISO 8601 в UTC.

## 2. Субъекты и сеансы

| Субъект | Как распознаётся | Что может |
| --- | --- | --- |
| Аноним | Cookie нет или сеанс не найден | Читать `GET /me`, отправить обращение без вложения, начать гостевую генерацию или загрузку — это создаст гостевую сессию |
| Гость | Cookie указывает на гостевую сессию (ADR-0010) | Одна попытка по ADR-0006 — после неудачи она возвращается и `POST /sketches` доступен снова; эскизы и загрузки этой сессии, обращение без вложения, регистрация и вход с присоединением |
| Клиент | Cookie указывает на сеанс входа пользователя с ролью «клиент» | Всё в своём кабинете |

**Cookie.** Одна cookie `rt_session`: host-only для поддомена приложения
(без `Domain`), `Secure`, `HttpOnly`, `Path=/`, `SameSite=Lax`. Значение —
непрозрачный секрет, по которому backend находит либо гостевую сессию, либо
сеанс входа. `Lax` достаточно: `ratedtattoo.ru` и поддомен приложения имеют
один регистрируемый домен, для браузера это один сайт, и `fetch`
с `credentials: "include"` cookie отправит. Frontend cookie не читает
(ADR-0009).

**Когда сессия появляется.** Только при первом изменяющем действии субъекта
без сессии: `POST /sketches`, `POST /uploads`. `GET`-запросы и обращение без
вложения сессию не создают — иначе каждый визит бота оставлял бы запись.
Гостевая сессия получает абсолютный срок от создания (параметр уровня 4);
запросы клиента его не продлевают, поздний результат генерации тоже
(ADR-0007). Сеанс входа — скользящий срок с потолком (два параметра),
завершается `POST /auth/logout` или истечением.

**Смена секрета.** Регистрация и вход выдают новый секрет и заменяют cookie;
гостевой секрет ключом от аккаунта не становится (ADR-0002). Гостевая
сессия после присоединения остаётся до своего срока, но эскизов у неё
уже нет.

## 3. Защита изменяющих запросов и CORS

- **CSRF.** Два независимых барьера. `SameSite=Lax` не отправляет cookie
  с межсайтовых `POST`. Дополнительно каждый запрос, кроме `GET` и `HEAD`,
  обязан нести заголовок `Origin` со значением `https://ratedtattoo.ru`;
  иначе `403 origin_rejected` без выполнения. `Sec-Fetch-Site` эту проверку
  не заменяет: для запроса с `ratedtattoo.ru` он даёт `same-site`, как
  и для любого другого поддомена нашего домена, а как проверка
  `same-origin` непригоден; `Origin` называет хост точно.
  JSON-тела к тому же не «простые» запросы и проходят preflight; загрузка
  `multipart` — простой запрос, её держит проверка `Origin`.
- **CORS.** `Access-Control-Allow-Origin: https://ratedtattoo.ru`
  (единственное значение, не подстановка), `Access-Control-Allow-Credentials:
  true`, методы `GET, POST, PATCH, DELETE`, заголовки `Content-Type,
  Idempotency-Key`, `Access-Control-Expose-Headers: Retry-After, ETag` —
  иначе frontend не прочитает `Retry-After` на `429`, — `Access-Control-Max-Age`
  — параметр. В конфигурации
  разработки допускается второй origin локального dev-сервера; в проде его
  нет.
- **Ограничение частоты.** На маршрутах входа, регистрации, восстановления
  пароля, создания задания и загрузки — по IP и по сессии; превышение даёт
  `429 rate_limited` с `Retry-After`. Значения — уровень 4/5.

## 4. Идемпотентность

Заголовок `Idempotency-Key` — UUID, который frontend создаёт один раз
на действие пользователя и сохраняет при сетевых повторах; новое намеренное
действие получает новый ключ, даже если поля совпадают (ADR-0011). Обязателен
на `POST /sketches`, `POST /sketches/{id}/generations`, `POST /inquiries`;
без него `400 idempotency_key_required`. На остальных маршрутах
не принимается.

Область ключа — субъект и маршрут; у анонимного обращения субъекта нет,
и область — только маршрут, уникальность даёт сам UUID. Тот же ключ с тем же телом возвращает
уже созданный ресурс с `200` вместо `201`; тот же ключ с другим телом —
`409 idempotency_conflict`. Ключ хранится на созданном ресурсе и живёт
столько же (ADR-0010); при присоединении гостевого эскиза ключи гостевой
сессии переходят пользователю (ADR-0011).

Известное ограничение гостя: если потерялся ответ, которым backend впервые
поставил cookie, повтор придёт без неё, ключ сопоставить не с чем,
и появятся вторая гостевая сессия и вторая гостевая попытка. ADR-0006 уже
признаёт, что гостевая сессия не гарантирует одного человека; отдельного
механизма здесь нет.

## 5. Вход и профиль

| Маршрут | Тело | Ответ |
| --- | --- | --- |
| `POST /auth/register` | `email`, `first_name`, `last_name`, `password` | `201`, cookie нового сеанса, `data`: профиль, `attached_sketch_ids`, `attempts` |
| `POST /auth/login` | `email`, `password` | `200`, cookie нового сеанса, `data` как у регистрации |
| `POST /auth/logout` | — | `204`, cookie стирается, сеанс закрыт на сервере |
| `POST /auth/password-reset` | `email` | всегда `202`: письмо уходит, если аккаунт есть; ответ существование аккаунта не раскрывает |
| `POST /auth/password-reset/confirm` | `token`, `password` | `204`; повтор с тем же `token` — `409 token_used` |
| `GET /me` | — | `data`: `kind` (`anonymous`, `guest`, `client`), `profile` у клиента, `attempts` у гостя и клиента |
| `PATCH /me/profile` | `first_name`, `last_name`, `phone` — любые из них | `200`, профиль; только клиенту, гостю — `401 login_required` |

**Присоединение** гостевых эскизов входит в транзакцию регистрации и входа:
backend читает гостевую сессию из cookie, пришедшей с запросом, и переносит
её эскизы по таблице ADR-0002 в той же транзакции, что создаёт сеанс.
Поэтому состояние «вошёл, но не присоединилось» из ADR-0002 не возникает:
либо ответ с новой cookie и списком `attached_sketch_ids` дошёл, либо
клиент повторяет вход с прежней гостевой cookie и получает тот же итог.
Гостевой cookie нет или срок истёк — вход выполняется, список пуст.

**Регистрация.** Повтор с занятым email — `409 email_taken`; frontend
предлагает вход, и присоединение произойдёт там. Ответ раскрывает
существование аккаунта — сознательно, ради понятной формы; подбор
сдерживает ограничение частоты. Три регистрационные попытки начисляются
в транзакции создания аккаунта, один раз (ADR-0006). Подтверждение email
в первый выпуск не входит; тем самым открытый вопрос ADR-0002 «момент
активации попыток относительно подтверждения почты» решается по
необходимости: при регистрации. `attempts` в ответе — `available`
и `restores_at` (пусто, пока правило восстановления ADR-0006 не выбрано).

**Профиль.** Email и пароль через `PATCH /me/profile` не меняются: смена
адреса требует подтверждения (ADR-0002) и в v1 отсутствует. `phone`
не проверяется как подтверждённый номер.

## 6. Эскизы и генерация

| Маршрут | Назначение |
| --- | --- |
| `POST /sketches` | Новый эскиз и его первое задание одной транзакцией |
| `GET /sketches` | Свои эскизы, курсорная пагинация, новые первыми |
| `GET /sketches/{id}` | Эскиз с версиями и заданиями |
| `DELETE /sketches/{id}` | Удаление по порядку ADR-0010 |
| `POST /sketches/{id}/generations` | Новое задание на существующем эскизе |
| `GET /generations/{id}` | Состояние одного задания |
| `POST /sketches/{id}/versions/{vid}/view` | Открытие версии |
| `GET /versions/{vid}/preview` | Байты предпросмотра со знаком |

**`POST /sketches`.** Тело: `description` (текст клиента), `style`
(из перечня студии), `placement` и `size` (необязательны), `source` —
одно из `{ "kind": "text" }`, `{ "kind": "upload", "upload_id" }`,
`{ "kind": "version", "version_id" }`. Последнее — смена стиля от версии:
по ADR-0010 стиль эскиза не меняется, новый стиль даёт новый эскиз
с происхождением «другая версия». Транзакция `accepted` из ADR-0011 §1
дополняется записью «Эскиз»: эскиз, задание, резерв с проверкой остатка,
ключ идемпотентности, outbox — вместе. Это закрывает вопрос #30
свип-ревью: неудачное первое задание оставляет эскиз без версий, и кабинет
показывает его с состоянием задания и действием «Повторить». Ответ `201`:
эскиз и задание. Гость с исчерпанной попыткой — `409 no_attempts`.

**Negative prompt** клиент не вводит. Его источник — шаблон правил студии
в параметрах задания (ADR-0010, «три слоя»); в API поля нет. Это ответ
на вопрос #27 свип-ревью. Место нанесения и размер сохраняются на эскизе
и в Job пока не передаются — открыто со свип-ревью, генератор их не читает.

**`POST /sketches/{id}/generations`.** Тело: `parent_version_id`
(необязателен), `description` (необязателен, по умолчанию описание эскиза).
С `parent_version_id` — доработка: исходник для Job — оригинал этой версии,
новая версия получает её родителем. Без него — повтор по происхождению
эскиза: текст, либо та же загрузка, либо та же исходная версия, что
и у первого задания. Стиль всегда стиль эскиза. На эскизе с незавершённым
заданием второе создаётся: ADR-0010 допускает две параллельные доработки,
а указатель на них не реагирует.

**Ресурс эскиза.** `id`, `description`, `style`, `placement`, `size`,
`origin` (`text`, `upload` с `upload_id`, `version` с `version_id`),
`created_at`, `last_viewed_version_id`, `versions[]`, `generations[]`.
Версия: `id`, `parent_version_id`, `generation_id`, `preview_state`
(`preparing`, `ready`, `error`), `viewed` (открывал ли клиент — источник
отметки «Новая»), `created_at`. Задание: `id`, `state`, `failure`,
`parent_version_id`, `version_id` при успехе, `created_at`, `deadline_at`.

**Состояние задания для клиента** — три значения, а не шесть из ADR-0011:

| Клиентское `state` | Состояния задания в backend | Что показать |
| --- | --- | --- |
| `pending` | `accepted`, `dispatched`, `awaiting_reconciliation` | Ожидание; сверка от задержки клиенту не отличается |
| `succeeded` | `succeeded` | Версия с `version_id`; предпросмотр может ещё готовиться |
| `failed` | `failed` | `failure.reason` из группы `generation_failed`, `timed_out`, `service_unavailable` и текст; попытка возвращена |

`cancelled` клиенту не показывается: оно возникает только при удалении
эскиза, после которого эскиз отвечает `404`. Каждое `failed` возвращает
попытку по ADR-0011, поэтому отдельного поля об этом нет. Для `succeeded`
по удалённому эскизу ответа тоже нет — эскиза нет.

**Как клиент узнаёт состояние.** Опросом `GET /generations/{id}` либо
`GET /sketches/{id}`, пока `state` = `pending`. Интервал — параметр
frontend (рекомендация 3 с). `deadline_at` в ответе — ориентир, а не
гарантия: после него backend завершит задание своей транзакцией по сроку,
как только до него дойдёт (ADR-0011: при недоступности — после
восстановления), поэтому frontend продолжает опрос ещё ограниченное время
после `deadline_at` и затем показывает «истекло», не меняя своих данных;
источник истины — ресурс, не часы клиента. Server-Sent Events
и WebSocket отвергнуты для v1: статическому сайту и одному заданию
за раз опрос достаточен, а долгие соединения добавили бы требования
к балансировщику на уровне инфраструктуры.

**Открытие версии** — `POST /sketches/{id}/versions/{vid}/view`, `204`.
Выполняет два условия владельца из ADR-0010: повтор безопасен (второй вызов
ничего не меняет), а загрузка списка и предзагрузка изображения просмотром
не считаются — frontend вызывает его только когда клиент явно открыл
версию в просмотрщике или переключился на неё, не при рендере карточек
и не по `onload` картинки. Запрос переводит `last_viewed_version_id`
эскиза и ставит отметку `viewed` на версии. Первая версия эскиза становится
показываемой автоматически без запроса (таблица событий ADR-0010).

**Предпросмотр** — `GET /versions/{vid}/preview` отдаёт байты изображения
со знаком через backend после проверки права (ADR-0010: изображение
не приходит из хранилища напрямую; вопрос #26 свип-ревью решён в пользу
прокси). Заголовки `Cache-Control: private, max-age` (параметр), `ETag`;
`Content-Type` из записи «Файл». Пока `preview_state` не `ready` —
`404 preview_not_ready`; состояние клиент читает из ресурса версии, а не
по этому коду. Оригинал версии клиенту не выдаётся никаким маршрутом
(ADR-0003); адреса хранилища в ответах не появляются.

**Удаление** — `DELETE /sketches/{id}`, `204`; выполняет первую транзакцию
порядка удаления ADR-0010 и отвечает после неё, физическая очистка идёт
следом. Повторный вызов — `404`: эскиза больше нет. Незавершённое задание
доводится по ADR-0011 §5, клиент этого не видит.

## 7. Загрузки

| Маршрут | Назначение |
| --- | --- |
| `POST /uploads` | `multipart/form-data`, поле `file`; проверка содержимого до ответа |
| `GET /uploads` | Свои принятые загрузки |
| `GET /uploads/{id}/content` | Байты своей загрузки без знака |
| `DELETE /uploads/{id}` | Удаление загрузки |

Проверка синхронная: backend декодирует изображение и проверяет тип, размер
и число пикселей, не доверяя заголовкам (ADR-0007); отклонённый файл
не сохраняется, ответ `422 upload_rejected` с причиной. Принятая загрузка —
`201` с `id`, `media_type`, `width`, `height`. Ограничения формата
и размера — параметры уровня 4. Гостю загрузка разрешена в пределах гостевой
сессии и присоединяется вместе с эскизами; ADR-0007 оставлял это
на проработку, здесь решено «да». Знак на собственный файл не накладывается
(ADR-0007). `DELETE /uploads/{id}` разрешён всегда: по ADR-0007 ссылка
из обращения не исключение из требования удаления, и обращение перестаёт
выдавать вложение — в карточке мастера остаётся «Эскиз удалён клиентом».
Для загрузки, ставшей происхождением эскиза, ADR-0007 вопрос оставляет
открытым; здесь по умолчанию удаление разрешено, а последующий
`POST /sketches/{id}/generations` без `parent_version_id` на таком эскизе
отвечает `409 origin_deleted` — пункт 5 «Открытых решений для владельца».

## 8. Обращение к мастеру

`POST /inquiries`, `Idempotency-Key` обязателен. Тело: `subject` — одно
из `{ "version_id" }`, `{ "upload_id" }`, `null`; `first_name`, `last_name`,
`phone` (обязателен), `message` (необязателен). Ответ `201`: `id`, `state`
(`received`), `created_at`. `GET /inquiries` — свои обращения клиента,
только с состоянием `received`: ADR-0003 велит показывать лишь то, что
backend может подтвердить, а доставка мастеру — внутреннее дело.

Backend сохраняет снимок полей на момент отправки (ADR-0010), проверяет
право на `version_id` или `upload_id` (чужое — `404`) и телефон; телефон
из обращения заполняет пустой телефон профиля, заполненный
не перезаписывает (предположение ADR-0010, владельцем не подтверждено).

**Кому доступно.** С `subject` — только клиенту: ADR-0003 описывает выбор
версии в кабинете, ADR-0010 записывает обращение за клиентом. Без `subject`
— гостю и анониму: это нынешняя форма записи с сайта (имя, телефон,
описание идеи), которая по ADR-0009 переезжает с Formspree на API;
требовать регистрацию для звонка мастеру — регресс относительно прода.
Для такого обращения поле «Клиент» записи становится необязательным.
Это ответ на вопрос B-19, который владелец ещё не дал; здесь он
рекомендация, см. «Открытые решения для владельца». Альтернатива — запрет
`subject = null` без входа — одна проверка, решение обратимо.

## 9. Ошибки

| HTTP | `code` | Когда |
| --- | --- | --- |
| 400 | `malformed_request`, `idempotency_key_required` | Не JSON, нет обязательного заголовка |
| 401 | `login_required`, `invalid_credentials` | Гость или аноним там, где нужен клиент, истёкший сеанс; неверные email или пароль при входе |
| 403 | `origin_rejected` | Изменяющий запрос без верного `Origin` |
| 404 | `not_found`, `preview_not_ready` | Нет ресурса или он чужой — существование чужого не раскрывается (ADR-0002) |
| 409 | `idempotency_conflict`, `email_taken`, `no_attempts`, `token_used`, `origin_deleted` | Конфликт состояния; `no_attempts` несёт `restores_at`, если правило ADR-0006 выбрано |
| 413 | `upload_too_large` | Превышен лимит загрузки |
| 415 | `unsupported_media_type` | Не изображение или неподдерживаемый формат |
| 422 | `validation_failed`, `upload_rejected` | Ошибки полей в `fields`; файл не декодируется |
| 429 | `rate_limited` | С `Retry-After` |
| 503 | `generation_paused` | Администратор остановил новые генерации (ADR-0010, «один выключатель»); кабинет работает |

Ошибки входа отвечают одинаково на неверный email и неверный пароль —
`401 invalid_credentials`, чтобы не раскрывать аккаунты (OWASP, ADR-0002);
исключение с `email_taken` описано в разделе 5.

## 10. Гонки, которые контракт закрывает

- **Регистрация или вход во время генерации.** Присоединение переносит
  эскиз вместе с его незавершённым заданием и ключами; завершение задания
  добавляет версию к тому же эскизу и владельца не восстанавливает
  (ADR-0002). Клиент видит результат в кабинете без повторной генерации.
- **Истечение гостевой сессии во время генерации.** Задание доводится
  до конца, гостевая очистка по ADR-0007 удаляет эскиз тем же порядком,
  что и удаление клиентом; поздний результат сессию не продлевает
  и в кабинете не появляется.
- **Удаление во время генерации.** Порядок ADR-0010, обработка
  у генератора — ADR-0011 §5; для клиента эскиз сразу `404`.
- **Двойная отправка.** Две вкладки или сетевой повтор с тем же
  `Idempotency-Key` дают один ресурс; резерв попытки берётся один раз
  (ADR-0006, ADR-0011 §1).

## Отвергнутые варианты

| Вариант | Почему отвергнут |
| --- | --- |
| Общий домен cookie `.ratedtattoo.ru` | Отправлял бы секрет на хост статики; host-only доходит до API и так (ADR-0009) |
| `SameSite=None` | Не нужен: хосты — один сайт; `None` лишь ослабил бы первый барьер CSRF |
| Токен CSRF в теле или заголовке | `Lax` плюс проверка `Origin` закрывают угрозу без состояния на клиенте; токен потребовал бы отдельного маршрута выдачи |
| Presigned URL на предпросмотр | ADR-0010 требует выдачу через backend; ссылка с подписью жила бы дольше права и обходила проверку при присоединении и удалении |
| Server-Sent Events или WebSocket для состояния задания | Одно задание за раз и статический сайт; долгие соединения — требование к балансировщику, которого пока нет |
| Отдельная cookie для гостя и клиента | Две cookie — два срока и два пути проверки; одна cookie с типом сеанса в базе проще |
| Сессия на каждом визите | Каждый бот оставлял бы запись гостевой сессии; сессия появляется с первым действием |
| Асинхронная проверка загрузки с опросом | Декодирование одного изображения укладывается в запрос; асинхронность добавила бы состояние «проверяется» и ещё один опрос |
| Идемпотентность через повтор ответа целиком | Хранить ответы дорого; достаточно вернуть созданный ресурс по ключу |

## Следствия

- `FORMSPREE_ENDPOINT` в `BookingModal` заменяется на `POST /api/v1/inquiries`
  с `subject = null`; имя и телефон перестают уходить за рубеж (ADR-0009).
- ADR-0011 §1: транзакция `accepted` для первого задания эскиза включает
  запись «Эскиз» (уточнение, при согласии владельца).
- ADR-0010: поле «Клиент» записи «Обращение» становится необязательным
  для обращений без вложения — только если владелец примет рекомендацию
  по B-19; до этого ADR-0010 не правится.
- ADR-0002: состояние «вошёл, но присоединение не подтверждено» не нужно —
  присоединение внутри транзакции входа.
- ADR-0006: три регистрационные попытки начисляются при создании аккаунта,
  подтверждение email в v1 отсутствует.
- Сайт получает экраны входа, регистрации, восстановления пароля, кабинет
  с историей версий и опросом задания; публикация остаётся статической.

## Открытые решения для владельца

1. **B-19, обращение без входа.** Рекомендация: без вложения — можно
   (нынешняя форма записи), с эскизом или загрузкой — только клиент.
   Альтернатива: любое обращение только после входа. Спрошено трижды,
   ответа нет.
2. **Записи мастера.** ADR-0010: клиент видит свои будущие сеансы.
   В v1 маршрута нет; предлагаю `GET /me/appointments` только для чтения
   отложить до появления журнала мастера в приложении.
3. **Гостевая загрузка.** Здесь разрешена; ADR-0007 оставлял на проработку.
4. **Регистрация раскрывает занятый email** ради понятной формы;
   альтернатива — нейтральный ответ и письмо «у вас уже есть аккаунт».
5. **Удаление загрузки, ставшей происхождением эскиза.** ADR-0007:68
   оставляет открытым. Здесь по умолчанию разрешено, повтор генерации
   по происхождению после этого отвечает `409 origin_deleted`;
   альтернатива — запрет удаления, пока эскиз жив.

## Параметры, которые контракт не фиксирует

- Сроки: гостевой сессии, сеанса входа и его потолка, кэша предпросмотра,
  `Access-Control-Max-Age`, окно опроса после `deadline_at`.
- Лимиты загрузки: форматы, байты, пиксели, число файлов.
- Ограничения частоты по маршрутам.
- Перечень стилей, мест нанесения и размеров — справочник студии.
- Подтверждение email, смена email, Яндекс ID — вне v1 (ADR-0002).
- API мастера и администратора — внутри приложения, вне этого контракта.
