## Контекст

ADR-0010 задал две очереди, доставку минимум один раз, запись `ProviderCall`
до платного вызова, перечни состояний Job и `ProviderCall`, финансовый исход
по созданному оригиналу, порядок удаления и обработку позднего Result.
Этот документ не пересматривает эти решения, а достраивает их переходами
и сообщениями. Владелец задал пять вопросов, на которых сходятся главные
незакрытые места: принятие задания, выполнение, неизвестный исход,
принятие результата, удаление во время работы. Шестой раздел фиксирует
сообщения. Сначала состояния и переходы, затем сообщения.

Термины: **задание генерации** — запись backend по ADR-0010 (в сообщениях
`GenerationJob`); **Job** — запись генератора; **`ProviderCall`** — запись
одной попытки платного вызова модели у генератора и её копия в backend;
проверка состояния внешней операции и скачивание её результата относятся
к этой попытке и новой записи не создают.

## Решение в одном абзаце

Обмен идёт тремя сообщениями в двух направлениях: `SubmitJob`
и `EraseGeneration` от backend к генератору, `Result` от генератора
к backend. Обе стороны пишут исходящие сообщения через outbox в одной
транзакции с изменением своих записей и подтверждают входящие только после
фиксации. Источник истины на каждой стороне — её база, а не очередь. Result
несёт полный снимок состояния задания у генератора с монотонной ревизией.
Подтверждения от backend генератору нет: у генератора нет действия, которое
должно ждать принятия результата.

## Состояния

### Задание генерации в backend

| Состояние | Что означает | Резерв попытки |
| --- | --- | --- |
| `accepted` | Одна транзакция: задание, резерв с проверкой остатка, ключ идемпотентности, запись на отправку. Здесь backend отвечает клиенту номером задания | Держится |
| `dispatched` | Очередь подтвердила приём `SubmitJob`. Только диагностика: клиенту разница не видна | Держится |
| `awaiting_reconciliation` | Генератор прислал Result с этим состоянием: исход внешнего вызова неизвестен, идёт сверка | Держится; `deadline_at` не приостанавливается |
| `succeeded` | Backend зафиксировал оригинал; при удалённом эскизе — принял Result `succeeded` без создания версии (раздел 5) | Списан |
| `failed` | Ошибка генератора, срок отправки, общий срок, отсутствие или несовпадение файла результата | Возвращён |
| `cancelled` | Генератор подтвердил отмену до создания оригинала | Возвращён |

У задания есть поле причины завершения. В него копируется `reason_code`
генератора либо ставится собственный код backend:
`dispatch_deadline_exceeded`, `execution_deadline_exceeded`,
`result_file_missing`, `result_file_mismatch`. Backend не приписывает генератору состояние,
о котором тот не сообщал: коды генератора и коды backend не смешиваются.

Кроме состояния задание хранит: ключ идемпотентности, `deadline_at`,
последнюю применённую ревизию Result, время подтверждения стирания.

### Job у генератора

Состояния по ADR-0010: `queued`, `running`, `awaiting_reconciliation`,
`succeeded`, `failed`, `cancelled`. Дополнительно Job хранит: текущий этап
выполнения из закрытого перечня, аренду исполнителя (идентификатор и срок),
`deadline_at` из `SubmitJob`, подготовленный запрос к графической модели,
дескриптор результата (`call_id`, `sha256`, размер, тип), зафиксированный
до первой записи в `transfer/output/` (§2), признаки стирания `erase_requested_at` и `content_erased_at`. Запись Job
может существовать и как tombstone: `cancelled` с признаками стирания,
созданная по `EraseGeneration`, пришедшему раньше `SubmitJob`.

### `ProviderCall`

Состояния по ADR-0010: `pending`, `running`, `succeeded`, `failed`,
`outcome_unknown`. Создание записи в `pending` — это зафиксированное
намерение выполнить платный вызов: оно делается в одной транзакции
с проверкой барьера стирания на записи Job, и с этого момента запрос
провайдеру «мог уйти». Восстановление и удаление опираются на это правило.
Отдельной ревизии у `ProviderCall` нет: ревизия одна на весь Result.

## 1. Принятие задания

Outbox. Запрос клиента фиксируется одной транзакцией: задание генерации
в `accepted`, резерв попытки с проверкой остатка — одна атомарная операция,
отрицательный доступный остаток запрещён, при одной оставшейся попытке
из двух конкурирующих заданий принимается ровно одно (ADR-0010 «Гарантия
резерва»), — ключ идемпотентности,
запись на отправку `SubmitJob`; для первого задания нового эскиза — в той же
транзакции запись «Эскиз» (уточнение 2026-09-11 по решению владельца
к ADR-0012: неудачное первое задание оставляет эскиз без версий, кабинет
показывает его с состоянием задания). Backend отвечает клиенту сразу после
фиксации. Потеря ответа покрывается повтором запроса с тем же ключом.

**Исходник.** Задание с исходным изображением — доработка от версии, новый
эскиз от версии или от загрузки — получает собственную копию исходника
и после фиксации от судьбы источника не зависит. Порядок повторяет приём
результата из раздела 4, только в обратную сторону: backend выбирает
`job_id`, копирует оригинал версии или файл загрузки серверным `COPY`
в `transfer/input/<job_id>/source`, затем выполняет транзакцию `accepted`,
в которой под блокировкой записи владельца источника — записи загрузки
либо записи эскиза, которому принадлежит исходная версия, — проверяет, что
источник не помечен удалённым. Ту же блокировку берут удаление загрузки
и первая транзакция порядка удаления эскиза (ADR-0010), поэтому принятие
задания и удаление источника выполняются строго одно после другого,
и предварительной проверки вне транзакции недостаточно. Если удаление
успело первым, транзакция не фиксируется, backend отвечает по ADR-0012
и удаляет копию; копия, оставшаяся после сбоя между `COPY` и транзакцией,
подбирается правилом жизненного цикла `transfer/`. Дескриптор копии
(`key`, `size`, `media_type`, `sha256`) уходит в `SubmitJob`; генератор
читает только её. Граница независимости точная: удаление отдельной
загрузки или другого эскиза-источника уже принятое задание не отменяет —
у него своя копия, а по ADR-0012 удалённая загрузка лишь помечает
происхождение эскиза недоступным для повторов. Удаление эскиза, которому
принадлежит само задание, — в том числе при доработке внутри одного эскиза,
где источник и результат принадлежат ему же, — всегда идёт по разделу 5:
пометка, `EraseGeneration`, барьер, независимо от наличия копии исходника
(уточнение 2026-09-11 по решению владельца, граница уточнена его
замечанием того же дня; правило для источника-версии и порядок копирования
выведены мной).

**Отправка.** Отдельный процесс читает записи на отправку и шлёт с повторами
и нарастающей паузой. Запись удаляется только после подтверждения очереди,
поэтому одно задание может уйти дважды: генератор распознаёт повтор
по `job_id`. Подтверждение очереди переводит только `accepted` →
`dispatched`; позднее подтверждение уже завершённое состояние не меняет.
Result принимается и из `accepted`, и из `dispatched`. Любой Result
доказывает доставку, поэтому его приём снимает запись на отправку,
если она ещё есть. Запись на отправку снимается и при любом завершении
задания в той же транзакции.

**Просрочка отправки.** Срок один, задаётся настройкой. По истечении задание
переходит в `failed` с причиной `dispatch_deadline_exceeded` — «доставка
не подтверждена», а не «не отправлено»: очередь могла принять сообщение,
а подтверждение потеряться. Переход, возврат резерва и прекращение повторов
фиксируются одной транзакцией. Она конкурирует с приёмом Result:

| Что backend зафиксировал первым | Что происходит дальше |
| --- | --- |
| Принятие успешного результата | Просрочка отправки задание не завершает и резерв не возвращает |
| Завершение по сроку отправки | Поздний Result сохраняет технический учёт; версия не создаётся, попытка не списывается |

Уже начатая отправка может закончиться после этой транзакции; такой Result
тоже поздний. Возможный расход у провайдера в этом редком случае несёт
студия.

**Общий срок.** При принятии backend фиксирует абсолютный `deadline_at`
и передаёт его в `SubmitJob`. В срок заложены ожидание отправки
и исполнения, разрешённые вызовы и повторы, сохранение файла и доставка
результата. По истечении backend завершает задание `failed`
с `execution_deadline_exceeded` и возвращает резерв одной транзакцией;
гонка с приёмом Result решается по той же таблице. Часы backend
и генератора должны совпадать в пределах секунд; обе части в одном
облаке.

**Ключ идемпотентности.** Создаёт frontend один раз на действие
пользователя и сохраняет при сетевых повторах; новый намеренный запрос
получает новый ключ, даже если параметры совпадают. Backend обеспечивает
уникальность в области вызывающего субъекта и операции; тот же ключ
с другим содержимым запроса возвращает конфликт. Содержимое сравнивается
по хешу канонического представления клиентского запроса до серверного
обогащения; правила канонической формы, отсутствующих полей и `null` —
ADR-0013 §4 (перенесено 2026-09-14 по решению владельца, S-11). Запись ключа входит
в транзакцию `accepted`; ключ хранится на записи задания и живёт столько
же, сколько оно, независимо от outbox-записи. При присоединении гостевого
эскиза к аккаунту по ADR-0002 ключи гостевой сессии переходят пользователю
в той же транзакции, что и эскизы, иначе прежний ключ стал бы «новым».
Ключ не считается клиентским содержимым и при удалении не затирается.

## 2. Выполнение у генератора

Источник истины — база генератора. Сообщение очереди только доставляет
задание. Получив `SubmitJob`, генератор фиксирует Job в базе и после
фиксации подтверждает сообщение; если выполнение начинается сразу, захват
с арендой сохраняется в той же транзакции. Подтверждение означает, что
генератор надёжно принял задание и отвечает за его выполнение; сообщение
в очереди до конца работы не удерживается.

Повтор `SubmitJob` распознаётся по `job_id` и нового задания не создаёт.
Действие по состоянию записи:

| Состояние записи | Действие |
| --- | --- |
| Нет записи | Создать в `queued`, захватить, выполнять |
| `queued` | Захватить, выполнять |
| `running`, аренда жива | Подтвердить сообщение, ничего не делать: работа у другого исполнителя |
| `running`, аренда истекла | Восстановление, см. ниже |
| `awaiting_reconciliation` | Подтвердить, ничего не делать |
| Завершено, в том числе tombstone | Дописать недостающие технические сведения, если их нет; prompt не восстанавливать, состояние не менять, работу не запускать; повторно отправить текущий Result |

**Аренда.** Захват — условное обновление записи Job идентификатором
исполнителя и сроком аренды; аренда продлевается по ходу работы.
Истечение аренды само по себе не разрешает повторный платный вызов.

**Восстановление.** Отдельный процесс генератора находит незавершённые
задания и задания с истёкшей арендой, смотрит сохранённый этап и последний
`ProviderCall` и определяет, как продолжить. Если последний вызов
в `pending` или `running`, запрос мог уйти провайдеру: вызов переводится
в `outcome_unknown`, Job — в `awaiting_reconciliation`, дальше раздел 3.
Если вызова нет или последний завершён, задание захватывается заново
и продолжается со следующего этапа. Последующие этапы повторяются, пока
доступен необходимый результат предыдущего этапа; иначе применяется
определённый исход потери данных — «Потеря результата» ниже. Для
повторяемости подготовленный запрос сохраняется в Job до вызова
графической модели, чтобы не платить текстовой модели дважды; ключ файла
определён `job_id`; Result и запись на его отправку сохраняются одной
транзакцией через outbox генератора.

**Порядок после платного вызова графической модели** (уточнение
2026-09-14 по свип-ревью). Платный вызов текстовой модели (этап `prepare`)
через запись в `transfer/output/` не проходит: его результат —
подготовленный запрос в Job. Для вызова графической модели:
исход `ProviderCall` (`succeeded`) фиксируется → байты результата
скачиваются и проверяются → в Job фиксируется дескриптор результата →
объект записывается в `transfer/output/` → отдельной транзакцией
фиксируется подтверждение записи `result_stored_at` → публикуется Result.
Дескриптор фиксируется только после `succeeded` вызова с тем же `call_id`;
`result_stored_at` — только после успешного ответа хранилища. Обе записи
идут с проверкой поколения аренды (ADR-0013 §7) и относятся к технической
информации. Исполнитель, потерявший аренду, новую запись объекта
не начинает.

**Идентичность байтов результата** (решение владельца 2026-09-14). Перед
первой записью в `transfer/output/` генератор фиксирует в Job дескриптор
результата: выбранный `call_id`, SHA-256, размер и тип. Дескриптор
записывается один раз и не перезаписывается: исполнитель, получивший
работу после восстановления, сверяет свои байты с уже зафиксированным
дескриптором (уточнение 2026-09-14 по свип-ревью). Каждый повтор
записи сверяет подготовленные байты с этим дескриптором; несовпадающее
содержимое в тот же ключ не отправляется. В первом выпуске в хранилище
передаются исходные байты изображения провайдера без перекодирования.
Повторно полученные байты сверяются с сохранённым дескриптором. При
несовпадении они не отправляются в `transfer/output/`, дескриптор
не изменяется. Получение результата того же вызова повторяется до
`deadline_at`. Достоверное подтверждение невозможности получить исходный
результат завершает Job с `result_payload_unavailable`; исчерпание
времени — с `result_delivery_deadline_exceeded`. Новая платная генерация
не запускается (решение владельца 2026-09-14: несовпадение — неудачная
попытка получения, а не доказательство невосстановимости). Одной
детерминированности обработки недостаточно: повторно скачанная ссылка
может вернуть другое содержимое, а версия обработчика — измениться.
Успешный Result публикуется после подтверждённой записи объекта.

**Потеря результата** (решения владельца 2026-09-14). Причина
`result_payload_unavailable` применяется, когда успешный исход вызова
достоверно сохранён, а продолжить передачу результата невозможно: байты
потеряны, получить их повторно у провайдера нельзя, сохранённого
подтверждения записи объекта (`result_stored_at`) нет.

Невосстановимость устанавливается по контракту маршрута. Основания:
провайдер возвращает результат только в ответе, который потерян; срок
получения окончательно истёк и обновить ссылку нельзя; получен
документированный окончательный отказ в выдаче результата. Таймаут,
временная ошибка и истечение одной ссылки при возможности получить новую
невосстановимость не доказывают: получение повторяется до `deadline_at`.
Несовпадение повторно полученных байтов с дескриптором — тоже неудачная
попытка получения, а не основание невосстановимости.
Подтверждение успеха провайдером без изображения само по себе основанием
не служит. Если передачу результата известного успешного вызова не удалось
завершить за отведённое время, причина — `result_delivery_deadline_exceeded`:
исчерпание времени отделено от доказанной потери содержимого.

Result `failed` с `result_payload_unavailable` или
`result_delivery_deadline_exceeded` включает `result_candidate` (`key`,
`call_id`, `sha256`, `size`, `media_type`), если в Job сохранён дескриптор
результата успешного вызова графической модели; если дескриптор
зафиксировать не успели, кандидата нет. Отдельный признак «первая запись
начата» не нужен. Кандидат говорит только, что объект мог быть записан:
разница между двумя кодами объясняет, почему генератор прекратил
передачу, но наличие файла не устанавливает — итог по кандидату
устанавливает backend (§4 «Кандидат результата»).

| Запись | Итог |
| --- | --- |
| `ProviderCall` | Сохраняет `succeeded` и достоверные сведения о расходе |
| Job | `failed` с `result_payload_unavailable` или `result_delivery_deadline_exceeded`; backend его не переписывает |
| Задание backend | Проверяет кандидата и устанавливает собственный итог (§4 «Кандидат результата») |
| Повтор платной генерации | Автоматически не запускается |

Если оригинал не принят, расход провайдера несёт студия. Если достоверный исход не успел
сохраниться и вызов остался в `pending` или `running`, действует сверка
неизвестного исхода (§3); `result_payload_unavailable` не подменяет
`provider_outcome_unresolved`. Для завершённых заданий и удалённых эскизов
действуют правила §4 и §5. Сохранение ответа провайдера в надёжном
хранилище до записи результата в первом выпуске не вводится: оно
сокращает риск после надёжного сохранения, но не закрывает промежуток
между получением ответа и этой записью, а добавляет хранилище клиентского
содержимого с собственной очисткой.

Перед каждым новым платным вызовом генератор проверяет остаток времени
до `deadline_at` и отсутствие барьера стирания.

## 3. Неизвестный исход

Сверяет генератор: только у него ключи провайдера, внешний request id
и запись `ProviderCall`. Backend в сверке не участвует.

**Способ сверки — свойство маршрута.** Если провайдер даёт идентификатор
операции и метод проверки, генератор опрашивает его по `external_request_id`.
Если ответ был синхронным и потерялся, а метода проверки нет, достоверной
сверки не существует, остаётся окно ожидания. Наличие способа проверки
и смысл ответов провайдера — обязательные пункты контракта маршрута
в исследовании роутера: таймаут, разрыв соединения и ответ «операция
не найдена» сами по себе не доказывают, что генерация не выполнялась.

**Окно и остаток времени.** Окно сверки задаётся настройкой на маршрут,
попытки с нарастающей паузой; генератор учитывает остаток до `deadline_at`.
Пока задание ждёт сверки, генератор публикует Result со состоянием
`awaiting_reconciliation`: backend держит резерв и отличает сверку
от задержки или падения генератора. Срок это не продлевает.

| Сверка показала | `ProviderCall` | Job |
| --- | --- | --- |
| Результат есть | `succeeded` | Скачивание и дальше по обычному пути |
| Вызов не выполнен | `failed` | Новый платный вызов допускается только после достоверно установленного окончательного исхода, если ошибка допускает повтор и остаются время и лимит вызовов на задание |
| Установить нельзя | `outcome_unknown` как итог вызова | `failed` с `provider_outcome_unresolved` |

**Стоимость отдельно от исхода.** Если провайдер подтвердил списание,
расход фактический даже при `outcome_unknown`; признак «неизвестная»
ставится только при неизвестной стоимости. Backend по
`provider_outcome_unresolved` возвращает попытку; возможный расход несёт
студия. Поздние достоверные сведения уточняют технический учёт повторным
Result, но не меняют завершённый клиентский итог и не отменяют возврат.

Промежуточных сообщений о ходе выполнения, кроме состояния
`awaiting_reconciliation` в снимке Result, в первом выпуске нет. Если
позже понадобится единый экран в админке, сообщения о ходе войдут в тот же
снимок с ревизией: они обновляют диагностику, не продлевая срок и не меняя
завершённое состояние.

## 4. Принятие результата

«Оригинал сохранён» означает, что backend принял его и зафиксировал ссылку
на него; сам файл копируется до транзакции. Порядок для Result
со состоянием `succeeded`:

1. Найти задание. Если Result с этой или меньшей ревизией уже применён,
   подтвердить сообщение. Если ревизия больше, применить, даже когда
   задание завершено: сведения учёта обновляются, версия, списание
   и предпросмотр повторно не создаются, шаги 2–3 пропускаются. Если
   задание уже завершено самим backend — по сроку отправки, общему сроку,
   отсутствию или несовпадению файла, — действует правило позднего Result. Пометка
   эскиза удалённым задание не завершает: Result по удалённому эскизу
   применяется по разделу 5.
2. Проверить объект в `transfer/output/` по размеру, типу и хешу из Result.
   `result_file_missing` фиксируется только при достоверном отсутствии
   объекта; таймаут или недоступность хранилища — повтор в пределах общего
   срока задания. Достоверное несовпадение размера, типа или SHA-256
   фиксируется как `result_file_mismatch` (решение владельца 2026-09-14):
   для действующего задания по неудалённому эскизу — `failed`, возврат
   резерва, сохранение учёта из Result, версия не создаётся. Сетевая
   ошибка несовпадением не считается. Переход с `result_file_mismatch`
   подчиняется тем же правилам, что переход с `result_file_missing` ниже:
   общему правилу транзакций по Result и перепроверке пометки удаления.
   Объект может отсутствовать и законно: другой обработчик
   того же Result уже принял его и выполнил шаг 6, либо параллельное
   удаление эскиза уже убрало `transfer/output/` шагом 4 порядка удаления
   ADR-0010. Поэтому переход в `failed` с `result_file_missing`
   подчиняется общему правилу транзакций по Result ниже и, как шаг 4,
   перепроверяет пометку удаления под блокировкой записи эскиза: если
   пометка стоит, действует правило удалённого эскиза (раздел 5) — Result
   `succeeded` применяется как есть, попытка списывается, а не
   возвращается через `result_file_missing`.
3. Создать запись «Файл» в состоянии «ожидает» с ключом назначения
   и `job_id`; запись одна на ключ, повторное создание возвращает
   существующую. Затем серверный `COPY` в клиентскую область. Ключ
   выводится из `job_id`, поэтому повторное копирование перезаписывает
   тот же объект. Объект результата после публикации Result генератор
   не заменяет: уточнения учёта сохраняют прежнюю идентичность результата.
4. Одна транзакция с повторной проверкой трёх условий: задание
   не терминально, ревизия Result больше последней применённой, эскиз
   не помечен удалённым. Проверка пометки идёт под блокировкой записи
   эскиза — той же, которую берёт первая транзакция порядка удаления
   ADR-0010, — поэтому принятие и удаление одного эскиза выполняются
   строго одно после другого, и обработчик, прочитавший пометку
   на шаге 1 ещё до удаления, не создаст версию после него. Если все три
   условия выполнены: версия эскиза с оригиналом и предпросмотром
   в состоянии «готовится»; «Файл» условным переходом из «ожидает»
   в «принят»; копии вызовов и расхода по `call_id`; задание
   в `succeeded`; резерв в списание; запись на подготовку предпросмотра;
   снятие записи на отправку; последняя применённая ревизия. Если эта
   или более новая ревизия уже применена другим обработчиком, транзакция
   ничего не меняет. Если ревизия новее, а задание за время копирования
   завершилось, транзакция обновляет снимок учёта и ревизию, клиентский
   итог не трогает. Если эскиз за время копирования помечен удалённым,
   состояние и расчёт берутся из Result по разделу 5, версия не создаётся.
   Во всех трёх случаях скопированный объект удаляется по правилу очистки
   ниже, а не безусловно.
5. Подтвердить сообщение после фиксации. Сбой между шагами приводит
   к повторной доставке; все шаги до фиксации повторяемы.
6. Удалить `transfer/output/<job_id>/` и, если задание шло с исходником,
   `transfer/input/<job_id>/`. Сбой не страшен: правило жизненного цикла
   подберёт остаток.

Result со состоянием `failed` или `cancelled` идёт короче: транзакция
переводит задание в то же состояние с `reason_code` генератора, копирует
учёт, возвращает резерв; подтверждение после фиксации. Result
с `awaiting_reconciliation` переводит задание в это состояние и копирует
учёт. Исключение — `failed` с `result_payload_unavailable` (ниже).

**Очистка после отказа** (решение владельца 2026-09-14, S-10). Транзакция,
завершающая задание отказом — короткий путь `failed` и переход
в `result_file_mismatch`, — фиксирует обязанность удалить
`transfer/output/<job_id>/`; само удаление выполняется после транзакции
с повторами (ADR-0014 §2). В ветке кандидата очистка начинается после
решения о кандидате. Остатки и поздние записи подбирает правило
жизненного цикла.

**Кандидат результата** (решения владельца 2026-09-14, S-1 и уточнение).
Result `failed` с `result_payload_unavailable` или
`result_delivery_deadline_exceeded` — явное исключение из короткого пути:
генератор сообщает, что не смог завершить передачу, а backend
устанавливает собственный итог; сохранённое состояние генератора
не переписывается. Обработка для обоих кодов общая. Для незавершённого
задания по неудалённому эскизу:

| Проверка объекта `result_candidate.key` по кандидату | Итог backend |
| --- | --- |
| Объект совпал с кандидатом по размеру, типу и SHA-256 | Обычное принятие оригинала по шагам 3–6, списание попытки |
| Объекта достоверно нет или кандидата нет | `failed` с исходной причиной генератора (`result_payload_unavailable` или `result_delivery_deadline_exceeded`), возврат резерва |
| Объект достоверно не совпал | `result_file_mismatch`, возврат резерва |
| Хранилище временно недоступно | Повтор проверки в пределах общего срока задания |

Новое окно ожидания после `deadline_at` не вводится: наступление срока
и зафиксированное завершение задания — разные события, и действует
правило конкуренции §1. Если backend уже зафиксировал завершение,
кандидат клиентский итог не меняет. Если проверка кандидата завершилась
и транзакция принятия зафиксировалась первой, результат принят. Если
хранилище недоступно, а срок истёк, новых повторов проверки нет: backend
фиксирует завершение по общему сроку. Обращение к хранилищу выполняется
вне транзакции и не удерживает блокировок, мешающих обработчику срока;
транзакция фиксации повторно проверяет состояние задания. Транзакции
ветки подчиняются общему правилу транзакций по Result и перепроверке
пометки удаления, как шаг 4 и `result_file_missing`. Для удалённого эскиза версия не создаётся:
проверенный кандидат даёт списание попытки; если объекта уже нет
и доказательства успешной записи нет, резерв возвращается, расход несёт
студия. Обычный Result `succeeded` с подтверждённой записью сохраняет
прежнее правило списания после удаления (§5). Уже завершённое задание
сохраняет свой клиентский итог при любом позднем сообщении.

**Общее правило транзакций по Result** (выведено мной как следствие
замечаний владельца 2026-09-11; три ветви и перепроверка пометки
удаления в ветке `result_file_missing` заданы владельцем 2026-09-11).
Проверка на шаге 1 идёт вне транзакции, а один Result может быть
доставлен дважды и обрабатываться параллельно, поэтому каждая транзакция,
применяющая Result, — шаг 4, короткий путь для `failed`, `cancelled`
и `awaiting_reconciliation`, переход в `failed` с `result_file_missing`
или `result_file_mismatch` —
внутри себя перечитывает последнюю применённую ревизию и состояние
задания и идёт по одной из трёх ветвей:

- ревизия не больше последней применённой — никаких изменений, сообщение
  подтверждается; устаревший снимок не перезаписывает более новый учёт;
- ревизия новее, задание завершено — обновить снимок учёта и ревизию,
  клиентский итог (состояние, версию, расчёт попытки) не трогать;
- ревизия новее, задание не завершено — применить Result по правилам
  состояния и удаления.

В третьей ветви транзакции, исход которых зависит от объекта, — шаг 4,
`result_file_missing` и `result_file_mismatch` — перепроверяют пометку удаления эскиза под
блокировкой записи эскиза; при пометке действует правило удалённого
эскиза. Без первой ветви задержавшийся обработчик ревизии 7 перезаписал
бы учёт ревизии 8; без второй вторая доставка одного `failed` вернула
бы резерв дважды, а второй обработчик успешного Result, придя на шаг 2
после шага 6 первого, завершил бы `succeeded`-задание как
`result_file_missing`; без перепроверки пометки обработчик, заставший
удаление между чтением эскиза и проверкой файла, вернул бы резерв там,
где правило удалённого эскиза требует списать попытку.

**Очистка объектов без принятой версии.** Копия в клиентской области
могла остаться без версии: задание завершилось или эскиз был удалён, пока
шёл `COPY`, либо обработчик упал между копированием и транзакцией. Правило
жизненного цикла `transfer/` таких объектов не касается. Один и тот же
Result может обрабатываться параллельно: очередь доставляет минимум один
раз, и повторная доставка возможна, пока первый обработчик ещё копирует.
Поэтому «моя транзакция не создала версию» — не основание удалять объект:
оба обработчика прошли бы проверку и `COPY`, первый создал бы версию,
а второй, увидев завершённое задание, удалил бы общий объект уже принятой
версии. Основание одно — на этот ключ нет принятой ссылки, и хранит его
запись «Файл», одна на ключ, с защитой от конкурентного принятия
(условие задано владельцем 2026-09-11; механика через запись «Файл»
выведена мной, владельцем не подтверждена):

- удалить копию, созданную приёмом результата, можно только через условный
  переход записи «Файл» из «ожидает» в «очищен» с отметкой времени либо
  когда запись уже в «очищен»; запись в «принят» удалять запрещает,
  и из «принят» она не возвращается — удаление принятых объектов
  при удалении эскиза идёт по порядку ADR-0010 и этим правилом
  не ограничено. Транзакция принятия переводит запись в «принят» тем
  же условным переходом из «ожидает», поэтому принятие и очистка одного
  ключа упорядочиваются на записи: кто зафиксировался первым, тот либо
  принял копию, либо освободил её для удаления;
- обработчик, чья транзакция не создала версию, сразу выполняет переход
  в «очищен» и при успехе или при уже стоящем «очищен» удаляет объект;
- обход по очистке берёт записи «Файл» в «ожидает», у которых задание
  в терминальном состоянии, выполняет тот же переход и удаляет объект;
  запись снимается вторым проходом после льготного срока, большего любого
  возможного времени `COPY`, и если объект появился заново от запоздавшего
  копирования, второй проход удаляет и его; сам запоздавший обработчик
  найдёт запись в «очищен» и тоже удалит объект, повтор безвреден;
- незавершённые задания обход не трогает, а каждое задание терминально
  хотя бы по общему сроку.

**Предпросмотр отдельно.** Версия существует с шага 4 в состоянии
«готовится». Водяной знак делает фоновая задача backend из оригинала
в клиентской области; сбой даёт состояние «ошибка» и повтор из того же
оригинала по ADR-0003. Списание на готовность предпросмотра не смотрит.

**Поздний Result** — Result по заданию, которое backend уже завершил
сам: `failed` с `dispatch_deadline_exceeded`, `execution_deadline_exceeded`,
`result_file_missing` или `result_file_mismatch`. Расчёт попытки по такому заданию уже сделан
и не меняется: backend идемпотентно сохраняет вызовы и расход, удаляет
объект в `transfer/output/`, версию не создаёт, попытку не списывает
и не возвращает повторно, эскиз и предыдущие версии не трогает.

Удалённый эскиз — не основание считать Result поздним. Пометка эскиза
удалённым задание не завершает, и пока задание не терминально, Result
применяется по обычным правилам расчёта: `succeeded` — задание
в `succeeded`, попытка списана; `failed` и `cancelled` — резерв
возвращён; `awaiting_reconciliation` — резерв держится. Отличие только
в том, что версия не создаётся, а объект в `transfer/output/` удаляется
(раздел 5). Пометку backend читает на шаге 1 и для удалённого эскиза
пропускает шаги 2–3: объект не проверяет и не копирует, состояние
и расчёт берёт из Result как есть, объект удаляет, если он ещё есть,
и `result_file_missing` или `result_file_mismatch` не ставит — объект мог удалить он сам на шаге
очистки передаточной области, а по ADR-0010 оригинал считается
созданным, когда его сохранил генератор, и позднее удаление backend
исхода не меняет (выведено мной, владельцем не задано). Если эскиз
удалён, а задание к приходу Result уже завершено backend по сроку,
действует правило позднего Result: расчёт не меняется.

## 5. Удаление во время работы

Один доменный запрос `EraseGeneration` с двумя обязательными эффектами:
стереть клиентское содержание и поставить барьер на новые платные действия.
Отдельной команды отмены нет: пользователь совершил одно действие — удалил
эскиз, а сценария «остановить генерацию, но сохранить эскиз и prompt»
в ADR нет. Запись `EraseGeneration` в outbox входит в первую транзакцию
порядка удаления ADR-0010 — вместе с пометкой эскиза, снятием
неотправленного `SubmitJob` и затиранием клиентского текста в backend;
физическая очистка объектов идёт после фиксации. Это даёт две гарантии
и не даёт третьей. Намерение отправить команду не теряется: падение
backend после фиксации команду не стирает. На стороне backend нет окна
между пометкой и командой: они фиксируются вместе. Но запись в outbox —
ещё не барьер у генератора. Барьер действует с момента, когда генератор
применил команду в своей базе; пока команда идёт через outbox и очередь,
генератор может зафиксировать новый `ProviderCall`. Такой вызов считается
начавшимся до удаления и доводится до известного исхода, а финансовый
итог по нему — по правилу ADR-0010: создан оригинал — попытка списана,
нет — резерв возвращён. Ранняя доставка безопасна: `EraseGeneration`,
пришедший раньше `SubmitJob`, даёт tombstone.

**Граница отмены** — зафиксированное намерение вызова, а не сетевой
запрос. Создание `ProviderCall` в `pending` и проверка барьера конкурируют
по одной записи Job: если вызов уже зафиксирован, он считается начавшимся
до удаления и доводится до известного исхода; если нет, барьер стоит,
и новый вызов появиться не может. Это выполняет требование ADR-0006
не повторять платную операцию при неизвестном исходе.

| Состояние Job | Действие генератора |
| --- | --- |
| Записи нет | Tombstone: `cancelled`, `erase_requested_at`, `content_erased_at`. Поздний `SubmitJob` дописывает техническую информацию, но не восстанавливает prompt, не меняет `cancelled`, не запускает работу |
| `queued` | `cancelled` |
| `running`, вызов не начат | `cancelled` |
| `running`, вызов начат | Дождаться исхода или сверка → `succeeded` либо `failed` |
| `awaiting_reconciliation` | Сверка до конца, новых вызовов нет → `succeeded` либо `failed` |
| Завершено | Состояние не менять, только стирание; если уже стёрто — переотправить текущий Result |

Во всех случаях клиентский текст затирается физически в Job, `ProviderCall`
и Result, локальные рабочие файлы задания удаляет их владелец после
последнего необходимого использования — файл результата начатого вызова
остаётся до `result_stored_at` или окончательного прекращения передачи
(ADR-0014 §3, «Локальные рабочие файлы»), признак стирания сохраняется, технический учёт остаётся, повтор
команды в записях ничего не меняет. Генератор подтверждает факт стирания
полем `content_erased_at` в повторном Result с новой ревизией; для tombstone
это Result `cancelled` с тем же полем. Backend фиксирует время подтверждения
на задании: «команда поставлена в очередь» и «генератор подтвердил
стирание» — разные факты.

**Повтор команды до подтверждения** (решение владельца 2026-09-11).
Подтверждение стирания может не дойти: Result с `content_erased_at` или сам
`EraseGeneration` теряются из очереди по истечении срока хранения при
недоступности другой стороны. Поэтому, пока на задании нет времени
подтверждения стирания, backend повторяет `EraseGeneration` по тому же
`job_id` с нарастающей паузой; период — параметр. Генератор на повторную
команду по заданию, где стирание уже выполнено, записи не меняет,
но переотправляет текущий Result — так же, как на повторный `SubmitJob`
по завершённому заданию в таблице раздела 2. Для tombstone это тот же
Result `cancelled` с `content_erased_at`. Повтор прекращается только
по подтверждению; верхней границы у него нет, потому что подтверждение
всегда достижимо: у генератора либо есть Job, либо команда создаёт
tombstone. Так обе потери, связанные со стиранием, из перечня требования
к очереди закрываются, и остаточной потерей остаётся только копия учёта
в backend.

**Копии текста вне основных записей.** Неопубликованные outbox-payload
с клиентским текстом затираются в той же транзакции стирания, у генератора
и у backend. Backend в транзакции удаления снимает собственную
неотправленную запись `SubmitJob`; команду стирания шлёт всё равно,
поскольку сообщение могло уйти без подтверждения. Сообщения уже в брокере
отредактировать нельзя: для них короткий срок хранения и обязательное
поглощение по tombstone или удалённому эскизу без сохранения текста —
`SubmitJob` с prompt у генератора, Result с `assembled_request` у backend.
«Короткий» здесь ограничен снизу требованием к очереди из раздела
«Параметры и требования»: срок хранения не короче горизонта `deadline_at`
с окном сверки, запасом и допустимой недоступностью другой стороны. Карантин
сообщений неизвестной версии индексируется по `job_id` и очищается
по той же команде на обеих сторонах.

`succeeded` после удаления означает только «генерация технически
состоялась»: backend не создаёт версию, удаляет объект результата
в `transfer/output/` и, если копия в клиентской области успела появиться,
её — по правилу очистки раздела 4, — и списывает попытку, потому что
оригинал создан. `failed` и `cancelled`
без оригинала возвращают резерв; `awaiting_reconciliation` держит резерв
как обычно. Исходник в `transfer/input/` backend удаляет на шаге очистки
передаточной области после транзакции удаления; если генератор не смог
его прочитать, задание завершается `cancelled` с `source_missing`,
платных вызовов не было. Отсутствующий исходник у неудалённого эскиза —
`failed` с `source_missing` (решение владельца 2026-09-14, S-5). Генератор
различает случаи по `erase_requested_at` под блокировкой Job: признак
стоит — `cancelled`, нет — `failed`. `content_erased_at` для этого
не используется: он может появиться из-за срока хранения текста и отмены
не означает. Переход в `cancelled` сохраняет условие отмены до начала
платного вызова (решение владельца 2026-09-14).

## 6. Сообщения

**Конверт.** У каждого сообщения есть неизменяемый конверт из трёх полей:
`message_type` (`SubmitJob`, `EraseGeneration`, `Result`),
`contract_version`, `job_id`; у `Result` в конверт входит ещё `revision`.
Конверт лежит вне версионируемого тела и разбирается до проверки версии:
его состав и разбор не меняются ни в одной версии контракта. Остальные
поля — тело сообщения, его состав задаёт `contract_version`.

| Сообщение | Направление | Ключ идемпотентности | Тело |
| --- | --- | --- | --- |
| `SubmitJob` | backend → генератор | `(message_type, job_id)` | `prompt`, `negative_prompt`, `style`, `parameters` — снимок на момент принятия: `studio_rules` (`text`, `version`), настройки модели, `placement` (код справочника, необязателен), `size` (значение и единица измерения, необязателен; желаемый физический размер, не разрешение); `source` при любом исходнике — доработка от версии, новый эскиз от версии или от загрузки (§1 «Исходник», уточнение 2026-09-11: раньше стояло «при доработке» и противоречило §1): `key`, `size`, `media_type`, `sha256`; `deadline_at`, `created_at` |
| `EraseGeneration` | backend → генератор | `(message_type, job_id)` | `requested_at` |
| `Result` | генератор → backend | `(job_id, revision)` | `state` (`awaiting_reconciliation`, `succeeded`, `failed`, `cancelled`), `reason_code`, `result` при успехе: `key`, `size`, `media_type`, `sha256`; `result_candidate` при `result_payload_unavailable` и `result_delivery_deadline_exceeded`, если дескриптор был зафиксирован: `key`, `call_id`, `sha256`, `size`, `media_type` (§2, §4); `provider_calls[]`, `stages[]`, `content_erased_at` |

**Время** (решение владельца 2026-09-14, S-7). Временные метки сообщений —
строки RFC 3339 с обязательным часовым смещением
([§5.6](https://www.rfc-editor.org/rfc/rfc3339.html#section-5.6));
отправители формируют UTC с `Z`, например `2026-09-14T12:30:00.123Z`.
Числа, числовые строки и даты без смещения получатель отклоняет. Правило
общее для Python и TypeScript. Обработка некорректного сообщения известной
версии открыта (документ стека, §7).

**Дескриптор файла** (решение владельца 2026-09-14, S-6). `media_type` —
канонический тип, установленный декодированием содержимого, например
`image/png`; расширение файла и заголовок провайдера формат не
подтверждают. `size` — число передаваемых байтов, `sha256` считается по
ним. При записи объекта `ContentType` равен `media_type` дескриптора.
Backend проверяет формат по тем же правилам; обе реализации проверяются
общим набором файлов с ожидаемыми результатами.

`mode` в `SubmitJob` нет (решение владельца 2026-09-11, B-28): генератор
выбирает обработку по наличию `source` — текстовая генерация или работа
с исходным изображением; новый эскиз или доработка — семантика backend,
и признак дублировал бы данные, допуская противоречивые сочетания.
Снимок `parameters` генератор использует как есть: повтор и восстановление
обновлённые правила студии не подхватывают; отсутствующие `placement`
и `size` догадкой не заменяются.

Ключ идемпотентности команд включает `message_type`: обе команды идут
одной очередью, и общий inbox иначе принял бы `EraseGeneration(42)`
за повтор `SubmitJob(42)`. Дескриптор `source` позволяет генератору
проверить, что прочитан именно тот объект, который передал backend.

**Result — полный снимок** состояния задания у генератора, а не набор
изменений. `revision` увеличивается при публикации нового снимка по
событиям ADR-0013 §7: переход Job в публикуемое состояние, установка
`content_erased_at`, поздние сведения провайдера об исходе или расходе.
Захват, продление аренды, промежуточные этапы, запись дескриптора
и `result_stored_at` сами по себе публикацию не вызывают; их результат
входит в следующий снимок. Стирание в `queued`/`running` входит в первый
последующий допустимый Result (решение владельца 2026-09-14, S-11).
Каждый Result несёт актуальный полный массив `provider_calls[]`.
Backend применяет только Result с ревизией больше текущей и синхронизирует
весь снимок по `call_id`. Отдельной ревизии у `ProviderCall` нет: при
стирании поле `assembled_request` пустеет, а ревизия вызова не изменилась
бы, и backend мог бы сохранить старый текст.

**Элемент `provider_calls[]`:** `call_id` (обязателен), провайдер, модель,
номер попытки, `external_request_id` (`null`, если неизвестен: провайдер
мог принять запрос, а идентификатор был в ответе, который генератор
не получил, — такой вызов всё равно входит в Result как `outcome_unknown`;
идентификатор, известный до отправки, — гарантия конкретного маршрута,
а не требование к каждому `ProviderCall`), состояние,
начало, завершение, ошибка, `assembled_request` (пусто после стирания),
расход: `units`, `amount` (`null` при неизвестной), `currency`, `cost_kind`
(`actual`, `estimated`, `unknown`), `tariff_version` при `estimated`;
метаданные по списку разрешённых полей. Расчётную стоимость считает
генератор — адаптер провайдера или роутер — по своему прайс-листу
(решение владельца 2026-09-11, B-62); источник цен и порядок обновления —
исследование роутера; нет применимого тарифа — `unknown`, не ноль.

**Ошибка провайдера** хранится только как `provider_error_code`, HTTP
status и ограниченный очищенный `error_message`. Сырое тело ошибки
в `ProviderCall` не попадает: провайдер может вернуть в нём часть запроса,
как и в метаданных.

**`stages[]`:** `stage` из закрытого перечня, `sequence`, `started_at`,
`finished_at`. Перечень: `prepare` (подготовка запроса текстовой моделью),
`generate` (вызов графической модели), `download`, `verify`, `store`
(запись в `transfer/output/`), `reconcile`. Этап, выполнявшийся
повторно, даёт несколько записей с одним `stage` и разными `sequence`.
Постановка самого Result в outbox и его доставка этапом не считаются:
их время не может попасть в снимок, который они публикуют, без новой
ревизии, и так без конца. Время работы outbox — транспортная
диагностика; оно хранится на outbox-записи генератора и в метриках,
а не в Result.

**`reason_code`** — закрытый перечень причин генератора: `provider_error`,
`provider_outcome_unresolved`, `source_missing` (`cancelled` при барьере
стирания, `failed` без него — §5), `deadline_exceeded`
(срок истёк до начала вызова), `result_payload_unavailable` (успешный
исход вызова сохранён, невосстановимость доказана по контракту маршрута,
подтверждённой записи нет — §2), `result_delivery_deadline_exceeded`
(передачу результата известного успешного вызова не удалось завершить
за отведённое время — §2), `erased`. Отображение причин на клиентскую
`failure.reason` — ADR-0012 §6. Не все они ошибки, поэтому поле
не называется `failure_reason`. Коды backend перечислены в разделе
«Состояния».

**Версия контракта.** Одно целое `contract_version` в конверте каждого
сообщения; добавление необязательных полей в тело версию не меняет.
Сообщение с неизвестной версией не отбрасывается и не выполняется,
а откладывается в карантин с уведомлением администратора: молчаливый
пропуск потерял бы задание вместе с резервом. Конверт читается и при
неизвестной версии, поэтому карантин знает `message_type` и `job_id`
каждого сообщения: по ним оно классифицируется, индексируется
и стирается по `EraseGeneration`. Карантин подчиняется правилу удаления
из раздела 5.

**Ключи объектов.** Передаточная область по ADR-0010. Клиентская область
без владельца в ключе: владелец эскиза меняется при присоединении гостя,
а доступ и так проверяет backend, владение живёт только в базе.

    client/sketches/<sketch_id>/<job_id>/original
    client/sketches/<sketch_id>/<job_id>/preview
    client/uploads/<upload_id>/original

## Отвергнутые варианты

| Вариант | Почему отвергнут |
| --- | --- |
| Отправка в очередь внутри запроса клиента | При сбое фиксации после успешной отправки у генератора остаётся задание, которого нет в backend, а распознать его генератор может только обратным запросом, которого по ADR-0010 нет |
| Сообщение удерживается в очереди невидимым до конца выполнения | Привязывает надёжность к технологии очереди; после подтверждения работу держит база генератора и его процесс восстановления |
| Отдельная команда `CancelJob` | Две команды с порядком, который пришлось бы согласовывать, хотя пользователь совершил одно действие; понадобится, только если появится сценарий «остановить, но сохранить эскиз» |
| Подтверждение от backend генератору о принятом результате | У генератора нет действия, ждущего принятия: файл удаляет backend, текст стирается по сроку или команде. Владелец снял собственное предложение. Понадобилось бы, если бы генератор хранил восстанавливаемую копию до принятия. Потеря Result из очереди ограничена не подтверждением, а требованием к сроку хранения; остаточные потери перечислены там же (раздел «Параметры и требования») |
| Промежуточное сообщение о состоянии `awaiting_reconciliation` | В решении 3 отложено; при Result как полном снимке заменено значением `state`, без отдельного типа сообщения |
| Ревизия на каждом `ProviderCall` | При стирании ревизия вызова не менялась бы, и backend мог бы сохранить старый `assembled_request` |
| Владелец в ключе объекта | Владелец эскиза меняется при присоединении гостя; объекты пришлось бы перемещать |

## Следствия для ADR-0010

Контракт добавляет поля, которых в ADR-0010 не было; по согласию владельца
2026-09-10 они внесены туда уточнением по правилу README:

- Задание генерации: ключ идемпотентности, `deadline_at`, последняя
  применённая ревизия Result, время подтверждения стирания, причина
  завершения с кодами backend; состояния по разделу «Состояния».
- Job: этап, аренда, `deadline_at`, подготовленный запрос, дескриптор
  результата и `result_stored_at` (уточнение 2026-09-14), признаки
  стирания; tombstone как допустимая форма записи.
- `ProviderCall`: без собственной ревизии; ошибка провайдера только кодом,
  HTTP status и очищенным сообщением.
- Result: снимок состояния, а не только итог; вызовы данными, не ссылками;
  ревизия.
- «Файл»: состояния «ожидает», «принят», «очищен»; запись одна на ключ,
  «принят» защищает принятую копию от очистки параллельным обработчиком
  (уточнение 2026-09-11).
- Расход провайдера: валюта.
- Порядок удаления: первая транзакция объединяет пометку эскиза, снятие
  неотправленного `SubmitJob`, запись `EraseGeneration` в outbox
  и затирание клиентского текста; физическая очистка объектов — после
  неё; ключи гостевой сессии переходят пользователю при присоединении
  (ADR-0002).

## Параметры и требования, которые контракт не фиксирует

- Значения сроков: отправки, `deadline_at` и его состав, аренды, окна сверки
  на маршрут, льготного срока очистки «Файл», хранения сообщений в брокере,
  периода повтора `EraseGeneration` до подтверждения стирания.
- Число платных вызовов на задание и какие ошибки провайдера допускают
  повтор — контракт маршрута в исследовании роутера, вместе со способом
  сверки, смыслом ответов провайдера и тем, известен ли
  `external_request_id` до отправки запроса.
- Очереди — Yandex Message Queue (решение владельца 2026-09-13),
  карантин — таблица в базе получателя (выведено мной из §5–6; ADR-0014
  «Свойства»); настройка очередей
  и способ уведомления администратора — уровень исполнения
  и инфраструктуры.
- **Требование к очереди, а не параметр.** Outbox-запись удаляется после
  подтверждения брокера, а подтверждения принятия от backend нет, поэтому
  после сдачи в очередь повторить Result некому. Обещание протокола одно:
  брокер хранит сообщение до потребления либо до истечения срока
  хранения, и срок не короче горизонта `deadline_at` плюс окно сверки,
  запас и допустимая длительность недоступности потребителя. Потеря
  внутри срока — нарушение требования; потеря по истечении срока
  допускается, и её цена ограничена перечнем ниже. Если backend был
  недоступен дольше срока, к моменту восстановления задание ещё
  не завершено: транзакция по общему сроку выполняется после
  восстановления и тогда возвращает резерв — клиентский итог тот же,
  только позже. Потерянный Result по такому заданию был бы поздним,
  поэтому версия и списание не затрагиваются. Что теряется
  (перечень выведен мной по замечанию владельца 2026-09-11):
  - копия `ProviderCall` и расхода в backend — база генератора их хранит;
  - подтверждение стирания `content_erased_at` в повторном Result —
    закрыто повтором команды до подтверждения (раздел 5): backend шлёт
    `EraseGeneration` снова, генератор переотправляет текущий Result;
  - `EraseGeneration`, потерянный при недоступности генератора дольше
    срока, — закрыто тем же повтором; до его доставки барьер и стирание
    по команде не наступают, действует стирание по сроку хранения
    текста, а платный вызов после `deadline_at` генератор не начнёт
    и без барьера.
  `SubmitJob`, потерянный так же, безвреден: задание падает по сроку
  без платного вызова. Требование проверяется до выпуска для выбранной
  очереди — Yandex Message Queue, срок хранения сообщений не более 14 дней
  (ADR-0014 «Свойства»).
- API backend для frontend: как клиент передаёт ключ идемпотентности
  и узнаёт состояние задания; cookie и CORS по ADR-0009; открытие версии —
  решено в [ADR-0012](0012-frontend-api-contract.md), принят 2026-09-11.

## Источники

- Решения владельца в обсуждении 2026-09-10, шесть решений по порядку:
  outbox и ответ после `accepted`, `dispatched` как диагностика, просрочка
  как «доставка не подтверждена», ключ идемпотентности с областью
  и проверкой содержимого; источник истины в базе генератора,
  подтверждение после фиксации Job, восстановление отдельным процессом;
  сверка у генератора, `deadline_at` в Job, повтор только после
  достоверного исхода, стоимость отдельно от исхода, без промежуточного
  сообщения; отказ от подтверждения генератору, ревизии, неизменный объект
  результата, перепроверка состояния в транзакции, восстанавливаемая
  очистка; один запрос `EraseGeneration` с двумя эффектами, граница
  по намерению вызова, tombstone, подтверждение стирания, копии текста
  в outbox, брокере и карантине; Result как полный снимок с одной ревизией,
  ключи с типом сообщения, `external_request_id`, `currency`, `reason_code`
  только генератора, `awaiting_reconciliation` в `state`, строгий формат
  `stages[]`, очищенная ошибка провайдера, ключи без владельца, дескриптор
  `source`.
- Выведено мной и владельцем не оспорено: намерение вызова как создание
  `ProviderCall` в `pending` без нового состояния; любой Result снимает
  запись на отправку; код `execution_deadline_exceeded`; последняя
  применённая ревизия на задании; карантин Result у backend под тем же
  правилом удаления; перечень этапов `stages[]`; запись «Файл»
  с состояниями и двухпроходный обход; подтверждение стирания через
  повторный Result, а не служебное сообщение; снятие неотправленного
  `SubmitJob` при удалении; повторяемость шагов физической очистки после
  транзакции удаления (ADR-0010, уточнение 2026-09-10); для удалённого
  эскиза backend пропускает проверку и копирование объекта и не ставит
  `result_file_missing`, потому что мог удалить объект сам.
- Замечания владельца 2026-09-10 после принятия, четыре пункта:
  удалённый эскиз исключён из оснований позднего Result — расчёт попытки
  по нему идёт по состоянию Result (`succeeded` списывает, `failed`
  и `cancelled` возвращают), а поздним считается только Result по
  заданию, которое backend завершил сам; запись `EraseGeneration`
  в outbox перенесена из шестого шага порядка удаления в первую
  транзакцию, физическая очистка — после неё; введён неизменяемый
  конверт `message_type`, `contract_version`, `job_id` (у `Result` ещё
  `revision`), читаемый до проверки версии; `publish` убран из `stages[]`
  как самореференция снимка.
- Решение владельца 2026-09-11 по пятому замечанию (потеря Result
  из очереди при недоступности backend дольше срока хранения): записать
  требование к очереди — хранение до потребления, срок не короче
  горизонта `deadline_at` с окном сверки и запасом, — а не допустимую
  деградацию. Формулировка требования и вывод о единственной остаточной
  потере (копия учёта в backend) — мои, приняты владельцем в том же
  обсуждении.
- Замечания владельца 2026-09-11 к ADR-0010 и ADR-0011, пять пунктов:
  условие удаления скопированного объекта — отсутствие принятой ссылки
  на ключ с защитой от конкурентного принятия, а не «моя транзакция
  не создала версию»; повторная проверка пометки удаления и ревизии
  Result внутри транзакции принятия, согласованная с транзакцией
  удаления; запись команды в outbox — не барьер, барьер действует после
  применения команды генератором; одно точное обещание о хранении
  сообщений и полный перечень потерь, включая подтверждение стирания,
  с поправкой, что при недоступном backend транзакция по сроку
  выполняется после восстановления; `external_request_id` допускает
  `null`, `call_id` обязателен. Выведено мной и владельцем ещё
  не подтверждено: механика защиты через условные переходы записи
  «Файл» (одна на ключ); блокировка записи эскиза как точка упорядочения
  принятия и удаления; общее правило перепроверки ревизии и терминальности
  во всех транзакциях по Result, включая `result_file_missing`; пропуск
  шагов 2–3 для задания, завершённого до прихода Result; состав перечня
  потерь, включая потерю `EraseGeneration`.
- Решение владельца 2026-09-11 по моему вопросу к перечню потерь:
  записать правилом повтор `EraseGeneration` до подтверждения стирания
  с переотправкой текущего Result генератором, а не оставлять потерю
  подтверждения и потерю команды принятыми остаточными. Механизм
  предложен мной, принят владельцем.
- Решение владельца 2026-09-11 к ADR-0012, внесено сюда по его указанию:
  запись «Эскиз» в транзакции `accepted` первого задания; проверка
  источника под блокировкой записи его владельца внутри транзакции,
  согласованная с удалением. Выведено мной: копирование исходника
  в `transfer/input/<job_id>/source` до транзакции по образцу раздела 4,
  распространение правила на источник-версию через блокировку записи
  эскиза, удаление `transfer/input/` на шаге 6. Замечание владельца
  2026-09-11 к `94c6771`: независимость задания от удаления источника
  относится к отдельной загрузке и другому эскизу; удаление собственного
  эскиза задания всегда по разделу 5.
- Проход 2 по свип-ревью 2026-09-11: в таблице сообщений `source`
  «при доработке» заменено на «при любом исходнике» — снятие противоречия
  с §1 «Исходник» в пользу более позднего текста по решению владельца.
- Решения владельца 2026-09-11 по открытым пунктам прохода 2: `mode` убран
  из `SubmitJob` (B-28); `parameters` несёт снимок правил студии текстом
  с меткой версии (B-15/16), место нанесения и размер структурированно
  (A-24); `tariff_version` в `provider_calls[]`, прайс-лист у генератора
  (B-62); гарантия резерва в §1 (B-31).
- Замечания владельца 2026-09-11 к коммиту `d3feecb`, два пункта: общее
  правило транзакций по Result разбито на три явные ветви — устаревшая
  ревизия ничего не меняет, а не «сохраняет учёт»; ветка
  `result_file_missing` перепроверяет пометку удаления под блокировкой
  записи эскиза, как шаг 4, и при пометке применяет правило удалённого
  эскиза.
- Решение владельца 2026-09-13
  ([принятый стек](../research/rated-accepted-stack.md) §2, §6): очереди —
  Yandex Message Queue; в «Параметрах и требованиях» названа выбранная
  очередь и граница срока хранения 14 дней. Карантин как таблица в базе
  получателя — следствие §5–6, записанное в ADR-0014 (выведено мной).
- Решения владельца 2026-09-14 при выборе клиента Object Storage
  генератора: §2 — повторяемость этапов условна, пока доступен результат
  предыдущего этапа; `result_payload_unavailable` для невосстановимой
  потери байтов при сохранённом успешном исходе (вариант «принять потерю»,
  надёжное промежуточное хранение ответа в первом выпуске отклонено);
  дескриптор результата в Job до первой записи и запрет несовпадающих
  байтов в том же ключе, исходные байты без перекодирования; §4 —
  `result_file_mismatch` у backend с теми же транзакционными правилами,
  что `result_file_missing`; §5 — удаление локальных рабочих файлов при
  стирании. Формулировки владельца; размещение по разделам — моё.
- Свип-ревью 2026-09-14 (`docs/reviews/2026-09-14-stack-sweep.md`), правки
  без новых решений по поручению владельца «закрывай правками»: порядок
  после платного вызова и подтверждение записи `result_stored_at` (F-3,
  F-4); дескриптор записывается один раз, потерявший аренду исполнитель
  новую запись не начинает (F-1); несовпадение повторно полученных байтов

  заменено уточнением владельца 2026-09-14 ниже);
  несовпадение файла в перечнях завершений backend (F-8); `ProviderCall` —
  попытка платного вызова (F-12); карантин-таблица помечена выводом, а не
  решением владельца (F-14).
- Решения владельца 2026-09-14 по развилкам свип-ревью: S-1 — кандидат
  результата в Result с `result_payload_unavailable` и проверка его
  backend как исключение из короткого пути, с правилами для удалённого
  эскиза и завершённого задания; S-2 — локальный файл результата начатого
  вызова живёт до `result_stored_at`; S-5 — `source_missing` у
  неудалённого эскиза даёт `failed`, отображение причин в ADR-0012; S-6 —
  тип по декодированному содержимому, `ContentType` из дескриптора; S-7 —
  RFC 3339 со смещением, отправители в UTC с `Z`; S-8 — основания
  невосстановимости по контракту маршрута и
  `result_delivery_deadline_exceeded`; S-10 — очистка `transfer/output/`
  после отказа; S-11 — `revision` при публикации снимка, канонический хеш
  в §1. Абзац порядка назван по вызову графической модели (замечание
  владельца к `6765268`).
- Уточнения владельца 2026-09-14 к решениям S-1 и S-8: несовпадение
  повторно полученных байтов с дескриптором — неудачная попытка получения
  с повтором до `deadline_at`, а не основание невосстановимости (заменяет
  правку F-2 свип-ревью); кандидат результата передаётся и проверяется
  при обоих кодах, `result_payload_unavailable` и
  `result_delivery_deadline_exceeded`; без кандидата или объекта
  сохраняется исходная причина генератора; новое окно после `deadline_at`
  не вводится, конкуренция с завершением по сроку — по правилу §1;
  `source_missing` различается по `erase_requested_at` под блокировкой
  Job, не по `content_erased_at`.
