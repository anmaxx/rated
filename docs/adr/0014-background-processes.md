## Контекст

Шаг 2 уровня 4 по порядку владельца (ADR-0013 «Контекст»): исполнители,
отправители outbox, обработчики результатов, восстановление, предпросмотры
и очистка. Требуемый результат — для каждой сохранённой работы определены
исполнитель и способ восстановления после его падения.

Что уже задано и здесь не переопределяется: захват длинных работ условным
обновлением с поколением аренды и записи исполнителя с проверкой поколения
(ADR-0013 §7); публикация Result только по событиям (ADR-0013 §7); две
семантики outbox (ADR-0013 §6); транзакции по срокам берут только строку
задания (ADR-0013 §5); подтверждение входящих сообщений после фиксации
(ADR-0011 §2, §4); два решения, которые ADR-0010 «Файлы» отдал уровню
исполнения — способ удаления объектов задания и способ обхода шагов 2–4
после сбоя.

## Решение в одном абзаце

Каждая сохранённая работа — строка в базе своей стороны с одинаковым
набором служебных колонок; ни один процесс не держит незавершённую работу
в памяти. Короткие работы забираются `FOR UPDATE SKIP LOCKED` с короткой
арендой, длинные — захватом с поколением аренды из ADR-0013 §7; это один
механизм, а не два. Повтор — по `next_attempt_at` с нарастающей паузой
и счётчиком попыток; исчерпание фиксируется на строке признаком, а не
потерей работы. Каждый цикл безопасен в N экземплярах, ни один не требует
единственности. Потребители брокера описаны свойствами из ADR-0011;
технология брокера — уровень 5 (решение владельца 2026-09-11).

## 1. Общий механизм записи-работы

Выведено мной; в ревью владельца не оспорено, отдельно не подтверждено.

- Служебные колонки на строке работы: `claimed_by`, `lease_generation`,
  `lease_until`, `attempts`, `next_attempt_at`, `done_at`, `exhausted_at`,
  `last_error`. Отдельной общей таблицы задач нет: колонки живут на той
  записи, которая и есть работа (версия, эскиз, загрузка, задание
  доставки, outbox).
- Захват — условное обновление `WHERE done_at IS NULL AND exhausted_at
  IS NULL AND <состояние работы допускает выполнение> AND (lease_until
  IS NULL OR lease_until < now()) AND next_attempt_at <= now()`
  с `lease_generation = lease_generation + 1`, как в ADR-0013 §7.
  Допустимое состояние у каждой работы своё и входит в тот же условный
  захват: версия в `preparing` **у эскиза без `deleted_at`** (чтение
  в том же условном обновлении, без блокировки эскиза — новых записей
  под удалённый префикс не начинать), эскиз с `deleted_at` без
  `cleanup_done_at`, outbox-строка без подтверждения, Job в `queued`
  или `running` с истёкшей арендой. Одних аренды и `next_attempt_at`
  недостаточно: после истечения аренды завершённая или исчерпанная
  работа снова подошла бы под условие (замечание владельца 2026-09-11).
  Выборка кандидатов — `FOR UPDATE SKIP LOCKED`. Периодические проходы
  без захвата (обход удалённых префиксов, просроченные сеансы) через
  этот механизм не идут: у них нет завершения, а `done_at IS NULL`
  исключил бы эскиз с выполненными шагами 2–4 навсегда; их безопасность
  в N экземплярах — идемпотентность удаления (выведено мной). Каждая последующая запись исполнителя —
  с `WHERE lease_generation = :mine`; ноль строк означает потерю аренды,
  исполнитель останавливается без фиксации.
- Работа с вызовом хранилища, брокера или внешнего сервиса не держит
  транзакцию открытой на время вызова: захват, вызов, фиксирующая
  транзакция. Повтор после падения посреди вызова у каждого внешнего
  эффекта обоснован отдельно — таблица ниже; общего обещания
  идемпотентности нет, для уведомлений допустим дубль (замечание
  владельца 2026-09-11).
- Неудача — `attempts + 1`, `next_attempt_at` с нарастающей паузой,
  `last_error`; исчерпание — `exhausted_at`. Исключение —
  `EraseGeneration`: `exhausted_at` не ставится, повтор продолжается
  до подтверждения стирания (ADR-0011 §5). Как об исчерпании узнаёт
  администратор — шаг 4. Численные значения пауз, попыток и интервалов
  обхода — шаг 4.
- Запуск — обход с интервалом, без сигналов между процессами. Обход
  выбирает строки по индексируемым колонкам (`state`, `next_attempt_at`,
  `deadline_at`, `deleted_at`), никогда по содержимому `jsonb`
  (ADR-0013 §2).

Основания безвредности повтора по видам внешнего эффекта:

| Внешний эффект | Основание повтора |
| --- | --- |
| `PUT` или `COPY` объекта | Ключ выводится из идентификаторов (`job_id`, версия), повторная запись даёт тот же объект |
| `DELETE` объекта, перечисление префикса | Отсутствие объекта — не ошибка; результат тот же |
| Публикация в брокер | Получатель различает по `(message_type, job_id)` и `(job_id, revision)` (ADR-0011 §1, §6); дубль сообщения безвреден |
| Платный вызов провайдера | Не идемпотентен. Повтор без достоверного исхода запрещён: `ProviderCall` в `pending` до вызова, восстановление через `awaiting_reconciliation` и сверку (ADR-0011 §2–3) |
| Письмо или уведомление | Не идемпотентно: сервис мог принять сообщение до падения исполнителя, аренда и условное обновление это не предотвращают. Дубль допустим — ADR-0003 не обещает строго однократной внешней доставки; разрыв после отправки фиксируется как неизвестный исход отдельно от успеха и ошибки, повтор после него — по политике ADR-0003, численно шаг 4 |
| Переход состояния в базе | Условное обновление; второй исполнитель обновляет ноль строк |

## 2. Backend: сохранённые работы

| Работа | Где хранится | Кто выполняет | Что запускает | После падения посреди работы | Защита от двух исполнителей |
| --- | --- | --- | --- | --- | --- |
| Отправка `SubmitJob` | Строка outbox | Отправитель outbox | Обход по `next_attempt_at` | Строка на месте, следующий обход; двойная отправка безвредна — генератор различает по `job_id` (ADR-0011 §1) | `SKIP LOCKED`, короткая аренда; удаление по ack брокера и в транзакциях завершения задания (ADR-0013 §6) |
| Отправка `EraseGeneration` | Строка outbox, живёт до `erase_confirmed_at` на задании | Тот же отправитель | Обход; переотправка с нарастающей паузой (ADR-0011 §5) | То же | То же; строка не удаляется по ack, только по подтверждению стирания; `exhausted_at` не ставится (раздел 1) |
| Приём Result | Сообщение в брокере до ack | Потребитель результатов | Доставка брокером | Ack не дан → повторная доставка; шаги до фиксации повторяемы (ADR-0011 §4) | Общее правило транзакций по Result и запись «Файл» (ADR-0013 §5) |
| Сроки отправки и исполнения | Колонки сроков на задании | Сторож сроков | Периодический обход нетерминальных заданий с истёкшим сроком | Следующий обход | Транзакция ADR-0013 §5 п. 4: задание `FOR UPDATE`, проверка нетерминальности |
| Подготовка предпросмотра | Строка версии: `preview_state`, номер серии, служебные колонки | Обработчик предпросмотров | Вставка в транзакции принятия результата (ADR-0011 §4 шаг 4) и `preview-retry` — новая серия (ADR-0012 §6) | Аренда истекает, обход подбирает; повтор из того же оригинала, ключ предпросмотра тот же | Аренда с поколением; запись «Файл» для ключа предпросмотра создаётся до `PUT` (ADR-0012 §6: `Content-Type` из неё); **порядок фиксации — решение владельца 2026-09-11**: (1) изображение готовится и `PUT` выполняется вне транзакции; (2) короткая транзакция берёт эскиз `FOR SHARE` → версию `FOR UPDATE` → запись «Файл» (порядок захвата ADR-0013); (3) проверяются пометка удаления, актуальность серии и поколение аренды; (4) при действительном результате атомарно: «Файл» → «принят», `preview_state = ready`, работа завершена (`done_at`); при пометке удаления готовность не фиксируется, объект остаётся под обходом удалённых префиксов (раздел 4), после фиксации обработчик его удаляет как страховку; захват новой серии у эскиза с пометкой невозможен (раздел 1). Блокировка эскиза даёт однозначный порядок с первой транзакцией удаления (эскиз `FOR UPDATE`): удаление зафиксировано первым — предпросмотр не принимается; предпросмотр первым — удаление охватывает принятый файл. Ключ `client/sketches/<sketch_id>/<job_id>/preview` (ADR-0010) один на версию, серии его делят: запись «Файл» одна, при ошибке серии остаётся в «ожидает», новая серия пишет тот же ключ. Обход очистки «Файл» записи предпросмотров не берёт — их состояние ведёт эта работа, объекты снимаются с эскизом по префиксу (раздел 4); терминальность задания генерации о подготовке предпросмотра не говорит ничего — генерация `succeeded` до её начала (замечание владельца 2026-09-11). Цена: принятие Result по параллельной доработке того же эскиза (эскиз `FOR UPDATE`, ADR-0013 §5) ждёт короткую фиксирующую транзакцию предпросмотра; `PUT` в неё не входит. Вариант без блокировки эскиза владелец отклонил в пользу согласованности «файл принят + предпросмотр готов» и порядка с удалением |
| Обход очистки «Файл» | Записи «Файл» копий результата (ключ `…/original`, работа — задание) в «ожидает» с терминальным заданием; запись «Файл» хранит, какой работе принадлежит, записи предпросмотров (работа — версия) обход не берёт | Обходчик очистки | Периодический обход, два прохода с льготным сроком (ADR-0011 §4 «Очистка») | Следующий обход | Условный переход «ожидает → очищен» |
| Физическое удаление эскиза, шаги 2–4 | Строка эскиза: `deleted_at`, `cleanup_done_at`, служебные колонки | Уборщик | Пометка в первой транзакции удаления; обход `deleted_at IS NOT NULL AND cleanup_done_at IS NULL` | Обход подбирает по пометке, а не по памяти процесса (ADR-0010 «Файлы») | Аренда с поколением; удаление объектов идемпотентно. Перечисление и удаление по префиксам, затем `cleanup_done_at` — отметка, что шаги 2–4 выполнены; защиту от поздних записей она не прекращает (строка ниже) |
| Обход удалённых префиксов | Строки эскиза и загрузки: `deleted_at`, `last_sweep_at` | Уборщик | Периодический проход по всем эскизам и загрузкам с `deleted_at`, включая те, у которых стоит `cleanup_done_at`; порядок — по `last_sweep_at` | Следующий проход | Без аренды и захвата (раздел 1): удаление идемпотентно, два уборщика над одним префиксом безвредны, `last_sweep_at` задаёт порядок, не защиту. **Решение владельца 2026-09-11 (второе ревью): в первом выпуске обход бессрочный.** Аренда не ограничивает время внешней записи: исполнитель может остановиться перед `PUT`, пережить истечение аренды и любой контрольный проход, затем записать объект; проверка поколения защитит базу, но объект появится, а падение исполнителя оставит его в хранилище. Поэтому конечный льготный срок и проверка живых аренд гарантии не дают; вариант «контрольный проход после льготного срока» отклонён. Прекращение обхода для эскиза требует отдельно доказанного прекращения всех возможных записей — не решено, в первом выпуске не применяется. Условие захвата новых работ предпросмотра (раздел 1) сужает окно, но не закрывает его. Удаление своего объекта обработчиком по пометке — страховка. Поздние записи генератора в `transfer/` покрывает правило жизненного цикла бакета (ADR-0010) |
| Физическое удаление загрузки | Строка загрузки, те же колонки | Уборщик | `DELETE /uploads/{id}` ставит пометку (ADR-0013 §6); обход | То же | То же, включая бессрочный обход префикса `client/uploads/<upload_id>/` |
| Гостевая очистка | Строка гостевой сессии: срок, `cleanup_done_at` | Уборщик сессий | Периодический обход истёкших сессий | Следующий обход | **Одна транзакция на сессию**: сессия `FOR UPDATE` — та же строка, что у присоединения (ADR-0013 §4), — затем внутри неё для всех эскизов сессии по возрастанию идентификатора первая транзакция удаления (эскиз `FOR UPDATE` → задания), пометка всех загрузок, `cleanup_done_at`. Порядок «владелец → эскиз → загрузка → задание» ADR-0013 соблюдён. Присоединение ждёт на строке сессии и после фиксации находит пустую сессию; разбить очистку на транзакции по одному эскизу нельзя — присоединение проскочило бы между ними и забрало часть эскизов. Физическая очистка объектов — строками выше (ADR-0012 §10, ADR-0007) |
| Доставка уведомлений и писем | «Задание доставки» на обращение и канал (ADR-0003, ADR-0010); письма восстановления пароля — тот же тип записи (выведено мной) | Отправитель доставок | Вставка в транзакции обращения (ADR-0012 §8) или запроса восстановления; обход по `next_attempt_at` | Строка с попытками; неизвестный исход отправки фиксируется отдельно от успеха (ADR-0003) | `SKIP LOCKED`, аренда; каналы независимы; исчерпание — `exhausted_at`, заметно оператору |
| Карантин сообщений неизвестной версии | Таблица карантина по `job_id` и типу сообщения | Потребитель результатов при неизвестной `contract_version` | Доставка | Без обработки; администратор уведомляется | Стирание по `job_id` в транзакции удаления (ADR-0011 §6) |
| Просроченные сеансы входа | Строки сеансов | Уборщик сессий | Периодический обход | Следующий обход | Удаление идемпотентно |
| Восстановление попыток по времени | Обход владельцев, вставка движения «восстановление» в журнал лимитов (ADR-0013 §3) | Обходчик лимитов | Периодический обход | Следующий обход; движение идемпотентно по владельцу и периоду | Само восстановление — принятое решение ADR-0006; открыт только способ (накопление или до трёх) и момент отсчёта, их задаёт владелец; без этого правила первый выпуск невозможен |

## 3. Генератор: сохранённые работы

| Работа | Где хранится | Кто выполняет | Что запускает | После падения | Защита от двух исполнителей |
| --- | --- | --- | --- | --- | --- |
| Приём `SubmitJob` и `EraseGeneration` | Сообщение в брокере до ack; строка Job | Потребитель команд, одна очередь на обе (ADR-0011 §6) | Доставка | Ack после фиксации Job (ADR-0011 §2); повторная доставка — по таблицам §2 и §5 | Первичный ключ `job_id`, вставка с игнорированием конфликта (ADR-0013 §4) |
| Исполнение задания | Строка Job: этап, аренда, подготовленный запрос | Исполнитель | Захват при приёме или обход `queued` | Аренда истекает → восстановление | Захват с `running` и поколением аренды, записи с `WHERE lease_generation = :mine` (ADR-0013 §7) |
| Восстановление | Job `running` с истёкшей арендой | Процесс восстановления | Периодический обход `FOR UPDATE SKIP LOCKED` | Следующий обход | Последний `ProviderCall` в `pending`/`running` → `outcome_unknown`, Job в `awaiting_reconciliation`, публикация; иначе повторный захват со следующего этапа (ADR-0011 §2) |
| Сверка неизвестного исхода | Job `awaiting_reconciliation`, `next_check_at`, `reconciliation_until` | Процесс сверки | Вход в состояние: в той же транзакции на Job сохраняется `reconciliation_until = min(момент входа + окно маршрута, deadline_at)` — окно сверки задаёт маршрут, остаток до общего срока учитывается (ADR-0011 §3); опрос провайдера с нарастающей паузой до него | `next_check_at` и `reconciliation_until` в базе, следующий обход; перезапуск процесса окно не начинает заново (замечание владельца 2026-09-11) | Публикация только при входе в состояние и при исходе (ADR-0013 §7); после `reconciliation_until` — `failed` с `provider_outcome_unresolved`, публикация |
| Отправка Result | Строка outbox `(job_id, revision)` | Отправитель outbox | Обход | Строка на месте | `SKIP LOCKED`, аренда; удаление по ack (ADR-0011 «Параметры»: подтверждения от backend нет) |
| Стирание по сроку | Job с ещё не стёртым текстом, у которых `deadline_at` плюс срок хранения уже прошли — независимо от состояния | Обходчик хранения | Периодический обход | Следующий обход | Срок считается от `deadline_at`, не от терминального состояния: после `deadline_at` платный вызов не начнётся (ADR-0011 §2) и текст не нужен, а Job, застрявший в сверке или без исполнителя, иначе держал бы текст вопреки «независимо от команды» (ADR-0010). Транзакция стирания ADR-0013 §6 **есть событие публикации**: установка `content_erased_at` входит в перечень ADR-0013 §7, поэтому та же транзакция даёт `revision + 1`, очищенный снимок и запись outbox; без новой ревизии переотправленный снимок с уже применённой ревизией backend отбросил бы, и подтверждение стирания не зафиксировалось бы (замечание владельца 2026-09-11). **Состояние Job стирание не выбирает** (решение владельца 2026-09-11, второе ревью): отсутствие незавершённого `ProviderCall` не означает, что генерации не было — вызов мог успешно завершиться, а исполнитель остановиться после сохранения оригинала до фиксации итога; `deadline_exceeded` тогда солгал бы. Стирание выполняется независимо: `FOR UPDATE` Job, стирание полей, `content_erased_at`, а для Job в `queued`/`running` — без публикации и без смены состояния и аренды. Завершение такого Job определяют сохранённый этап и последний `ProviderCall` по правилам восстановления ADR-0011 §2: вызова нет — исполнитель перед первым платным вызовом видит истёкший `deadline_at` и завершает `deadline_exceeded` (единственный случай этого кода); последний вызов завершён успешно и оригинал сохранён — этапы после вызова повторяемы, текст им не нужен, исход `succeeded`; вызов в `pending`/`running` — `outcome_unknown` и сверка до `reconciliation_until`. Первая же публикация после стирания несёт `content_erased_at`: снимок строится из строки Job в транзакции публикации, не из памяти исполнителя. Барьер для производного текста (выведено мной): запись подготовленного запроса и любого производного клиентского текста в Job идёт с условием `content_erased_at IS NULL` — как `erase_requested_at` в ADR-0013 §7 для команды; ноль строк — исполнитель текст не пишет и продолжает без него. Иначе исполнитель с живой арендой, застрявший в вызове текстовой модели и вернувшийся после срока хранения, записал бы производный текст в уже стёртый Job — аренда время внешнего вызова не ограничивает. Job, до которого восстановление не дошло, текст уже не держит — это и есть «независимо от команды»; его исход ждёт восстановления, backend к тому времени завершил задание по сроку сам (ADR-0011 §1). Поздняя команда `EraseGeneration` записи не меняет и переотправляет текущий Result (ADR-0011 §5) |
| Карантин | Таблица карантина | Потребитель команд при неизвестной `contract_version` | Доставка | — | Стирание по `EraseGeneration` |

Правило жизненного цикла `transfer/` — настройка бакета, не процесс
(ADR-0010 «Файлы»).

## 4. Два решения, которые ADR-0010 отдал уровню исполнения

Оба выведены мной; в ревью владельца не оспорены, отдельно не подтверждены.

1. **Удаление объектов при удалении эскиза и загрузки** — перечислением
   по префиксам `client/sketches/<sketch_id>/`, `transfer/input/<job_id>/`,
   `transfer/output/<job_id>/` для эскиза и `client/uploads/<upload_id>/`
   для загрузки (ключи ADR-0011 §6) как основной способ; записи «Файл» —
   для переходов состояний и `Content-Type`. Причина: поздний `PUT`
   предпросмотра, зафиксированный обработчиком до того, как он увидел
   пометку удаления, попадает под префикс, а в записи «Файл» может ещё
   стоять «ожидает». Перечисление повторяемо и не требует знать все ключи
   заранее, но само по себе не ловит запись, завершившуюся после обхода, —
   поэтому обход удалённых префиксов в первом выпуске бессрочный
   (раздел 2, решение владельца).
2. **Обход шагов 2–4 после сбоя** — пометки `deleted_at` и
   `cleanup_done_at` на строке эскиза; уборщик доводит шаги по пометке
   в порядке ADR-0010, результат идемпотентен; `cleanup_done_at`
   подтверждает выполненную очистку, но не прекращает обход префиксов
   (`last_sweep_at`).

## 5. Свойства

- Каждый цикл безопасен в N экземплярах: работы забираются условными
  обновлениями и `SKIP LOCKED`, фиксирующие транзакции перечитывают
  состояние, а проходы без захвата идемпотентны. Процессов, требующих
  единственности, нет.
- Число процессов и экземпляров — уровень 5. Минимальная раскладка:
  у backend процесс API и фоновый процесс со всеми циклами; у генератора
  один тип процесса со всеми циклами. Любой цикл можно вынести отдельно
  без изменения правил.
- Потребители брокера описаны свойствами ADR-0011 «Параметры
  и требования»: хранение сообщения до потребления или истечения срока,
  доставка минимум один раз, ack после фиксации, малая предвыборка.
  Ни одна строка таблиц выше от конкретного продукта не зависит.
- Запуск по обходу с интервалами, без сигналов между процессами.

Владельцем не обсуждались; обоснования проверяемы по ADR.

| --- | --- |
| Общая таблица задач для всех фоновых работ | Второй источник истины рядом с записью, которая и есть работа; служебные колонки на самой записи дают ту же выборку |

| Сигналы между процессами вместо обхода | Ещё один канал с собственными потерями; обход с интервалом достаточен и восстанавливается сам |

## Следствия для ADR-0013

Выведены мной при учёте замечаний владельца; внести при уточнении
ADR-0013:

- §5: у записи «Файл» признак работы-владельца — задание (копия
  результата) или версия (предпросмотр); обход очистки берёт только
  первые.
- §6: на строках эскиза и загрузки `last_sweep_at` рядом с `deleted_at`
  и `cleanup_done_at`; стирание по сроку у генератора для Job
  в `queued`/`running` состояние и аренду не меняет.
- §7: на Job `reconciliation_until`; стирание по сроку — событие
  публикации для публикуемых состояний, для остальных
  `content_erased_at` входит в первую последующую публикацию;
  восстановление, отнимающее работу у исполнителя, делает
  `lease_generation + 1` (это захват ADR-0013 §7); записи подготовленного
  запроса и производного текста в Job — с условием
  `content_erased_at IS NULL`, как `erase_requested_at` для команды.
