## Контекст

Шаг 2 уровня 4 по порядку владельца (ADR-0013 «Контекст»): исполнители,
отправители outbox, обработчики результатов, восстановление, предпросмотры
и очистка. Требуемый результат — для каждой сохранённой работы определены
исполнитель и способ восстановления после его падения.

Что уже задано и здесь не переопределяется: захват длинных работ условным
обновлением с поколением аренды и записи исполнителя с проверкой поколения
(ADR-0013 §7); публикация Result только по событиям (ADR-0013 §7); две
семантики outbox (ADR-0013 §6); транзакции по срокам берут только строку
задания (ADR-0013 §5); подтверждение входящих сообщений после фиксации
(ADR-0011 §2, §4); два решения, которые ADR-0010 «Файлы» отдал уровню
исполнения — способ удаления объектов задания и способ обхода шагов 2–4
после сбоя.

## Решение в одном абзаце

Каждая сохранённая работа — строка в базе своей стороны с одинаковым
набором служебных колонок; ни один процесс не держит незавершённую работу
в памяти. Короткие работы забираются `FOR UPDATE SKIP LOCKED` с короткой
арендой, длинные — захватом с поколением аренды из ADR-0013 §7; это один
механизм, а не два. Повтор — по `next_attempt_at` с нарастающей паузой
и счётчиком попыток; исчерпание фиксируется на строке признаком, а не
потерей работы. Каждый цикл безопасен в N экземплярах, ни один не требует
единственности. Потребители брокера описаны свойствами из ADR-0011;
технология брокера — уровень 5 (решение владельца 2026-09-11).

## 1. Общий механизм записи-работы

Выведено мной; ждёт построчного ревью владельца.

- Служебные колонки на строке работы: `claimed_by`, `lease_generation`,
  `lease_until`, `attempts`, `next_attempt_at`, `done_at`, `exhausted_at`,
  `last_error`. Отдельной общей таблицы задач нет: колонки живут на той
  записи, которая и есть работа (версия, эскиз, загрузка, задание
  доставки, outbox).
- Захват — условное обновление `WHERE (lease_until IS NULL OR lease_until
  < now()) AND next_attempt_at <= now()` с `lease_generation =
  lease_generation + 1`, как в ADR-0013 §7; выборка кандидатов —
  `FOR UPDATE SKIP LOCKED`. Каждая последующая запись исполнителя —
  с `WHERE lease_generation = :mine`; ноль строк означает потерю аренды,
  исполнитель останавливается без фиксации.
- Работа с вызовом хранилища, брокера или внешнего сервиса не держит
  транзакцию открытой на время вызова: захват, вызов, фиксирующая
  транзакция. Эффект каждой работы идемпотентен по ключу объекта или
  по условному переходу состояния, поэтому повтор после падения посреди
  вызова безвреден.
- Неудача — `attempts + 1`, `next_attempt_at` с нарастающей паузой,
  `last_error`; исчерпание — `exhausted_at`. Как об исчерпании узнаёт
  администратор — шаг 4. Численные значения пауз, попыток и интервалов
  обхода — шаг 4.
- Запуск — обход с интервалом, без сигналов между процессами. Обход
  выбирает строки по индексируемым колонкам (`state`, `next_attempt_at`,
  `deadline_at`, `deleted_at`), никогда по содержимому `jsonb`
  (ADR-0013 §2).

## 2. Backend: сохранённые работы

| Работа | Где хранится | Кто выполняет | Что запускает | После падения посреди работы | Защита от двух исполнителей |
| --- | --- | --- | --- | --- | --- |
| Отправка `SubmitJob` | Строка outbox | Отправитель outbox | Обход по `next_attempt_at` | Строка на месте, следующий обход; двойная отправка безвредна — генератор различает по `job_id` (ADR-0011 §1) | `SKIP LOCKED`, короткая аренда; удаление по ack брокера и в транзакциях завершения задания (ADR-0013 §6) |
| Отправка `EraseGeneration` | Строка outbox, живёт до `erase_confirmed_at` на задании | Тот же отправитель | Обход; переотправка с нарастающей паузой (ADR-0011 §5) | То же | То же; строка не удаляется по ack, только по подтверждению стирания |
| Приём Result | Сообщение в брокере до ack | Потребитель результатов | Доставка брокером | Ack не дан → повторная доставка; шаги до фиксации повторяемы (ADR-0011 §4) | Общее правило транзакций по Result и запись «Файл» (ADR-0013 §5) |
| Сроки отправки и исполнения | Колонки сроков на задании | Сторож сроков | Периодический обход нетерминальных заданий с истёкшим сроком | Следующий обход | Транзакция ADR-0013 §5 п. 4: задание `FOR UPDATE`, проверка нетерминальности |
| Подготовка предпросмотра | Строка версии: `preview_state`, номер серии, служебные колонки | Обработчик предпросмотров | Вставка в транзакции принятия результата (ADR-0011 §4 шаг 4) и `preview-retry` — новая серия (ADR-0012 §6) | Аренда истекает, обход подбирает; повтор из того же оригинала, ключ предпросмотра тот же | Аренда с поколением; запись «Файл» для ключа предпросмотра создаётся до `PUT` (ADR-0012 §6: `Content-Type` из неё); фиксирующая транзакция берёт только версию `FOR UPDATE`, читает пометку удаления эскиза в той же транзакции без блокировки его строки и при пометке `ready` не ставит; объект, записанный до пометки, убирает уборщик по префиксу (раздел 4). Эскиз не блокируется намеренно: `FOR SHARE` на нём заставил бы принятие Result по второй параллельной доработке ждать финализации предпросмотра первой (выведено мной, вариант с блокировкой эскиза вынесен владельцу) |
| Обход очистки «Файл» | Записи «Файл» в «ожидает» с терминальным заданием | Обходчик очистки | Периодический обход, два прохода с льготным сроком (ADR-0011 §4 «Очистка») | Следующий обход | Условный переход «ожидает → очищен» |
| Физическое удаление эскиза, шаги 2–4 | Строка эскиза: `deleted_at`, `cleanup_done_at`, служебные колонки | Уборщик | Пометка в первой транзакции удаления; обход `deleted_at IS NOT NULL AND cleanup_done_at IS NULL` | Обход подбирает по пометке, а не по памяти процесса (ADR-0010 «Файлы») | Аренда с поколением; удаление объектов идемпотентно |
| Физическое удаление загрузки | Строка загрузки, те же колонки | Уборщик | `DELETE /uploads/{id}` ставит пометку (ADR-0013 §6); обход | То же | То же |
| Гостевая очистка | Строка гостевой сессии: срок, `cleanup_done_at` | Уборщик сессий | Периодический обход истёкших сессий | Следующий обход | **Одна транзакция на сессию**: сессия `FOR UPDATE` — та же строка, что у присоединения (ADR-0013 §4), — затем внутри неё для всех эскизов сессии по возрастанию идентификатора первая транзакция удаления (эскиз `FOR UPDATE` → задания), пометка всех загрузок, `cleanup_done_at`. Порядок «владелец → эскиз → загрузка → задание» ADR-0013 соблюдён. Присоединение ждёт на строке сессии и после фиксации находит пустую сессию; разбить очистку на транзакции по одному эскизу нельзя — присоединение проскочило бы между ними и забрало часть эскизов. Физическая очистка объектов — строками выше (ADR-0012 §10, ADR-0007) |
| Доставка уведомлений и писем | «Задание доставки» на обращение и канал (ADR-0003, ADR-0010); письма восстановления пароля — тот же тип записи (выведено мной) | Отправитель доставок | Вставка в транзакции обращения (ADR-0012 §8) или запроса восстановления; обход по `next_attempt_at` | Строка с попытками; неизвестный исход отправки фиксируется отдельно от успеха (ADR-0003) | `SKIP LOCKED`, аренда; каналы независимы; исчерпание — `exhausted_at`, заметно оператору |
| Карантин сообщений неизвестной версии | Таблица карантина по `job_id` и типу сообщения | Потребитель результатов при неизвестной `contract_version` | Доставка | Без обработки; администратор уведомляется | Стирание по `job_id` в транзакции удаления (ADR-0011 §6) |
| Просроченные сеансы входа | Строки сеансов | Уборщик сессий | Периодический обход | Следующий обход | Удаление идемпотентно |
| Восстановление попыток по времени | Обход владельцев, вставка движения «восстановление» в журнал лимитов (ADR-0013 §3) | Обходчик лимитов | Периодический обход | Следующий обход; движение идемпотентно по владельцу и периоду | Само восстановление — принятое решение ADR-0006; открыт только способ (накопление или до трёх) и момент отсчёта, их задаёт владелец; без этого правила первый выпуск невозможен |

## 3. Генератор: сохранённые работы

| Работа | Где хранится | Кто выполняет | Что запускает | После падения | Защита от двух исполнителей |
| --- | --- | --- | --- | --- | --- |
| Приём `SubmitJob` и `EraseGeneration` | Сообщение в брокере до ack; строка Job | Потребитель команд, одна очередь на обе (ADR-0011 §6) | Доставка | Ack после фиксации Job (ADR-0011 §2); повторная доставка — по таблицам §2 и §5 | Первичный ключ `job_id`, вставка с игнорированием конфликта (ADR-0013 §4) |
| Исполнение задания | Строка Job: этап, аренда, подготовленный запрос | Исполнитель | Захват при приёме или обход `queued` | Аренда истекает → восстановление | Захват с `running` и поколением аренды, записи с `WHERE lease_generation = :mine` (ADR-0013 §7) |
| Восстановление | Job `running` с истёкшей арендой | Процесс восстановления | Периодический обход `FOR UPDATE SKIP LOCKED` | Следующий обход | Последний `ProviderCall` в `pending`/`running` → `outcome_unknown`, Job в `awaiting_reconciliation`, публикация; иначе повторный захват со следующего этапа (ADR-0011 §2) |
| Сверка неизвестного исхода | Job `awaiting_reconciliation`, `next_check_at` | Процесс сверки | Вход в состояние; опрос провайдера по маршруту с нарастающей паузой до `deadline_at` (ADR-0011 §3) | `next_check_at` в базе, следующий обход | Публикация только при входе в состояние и при исходе (ADR-0013 §7); после `deadline_at` — `provider_outcome_unresolved`, публикация |
| Отправка Result | Строка outbox `(job_id, revision)` | Отправитель outbox | Обход | Строка на месте | `SKIP LOCKED`, аренда; удаление по ack (ADR-0011 «Параметры»: подтверждения от backend нет) |
| Стирание по сроку | Job с ещё не стёртым текстом, у которых `deadline_at` плюс срок хранения уже прошли — независимо от состояния | Обходчик хранения | Периодический обход | Следующий обход | Срок считается от `deadline_at`, не от терминального состояния: после `deadline_at` платный вызов не начнётся (ADR-0011 §2) и текст не нужен, а Job, застрявший в сверке или без исполнителя, иначе держал бы текст вопреки «независимо от команды» (ADR-0010). | Карантин | Таблица карантина | Потребитель команд при неизвестной `contract_version` | Доставка | — | Стирание по `EraseGeneration` |

Правило жизненного цикла `transfer/` — настройка бакета, не процесс
(ADR-0010 «Файлы»).

## 4. Два решения, которые ADR-0010 отдал уровню исполнения

Оба выведены мной, владельцем приняты вместе с документом.

1. **Удаление объектов при удалении эскиза и загрузки** — перечислением
   по префиксам `client/sketches/<sketch_id>/`, `transfer/input/<job_id>/`,
   `transfer/output/<job_id>/` для эскиза и `client/uploads/<upload_id>/`
   для загрузки (ключи ADR-0011 §6) как основной способ; записи «Файл» —
   для переходов состояний и `Content-Type`. Причина: поздний `PUT`
   предпросмотра, зафиксированный обработчиком до того, как он увидел
   пометку удаления, попадает под префикс, а в записи «Файл» может ещё
   стоять «ожидает». Перечисление повторяемо и не требует знать все ключи
   заранее.
2. **Обход шагов 2–4 после сбоя** — пометки `deleted_at` и `cleanup_done_at`
   на строке эскиза; уборщик доводит шаги по пометке в порядке ADR-0010,
   результат идемпотентен.

## 5. Свойства

- Каждый цикл безопасен в N экземплярах: работы забираются условными
  обновлениями и `SKIP LOCKED`, фиксирующие транзакции перечитывают
  состояние. Процессов, требующих единственности, нет.
- Число процессов и экземпляров — уровень 5. Минимальная раскладка:
  у backend процесс API и фоновый процесс со всеми циклами; у генератора
  один тип процесса со всеми циклами. Любой цикл можно вынести отдельно
  без изменения правил.
- Потребители брокера описаны свойствами ADR-0011 «Параметры
  и требования»: хранение сообщения до потребления или истечения срока,
  доставка минимум один раз, ack после фиксации, малая предвыборка.
  Ни одна строка таблиц выше от конкретного продукта не зависит.
- Запуск по обходу с интервалами, без сигналов между процессами.

## Варианты, отклонённые при подготовке предложения

Владельцем не обсуждались; обоснования проверяемы по ADR.

| Вариант | Почему не предложен |
| --- | --- |
| Общая таблица задач для всех фоновых работ | Второй источник истины рядом с записью, которая и есть работа; служебные колонки на самой записи дают ту же выборку |
| Хранение незавершённой работы в памяти процесса | Против ADR-0011 §2: источник истины — база; падение теряло бы работу |
| Отдельный механизм захвата для коротких работ | ADR-0013 §7 уже задал захват с поколением аренды; второй механизм добавил бы второй набор ошибок |
| Сигналы между процессами вместо обхода | Ещё один канал с собственными потерями; обход с интервалом достаточен и восстанавливается сам |
