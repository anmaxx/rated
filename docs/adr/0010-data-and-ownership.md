## Контекст

ADR-0009 разделил систему на frontend, backend, генератор, хранилища
и внешние сервисы. Этот документ отвечает, какие данные существуют, какая
часть системы владеет каждой записью и файлом, и как backend и генератор
обмениваются заданиями и результатами.

## Сущности backend

Все записи ниже хранятся в базе backend. Он владеет всеми, кроме «Вызова
провайдера»: тот первичен у генератора, backend держит копию.

| Сущность | Что хранит |
| --- | --- |
| Пользователь | Email, имя, фамилия, хеш пароля, телефон (необязателен до обращения), ровно одна роль: клиент, мастер или администратор. Одна таблица для всех ролей |
| Тип клиента | Справочник студии: «постоянный», «любимый» и другие. Ведёт мастер или администратор, клиент его не видит |
| Тип клиента у пользователя | Связь пользователя с типами: у одного клиента их может быть несколько сразу. Ставит мастер или администратор |
| Гостевая сессия | Идентификатор, секрет cookie, срок действия. Владеет эскизом до входа. Состояния гостевой попытки не хранит |
| Сеанс входа | Серверная запись cookie для клиента, мастера и администратора |
| Эскиз | Владелец (гость или пользователь), описание, стиль, место нанесения, размер, происхождение: текст, загрузка или другая версия; ссылка на текущую версию |
| Версия эскиза | Оригинал и предпросмотр со знаком как два файла, состояние предпросмотра: готовится, готов или ошибка; родительская версия, задание генерации, которое её создало |
| Загрузка | Файл клиента, владелец, результат проверки содержимого. Основа для эскиза или вложение в обращение |
| Файл | Запись об объекте в хранилище: ключ, размер, тип, назначение |
| Задание генерации | Бизнес-операция: кто запросил; эскиз; исходная версия; текстовый prompt; negative prompt; стиль; параметры; состояние; дата создания; дата завершения; время этапов выполнения |
| Вызов провайдера | Копия `ProviderCall` генератора для админки, сверки и учёта: задание; провайдер; модель; номер попытки; внешний request id; состояние; начало; завершение; ошибка HTTP/API; собранный запрос к модели отдельным полем; технические метаданные провайдера по списку разрешённых полей. Источник истины — генератор |
| Лимиты клиента | Журнал движений попыток по владельцу: гостевое начисление, регистрационное, восстановление по времени, резерв под задание, списание, возврат. Остаток равен сумме записей и числом не хранится. Единственный источник истины для остатка, включая гостевую попытку |
| Расход провайдера | Стоимость по каждому вызову провайдера: единицы, сумма как её сообщил провайдер, признак «фактическая», «расчётная» или «неизвестная», дата |
| Обращение | Клиент, выбранная версия или загрузка, телефон и сообщение на момент отправки, состояние |
| Задание доставки | Обращение, канал, получатель, состояние, число попыток, идентификатор сообщения от сервиса |
| Получатель уведомлений | Канал и адрес; задаёт администратор |
| Запись | Журнал мастера: клиент, дата и время, длительность, заметка, обращение-источник. Клиент видит свои будущие сеансы |

Стиль задаётся при создании эскиза и дальше не меняется. Доработка уточняет
описание и порождает новую версию того же эскиза; смена стиля создаёт новый
эскиз с происхождением «другая версия». Так у клиента остаются обе работы
рядом — форма та же, стиль разный, — вместо того чтобы вторая подменяла
первую в истории версий. Отсюда же следует, что стиль в задании генерации
всегда равен стилю его эскиза и разойтись с ним не может.

Сущности «проект» нет: владелец исключил её, чтобы не вводить клиенту
незнакомую абстракцию. Календарь это журнал мастера, а не самозапись
клиента по свободным окнам.

## Сущности генератора

Генератор не хранит профиля клиента: ни имён, ни контактов, ни истории
эскизов. Клиентский текст задания — prompt, negative prompt, собранный
запрос и другие производные — он держит только пока тот нужен для
выполнения задания. У него своя база с тремя записями и одна область
в хранилище.

| Сущность | Что хранит |
| --- | --- |
| Job | Единица очереди заданий: номер задания генерации, режим (новый эскиз или доработка), prompt, negative prompt, стиль, параметры, ключ исходного файла при доработке. Состояние: `queued`, `running`, `awaiting_reconciliation`, `succeeded`, `failed`, `cancelled` |
| ProviderCall | Самостоятельная запись одного внешнего вызова: задание, провайдер, модель, номер попытки, внешний request id, состояние (`pending`, `running`, `succeeded`, `failed`, `outcome_unknown`), начало, завершение, ошибка, расход, собранный запрос к модели отдельным полем. Создаётся до платного вызова и существует независимо от того, сформирован ли Result |
| Result | Итог выполнения задания: номер задания, состояние, вызовы провайдера данными или ссылками на `ProviderCall`, время этапов, ключ файла результата |

`ProviderCall` первичен у генератора: у него собственные состояние, номер
попытки, внешний request id, время выполнения, ошибка и расход, и он должен
существовать независимо от того, сформирован ли Result. Запись создаётся
до платного вызова — на неё опирается проверка исхода у провайдера из шага 2,
которой иначе было бы не на что опереться. Backend держит копию для
административного интерфейса, сверки и учёта расходов, но источником истины
для неё не является. Result фиксирует итог выполнения задания и передаёт
backend то, что нужно для завершения задания и синхронизации технического
учёта; вызовы провайдера не вложены в Result, а идут данными или ссылками
на самостоятельные `ProviderCall`.

Отдельной записью Result в backend не хранится: тот раскладывает полученное
по своим сущностям. Собранный запрос к модели относится к конкретному вызову
и ложится отдельным полем в копию `ProviderCall`, отдельно от технических
метаданных провайдера; при удалении эскиза это поле очищается как клиентское
содержание. Время этапов относится к заданию целиком и сохраняется в задании
генерации, где остаётся после удаления вместе с прочей технической историей.

Неизвестность исхода относится к конкретному вызову, а не к заданию: одно
задание может породить несколько внешних вызовов, и текстовая модель может
ответить успешно, пока исход графической неизвестен. Поэтому
`outcome_unknown` — состояние `ProviderCall`. Если от исхода такого вызова
зависит продолжение задания, Job переходит в `awaiting_reconciliation`
и до установления результата новых платных вызовов не делает. После сверки
состояние `ProviderCall` уточняется, а Job либо продолжает выполнение,
либо завершается соответствующим итогом.

Клиентский текст у генератора стирается по команде и по сроку. При удалении
эскиза backend отправляет идемпотентную команду стирания по номеру задания
генерации — тем же направлением, что и Job, формат определяет уровень
контрактов. Генератор убирает клиентский текст из Job, `ProviderCall`
и Result и сохраняет
признак стирания, чтобы позднее или повторно доставленное сообщение не
восстановило эти данные. Техническая история задания остаётся: идентификаторы,
провайдер, модель, внешний request id, состояние, тайминги, коды ошибок,
usage и расход.

Метаданные провайдера генератор записывает только по списку разрешённых
полей: тела запросов и ответов, эхо промпта и другие поля с клиентским
содержимым не сохраняются. Независимо от команды действует ограниченный
срок хранения клиентского текста — он очищает то, что осталось после сбоя
или недоставленной команды стирания.

## Поля задания: три слоя

- **Текстовый prompt** это текст клиента как он его ввёл. Хранится без
  изменений, чтобы после запуска были видны реальные запросы.
- **Параметры** содержат версию правил студии (шаблон требований к эскизу,
  ведёт администратор) и настройки модели. Отдельной сущности для правил нет.
- **Собранный запрос к модели** делает генератор, хранит в `ProviderCall`
  и передаёт backend через Result. Ввод клиента и то, что ушло провайдеру,
  никогда не смешиваются.

Negative prompt поддерживают не все провайдеры. Поле хранится всегда,
генератор передаёт его, если маршрут умеет. Клиентский текст в нём есть:
при удалении эскиза оно затирается наравне с prompt. Вводит ли его клиент
сам или подставляет шаблон студии — вопрос API на уровне контрактов.

## Обмен между backend и генератором

Обмен идёт через две очереди, а не через вызовы API.

1. Backend создаёт задание генерации, резервирует попытку в одной транзакции
   с проверкой остатка и кладёт Job в очередь заданий.
2. Генератор берёт Job. Доставка минимум один раз, поэтому перед любым
   платным вызовом генератор проверяет по номеру задания, не выполнял ли его.
   Job в состоянии `running` при падении потребителя не перевыдаётся
   молча: сначала сверка исхода у провайдера по сохранённому `ProviderCall`.
3. Генератор собирает запрос, записывает `ProviderCall` до обращения
   к провайдеру, вызывает модель через роутер и получает результат.
   Далее по порядку: скачать результат от провайдера; проверить тип и размер,
   декодируя изображение, а не доверяя заголовкам; положить файл
   в `transfer/output/`; закрыть `ProviderCall` и записать Result в свою базу;
   положить Result в очередь результатов.
4. Backend читает Result, копирует файл в клиентскую область серверной
   операцией хранилища, создаёт версию эскиза, делает предпросмотр с водяным
   знаком, копирует вызовы и расход, переводит резерв в списание. При
   подтверждённой ошибке резерв возвращается; пока задание стоит
   в `awaiting_reconciliation`, резерв держится.

Версия существует и до готового предпросмотра: по ADR-0003 при сбое подготовки
оригинал сохраняется, клиенту показывается состояние подготовки или ошибка,
а сама подготовка повторяется из сохранённого оригинала. Новой платной
генерации это не требует, и чистый оригинал клиенту всё равно не показывают.
Ошибка знака по ADR-0006 обрабатывается по своим правилам, отдельно
от подтверждённой ошибки и неизвестного исхода.

Изображение не приходит в браузер из хранилища напрямую: доступ всегда идёт
через backend с проверкой права по ADR-0007. Клиент видит только предпросмотр
со знаком. Мастер после входа получает оригинал — ADR-0007 предусматривает
передачу мастеру наравне с чтением и вызовом модели.

## Файлы

Все файлы лежат в объектном хранилище за совместимым с S3 API: в проде
Yandex Object Storage по ADR-0004, локально MinIO, код одинаковый.
Пространство имён и права:

    transfer/input/<номер задания>/source    исходник для доработки
    transfer/output/<номер задания>/result   результат генерации
    client/…                                 оригиналы, предпросмотры, загрузки

| Область | Backend | Генератор | Очистка |
| --- | --- | --- | --- |
| `transfer/input/*` | `PUT`, `DELETE` | `GET` | Аварийная сборка мусора правилом жизненного цикла |
| `transfer/output/*` | `GET`, `COPY`, `DELETE` | `PUT` | Аварийная сборка мусора правилом жизненного цикла |
| `client/*` | `GET`, `PUT`, `DELETE` | Нет доступа | Без срока, до удаления клиентом |

Временные объекты удаляет только backend: он владелец жизненного цикла
клиентских данных, генератору `DELETE` не нужен. Правило жизненного цикла
передаточной области — аварийная сборка мусора на случай, когда штатное
удаление не состоялось, а не основной механизм. Ключ результата определён
номером задания, поэтому повторная запись после перевыдачи Job перезаписывает
тот же объект. Раскладка префиксов по бакетам — уровень инфраструктуры.

Исходный файл для доработки backend сам кладёт в `transfer/input/`
и указывает ключ в Job. Удаление по ADR-0007 целиком у backend и идёт
в таком порядке:

1. пометить эскиз удалённым, чтобы задание больше не порождало версию;
2. удалить объекты клиента в `client/`;
3. удалить объекты в `transfer/input/`;
4. удалить известные объекты в `transfer/output/`;
5. затереть клиентский текст в истории задания;
6. отправить генератору команду стирания по номеру задания.

Пометка идёт первой, потому что закрывает гонку: генератор может записать
результат уже после шага 4.

Клиентское содержимое убирается и из истории: текстовый prompt, negative
prompt и сохранённые производные запросы к моделям затираются физически —
значение обнуляется, а не подменяется меткой вроде «удалено». История
выполнения остаётся в технической части: идентификаторы, состояния,
провайдеры и модели, параметры без клиентского текста, временные метки,
вызовы, ошибки и расходы. Так сохраняются учёт и диагностика, но не
содержание, которое клиент удалил.

Удаление эскиза не определяет финансовый исход запущенного задания и не
удаляет историю его выполнения. Исход определяет то, был ли создан
пригодный оригинал — то есть скачал ли генератор файл, проверил тип
и размер и положил его в `transfer/output/`:

- задание отменено до создания оригинала — резерв возвращается;
- оригинал создан — попытка использована, даже если эскиз удалён раньше,
  чем клиент увидел результат;
- подтверждённая ошибка без созданного оригинала — резерв возвращается;
- неизвестный исход — резерв держится, пока задание стоит
  в `awaiting_reconciliation`.

Пометка эскиза удалённым — не то же самое, что `cancelled` у Job: задание
переходит в `cancelled`, только если отмена состоялась до создания оригинала.
Иначе оно доходит до своего итога, а удалённым остаётся эскиз.

Расход провайдера учитывается независимо от попытки клиента и сохраняется
в backend даже для удалённого эскиза. Поэтому поздний Result по удалённому
эскизу не отбрасывается целиком: backend завершает по нему состояние
задания, списывает или возвращает резерв, копирует вызовы и расход, но
версию эскиза не создаёт и удаляет `transfer/output/<номер задания>/`.
Если Result не придёт вовсе, объект подберёт правило жизненного цикла.
Механизм гарантированной отмены задания до создания оригинала — уровень
контрактов.

## Учёт

Лимиты клиента и расход провайдера ведутся раздельно, потому что попытка
клиента и рубль провайдера это разные единицы. Одно задание может породить
несколько вызовов провайдера: текстовая модель и графическая. Администратор
видит расход по дням и провайдерам и имеет один выключатель: остановить
новые генерации, не трогая кабинеты. Правило восстановления попыток
по ADR-0006 остаётся открытым; на структуру записей оно не влияет.

## Отвергнутые варианты

| Вариант | Почему отвергнут |
| --- | --- |
| Сущность «проект» между клиентом и эскизами | Незнакомая клиенту абстракция; обращение к мастеру группирует нужное само |
| Самозапись клиента по свободным окнам | Отдельный продукт по объёму; время сеанса согласуют лично |
| Оригинал живёт у генератора, backend хранит ключ | Удаление растягивается на два сервиса |
| Возврат результата обратным вызовом или опросом | Генератор должен знать адрес и ключ backend либо держать результат при его недоступности |
| Стоимость полями в backend-копии «Вызов провайдера» | Владелец выделил расход в отдельную сущность. У генератора расход остаётся полем `ProviderCall` и разворачивается в «Расход провайдера» при копировании |

## Что решает следующий уровень

Контракты: форматы сообщений Job, Result и команды стирания с их версиями;
API backend для frontend поверх host-only cookie backend и списка разрешённых
источников по ADR-0009; состояния Result и задания генерации в backend, а
также кто и в какой предельный срок сверяет неизвестный исход; ключи объектов
клиентской области и срок правила жизненного цикла для `transfer/`.
