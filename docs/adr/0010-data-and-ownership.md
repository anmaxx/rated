# ADR-0010: Данные и владение

- **Статус:** принят владельцем 2026-09-09 как второй уровень архитектуры;
  состав сущностей первоначальный и будет расширяться.
- **Дата:** 2026-09-09.
- **Принимает решение:** владелец проекта.
- **Связи:** [состав системы](0009-system-composition.md),
  [самостоятельный генератор](0008-independent-generation-service.md),
  [попытки](0006-generation-attempts-and-usage.md),
  [хранение и удаление](0007-sketch-storage-uploads-and-deletion.md).
- **Состояние реализации:** ни одна сущность не реализована.

## Контекст

ADR-0009 разделил систему на frontend, backend, генератор, хранилища
и внешние сервисы. Этот документ отвечает, какие данные существуют, какая
часть системы владеет каждой записью и файлом, и как backend и генератор
обмениваются заданиями и результатами.

## Сущности backend

Все записи ниже принадлежат backend и хранятся в его базе данных.

| Сущность | Что хранит |
| --- | --- |
| Пользователь | Email, имя, фамилия, хеш пароля, телефон (необязателен до обращения), роль: клиент, мастер, администратор. Одна таблица для всех ролей |
| Тип клиента | Справочник студии: «постоянный», «любимый» и другие. Ставит мастер или администратор, клиент его не видит |
| Гостевая сессия | Секрет cookie, срок, признак использованной гостевой попытки. Владеет эскизом до входа |
| Сеанс входа | Серверная запись cookie для клиента, мастера и администратора |
| Эскиз | Владелец (гость или пользователь), описание, стиль, происхождение: текст, загрузка или другая версия; ссылка на текущую версию |
| Версия эскиза | Оригинал и предпросмотр со знаком как два файла, родительская версия, задание генерации, которое её создало |
| Загрузка | Файл клиента, владелец, результат проверки содержимого. Основа для эскиза или вложение в обращение |
| Файл | Запись об объекте в хранилище: ключ, размер, тип, назначение |
| Задание генерации | Бизнес-операция: кто запросил; эскиз; исходная версия; текстовый prompt; negative prompt; стиль; параметры; состояние; дата создания; дата завершения |
| Вызов провайдера | Техническая запись (копия из Result): задание; провайдер; модель; номер попытки; внешний request id; состояние; начало; завершение; ошибка HTTP/API; сырые технические метаданные без байтов изображения |
| Лимиты клиента | Журнал движений попыток по владельцу: гостевое начисление, регистрационное, восстановление по времени, резерв под задание, списание, возврат. Остаток равен сумме записей и числом не хранится |
| Расход провайдера | Стоимость по каждому вызову провайдера: единицы, сумма как её сообщил провайдер, признак «фактическая» или «расчётная», дата |
| Обращение | Клиент, выбранная версия или загрузка, телефон и сообщение на момент отправки, состояние |
| Задание доставки | Обращение, канал, получатель, состояние, число попыток, идентификатор сообщения от сервиса |
| Получатель уведомлений | Канал и адрес; задаёт администратор |
| Запись | Журнал мастера: клиент, дата и время, длительность, заметка, обращение-источник. Клиент видит свои будущие сеансы |

Сущности «проект» нет: владелец исключил её, чтобы не вводить клиенту
незнакомую абстракцию. Календарь это журнал мастера, а не самозапись
клиента по свободным окнам.

## Сущности генератора

Генератор не хранит клиентских данных: ни имён, ни контактов, ни истории
эскизов. У него своя база с двумя записями и одна область в хранилище.

| Сущность | Что хранит |
| --- | --- |
| Job | Единица очереди заданий: номер задания генерации, режим (новый эскиз или доработка), prompt, negative prompt, стиль, параметры, ключ исходного файла при доработке. Состояние: в очереди, взято, выполнено, ошибка |
| Result | Состояние результата: номер задания, состояние, провайдер, модель, внешний идентификатор, собранный запрос к модели, вызовы провайдера с расходом, время этапов, ключ файла результата |

Записи «Вызов провайдера» первичны у генератора и копируются в backend
через Result, чтобы администратор видел всё в одном месте.

## Поля задания: три слоя

- **Текстовый prompt** это текст клиента как он его ввёл. Хранится без
  изменений, чтобы после запуска были видны реальные запросы.
- **Параметры** содержат версию правил студии (шаблон требований к эскизу,
  ведёт администратор) и настройки модели. Отдельной сущности для правил нет.
- **Собранный запрос к модели** делает генератор и возвращает в Result.
  Ввод клиента и то, что ушло провайдеру, никогда не смешиваются.

Negative prompt поддерживают не все провайдеры. Поле хранится всегда,
генератор передаёт его, если маршрут умеет.

## Обмен между backend и генератором

Обмен идёт через две очереди, а не через вызовы API.

1. Backend создаёт задание генерации, резервирует попытку в одной транзакции
   с проверкой остатка и кладёт Job в очередь заданий.
2. Генератор берёт Job. Доставка минимум один раз, поэтому перед любым
   платным вызовом генератор проверяет по номеру задания, не выполнял ли его.
   Задание в состоянии «взято» при падении потребителя не перевыдаётся молча:
   сначала проверка исхода у провайдера.
3. Генератор собирает запрос, вызывает модель через роутер и получает результат.
   Далее по порядку: скачать результат от провайдера; проверить тип и размер,
   декодируя изображение, а не доверяя заголовкам; положить файл в свою
   область хранилища; записать Result и вызовы провайдера в свою базу;
   положить Result в очередь результатов.
4. Backend читает Result, копирует файл в клиентскую область серверной
   операцией хранилища, создаёт версию эскиза, делает предпросмотр с водяным
   знаком, копирует вызовы и расход, переводит резерв в списание. При
   подтверждённой ошибке резерв возвращается; при неизвестном исходе
   держится до выяснения.

Изображение никогда не возвращается в браузер напрямую. Клиент видит только
предпросмотр, который выдаёт backend.

## Файлы

Все файлы лежат в объектном хранилище за совместимым с S3 API: в проде
Yandex Object Storage по ADR-0004, локально MinIO, код одинаковый. Две области:

| Область | Право генератора | Право backend | Срок |
| --- | --- | --- | --- |
| Передаточная | Только запись | Чтение и копирование | Объекты истекают правилом жизненного цикла через часы |
| Клиентская | Нет доступа | Владеет: оригиналы, предпросмотры, загрузки | Без срока, до удаления клиентом |

Исходный файл для доработки backend сам кладёт в передаточную область
и указывает ключ в Job. Удаление по ADR-0007 целиком у backend; генератору
чистить нечего, поздний Result по удалённому заданию отбрасывается
по состоянию задания.

## Учёт

Лимиты клиента и расход провайдера ведутся раздельно, потому что попытка
клиента и рубль провайдера это разные единицы. Одно задание может породить
несколько вызовов провайдера: текстовая модель и графическая. Администратор
видит расход по дням и провайдерам и имеет один выключатель: остановить
новые генерации, не трогая кабинеты. Правило восстановления попыток
по ADR-0006 остаётся открытым; на структуру записей оно не влияет.

## Отвергнутые варианты

| Вариант | Почему отвергнут |
| --- | --- |
| Сущность «проект» между клиентом и эскизами | Незнакомая клиенту абстракция; обращение к мастеру группирует нужное само |
| Самозапись клиента по свободным окнам | Отдельный продукт по объёму; время сеанса согласуют лично |
| Оригинал живёт у генератора, backend хранит ключ | Удаление растягивается на два сервиса |
| Возврат результата обратным вызовом или опросом | Генератор должен знать адрес и ключ backend либо держать результат при его недоступности |
| Стоимость полями в «Вызов провайдера» | Владелец выделил расход в отдельную сущность |

## Что решает следующий уровень

Контракты: формат сообщений Job и Result и их версии; API backend для
frontend с общим доменом cookie и списком разрешённых источников; правила
состояний задания и неизвестного исхода; ключи объектов и правило
жизненного цикла передаточной области.
