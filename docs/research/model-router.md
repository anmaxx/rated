## Инженерная задача

Роутер выбирает сервис и модель для задания, переводит запрос в нужный API
и возвращает генератору понятный результат. Рассматриваем Yandex AI Studio
и NanoGPT. Сам роутер работает в Yandex Cloud; правила передачи данных
сервисам должны быть частью его контракта.

Генератор выделен в самостоятельный внутренний сервис по
[ADR-0008](../adr/0008-independent-generation-service.md). Форма роутера
решена владельцем 2026-09-11: **библиотека внутри генератора**, не отдельный
сервис (ADR-0009 «Следствия», уточнение 2026-09-11, с основаниями). Ключи
провайдеров, идентификаторы внешних операций и учёт вызовов остаются
в зоне ответственности генератора (ADR-0011 §2–3; число его исполнителей
— уровень 4); роутер — модуль с чёткой границей, единственная точка
политики передачи данных провайдерам и прайс-листа. Граница модуля
инкапсулирует доступ к ключам, но не изолирует полномочия: это задача
прав исполнения и хранилища секретов на уровнях 4–5.

Сравнить LiteLLM как библиотеку (Python SDK внутри генератора) и собственный
небольшой роутер. Вариант LiteLLM Proxy Server как отдельного сервиса
из сравнения исключён решением владельца 2026-09-11. На вводной странице
LiteLLM документированы общий интерфейс для API моделей, повторные запросы,
переключение между сервисами и учёт использования. Это пока не подтверждает
совместимость с нужными нам маршрутами изображений Яндекса и NanoGPT.
**Проверяемое требование к библиотеке (владелец, 2026-09-11):** библиотека
роутера и вложенные в неё SDK провайдеров не выполняют скрытых повторных
платных вызовов и не переключают провайдера сами. Решение о новом вызове
принимает исполнитель генератора по ADR-0011, каждая попытка платного
вызова — отдельный `ProviderCall`; проверка состояния и скачивание
результата относятся к ней (уточнение 2026-09-14). Документация LiteLLM описывает настраиваемые `num_retries`
и `fallbacks` ([reliable completions](https://docs.litellm.ai/docs/completion/reliable_completions)),
но это не доказывает их поведение для нужных методов изображений.
Проверять всю цепочку до HTTP-клиента на зафиксированных версиях
зависимостей.

## Что исследовать

| Область | Вопрос исследования |
| --- | --- |
| Подготовка задания | Текстовые запросы, режимы рассуждений, структурированный результат и ограничения модели |
| Создание изображения | Поддержка конкретных API, параметры, форматы результата, ожидание и ошибки |
| Правки | Входной оригинал, пользовательская загрузка, сохранение композиции, поддержка маски при наличии |
| Выбор маршрута | Соответствие возможностей модели операции, доступность, качество, задержка и стоимость |
| Сбои | Ограничения частоты, таймаут, неизвестный исход, идентификатор внешней операции, возможность проверки результата. По ADR-0011 §3 способ сверки исхода — обязательное свойство контракта каждого маршрута, включая ветку «проверить нельзя» для синхронных API |
| Повторы | Какие ошибки допускают повтор или другой сервис без риска скрытого двойного вызова. По ADR-0011 §3 повтор только после достоверного исхода; число вызовов и допускающие повтор ошибки задаёт контракт маршрута |
| Данные | Что уходит в каждый сервис, где обрабатывается и сохраняется, как отключается логирование и удаляются копии |
| Учёт | Что провайдер сообщает для заполнения «Расхода провайдера» (ADR-0010): структура учёта уже задана ADR-0010/0011, прайс-лист для расчётной стоимости ведёт генератор с `tariff_version` (решение владельца 2026-09-11) |
| Эксплуатация | Зависимости, версии, лицензия выбранного варианта, обновления, хранение настроек и диагностика |

Проверить отдельно создание по тексту и работу с изображением. Совместимость
с одним текстовым API не доказывает совместимость всех методов.
Не добавлять автоматическое переключение в другой сервис при неизвестном
исходе оплачиваемого запроса. Маршрут не должен обходить правила доступа
к загруженному файлу, его удаление или выбранные ограничения передачи данных.

## Результат трека

- Матрица подтверждённых возможностей по версиям библиотек, API и моделей.
- Сравнение LiteLLM SDK и собственного роутера на наших операциях
  (LiteLLM Proxy исключён решением владельца 2026-09-11).
- Предложенный интерфейс между генератором и роутером (внутренний для
  генератора; backend с роутером не связан — обмен идёт через `SubmitJob`
  и `Result` по ADR-0011).
- Правила ошибок, повторов, выбора сервиса и учёта расходов.
- Проверочные задания для эскизов и последовательных правок с оценкой мастером.
- Рекомендация с обоснованием и отдельный ADR о выбранном решении.

Платные прогоны и подключение ключей требуют согласованной программы проверки;
в этом треке они пока не выполнены. Продукт продолжаем проектировать параллельно.
