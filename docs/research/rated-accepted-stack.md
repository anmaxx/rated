# Rated — принятый технологический стек

Дата фиксации: **13 сентября 2026 года**.

Статус: **принятые в обсуждении решения**. Открытые вопросы перечислены отдельно и не являются частью утверждённого выбора.

## 1. Назначение документа

Документ фиксирует технологии Rated, границы их применения и основания выбора. Он объединяет результаты обсуждения стека и последнее решение о хранении сессий в PostgreSQL.

Rated разрабатывается полностью с участием AI-агентов, которые пишут и изменяют код. Поэтому при реализации важны однозначные правила, проверяемые изменения и соответствие поведения принятым архитектурным решениям. Сам по себе выбор библиотеки не доказывает корректность транзакций, списаний или восстановления после сбоя.

Документ не меняет бизнес-правила существующих ADR. Два технологических решения конфликтовали с принятыми ADR и внесены в них 13 сентября 2026 года: своя установка PostgreSQL — в [ADR-0013](../adr/0013-databases-and-transactions.md), Yandex Message Queue и карантин как таблица в базе — в [ADR-0014](../adr/0014-background-processes.md) и [ADR-0011](../adr/0011-generation-execution-contract.md). Код по этому стеку ещё не написан.

## 2. Принятые решения

| --- | --- | --- |
| Backend | **TypeScript, Node.js, NestJS** | API для frontend, доступ, пользователи, эскизы и версии, задания, учёт попыток, принятие результатов и удаление |

| Внутренний стек генератора | **SQLAlchemy Core + Psycopg 3, Alembic, Pydantic, `asyncio`** | База, миграции, настройки и модели проверенных данных генератора; условия применения — §4 |

| Хранение файлов | **Yandex Object Storage** | Клиентские оригиналы, предпросмотры и временная передача файлов |
| Клиент Object Storage генератора | **Boto3, отдельный клиент и пул потоков для файлов** | `get_object` из `transfer/input/`, `put_object` в `transfer/output/` (решение 14 сентября 2026 года, §6) |
| Клиент Object Storage backend | **AWS SDK for JavaScript v3, пакет `@aws-sdk/client-s3`, внутри модуля хранения NestJS** | Проверка и приём результата, загрузки клиента, предпросмотры, серверное копирование, удаление и обход префиксов при очистке (решение 15 сентября 2026 года, §3) |

## 3. Backend: NestJS и PostgreSQL

NestJS задаёт структуру приложения и разделение на модули по обязанностям. Модуль приложения не означает отдельный сетевой сервис. Границы кода должны соответствовать операциям Rated: управление сессиями, работа с эскизами, учёт попыток, выполнение заданий и удаление.

Kysely используется для построения запросов, близких к SQL, с проверкой типов средствами TypeScript. Драйвер `pg` обеспечивает подключение к PostgreSQL. Prisma и Drizzle рассматривались как допустимые альтернативы; в выбранный состав они не входят.

Основание выбора Kysely — возможность явно выразить принятые правила базы: порядок блокировок, условные обновления, резервирование попытки и запись на отправку в одной транзакции. Ручные SQL-фрагменты допустимы там, где они делают операцию понятнее. Корректность таких фрагментов проверяется отдельно от проверки типов.

Все действия одной транзакции используют один объект транзакции, включая вызовы вспомогательных методов. Создание задания, резерв и запись на отправку фиксируются вместе. Копирование файлов и внешние вызовы выполняются вне транзакций базы в порядке, установленном контрактом выполнения.

Изменения структуры PostgreSQL оформляются проверяемыми миграциями. Типы для запросов должны соответствовать фактической схеме после миграций. Конкретный инструмент запуска миграций и генерации типов остаётся выбором реализации.

**Проверка сообщений очереди** (решение владельца 2026-09-15, ADR-0011 §6 «Описание сообщений»). Сообщения от генератора backend проверяет по общим схемам JSON Schema 2020-12 валидатором **Ajv2020** (`ajv` 8.20) с **`ajv-formats`** (3.0) в собственном модуле приёма, а не `class-validator`/`ValidationPipe` NestJS: при contract-first второй источник истины в декораторах классов недопустим. Параметры, измеренные пробой ([отчёт](2026-09-15-message-schemas-probe.md) §7): `strict: true`, `strictRequired: false` (не видит свойства за `$ref`/`allOf`, корни документа так составлены), `allowUnionTypes: true` (только ради `assembled_request`), `coerceTypes`/`useDefaults`/`removeAdditional` — `false`, `validateFormats: true`; `$anchor` и слово классификации регистрируются через `addKeyword`, иначе строгий режим отказывает компилировать; схемы регистрируются по `$id`. Одинаковость проверки времени и UUID с генератором обеспечивает не `ajv-formats` (его `date-time` и `uuid` шире, чем у Python: принимал `+0300`, `+03`, `:60`, `urn:uuid:`), а общий профиль шаблоном в схеме (ADR-0011 §6, замечание владельца 2026-09-15, P1). Типы TypeScript из тех же схем — `json-schema-to-typescript` 16 через API с локальным резолвером `$id`-ссылок; они слабее схем (открытые, теряют `required`) и служат компилятору, а не проверке.

### Клиент Object Storage в backend

**Принято владельцем проекта 15 сентября 2026 года** вместе с условиями ниже. Backend обращается к Yandex Object Storage через AWS SDK for JavaScript v3, пакет `@aws-sdk/client-s3`. Yandex документирует этот пакет и настройку своего адреса хранилища: endpoint `https://storage.yandexcloud.net`, регион `ru-central1` ([документация Yandex](https://yandex.cloud/en/docs/storage/tools/aws-sdk-js)). Клиент размещается внутри модуля хранения NestJS; остальной backend обращается к операциям этого модуля. Решения о принятии результата, списании и удалении остаются в соответствующих обработчиках (ADR-0011 §4, ADR-0014 §2).

| Операция | Для чего нужна Rated |
| --- | --- |
| `GetObject` | Проверка результата и кандидата результата в `transfer/output/`; чтение оригиналов и предпросмотров для выдачи через backend |
| `PutObject` | Сохранение загрузок клиента и подготовленных предпросмотров |
| `CopyObject` | Серверное копирование исходника в `transfer/input/` (ADR-0011 §1) и принятого результата в клиентскую область (ADR-0011 §4, шаг 3) |
| `DeleteObject` | Удаление конкретного объекта |
| `ListObjectsV2` | Обход префиксов при очистке (ADR-0014 §4) с обработкой всех страниц списка: Yandex отдаёт до 1000 ключей на страницу, продолжение — по `NextContinuationToken` при `IsTruncated` ([ListObjectsV2](https://yandex.cloud/en/docs/storage/s3/api-ref/bucket/listobjects)) |

Права по областям — таблица ADR-0010 «Файлы»; набор операций ей соответствует, включая `LIST` для backend: перечислению отвечает отдельное разрешение `s3:ListBucket` на бакет, право читать объекты его не заменяет ([действия Yandex Object Storage](https://yandex.cloud/en/docs/storage/s3/api-ref/policy/actions); замечание владельца 2026-09-15, P2). Backend получает право перечислять используемые префиксы в соответствующих бакетах, генератору оно не требуется, и проверка совместимости выполняет обход именно с рабочими правами backend. `DeleteObjects` (пакетное удаление) в набор не входит: у операций с обязательной контрольной суммой поведение клиента под настройками ниже не проверялось. Составная загрузка и `@aws-sdk/lib-storage` в первом выпуске не используются, как и у генератора (§6). Серверное копирование ограничено 5 ГБ одним запросом ([CopyObject](https://yandex.cloud/en/docs/storage/s3/api-ref/object/copy)).

**Конфигурация клиента.** Версии `@aws-sdk/client-s3` и `@smithy/node-http-handler` закрепляются точно, без каретки: пример Yandex указывает `"^3.726.1"`, а с 3.729.0 клиент по умолчанию добавляет контрольную сумму CRC32 ко всем `Put` и проверяет суммы при `Get` ([объявление AWS](https://github.com/aws/aws-sdk-js-v3/issues/6810)); каретка пропускает эту границу, поддержку CRC32 Yandex Object Storage не документирует. Совместимость проверяется именно с закреплённой конфигурацией:

```ts
maxAttempts: 1,
requestChecksumCalculation: "WHEN_REQUIRED",
responseChecksumValidation: "WHEN_REQUIRED",
requestHandler: new NodeHttpHandler({
  connectionTimeout, requestTimeout, socketTimeout, // явные значения
  throwOnRequestTimeout: true,
  httpsAgent: new Agent({ maxSockets }),
}),
```

**Условия применения.**

1. **Параллельные передачи и ожидание ограничены.** Сетевые обращения SDK асинхронны; ограничение действует на работающие и ожидающие операции, и его пишет модуль хранения — SDK такого ограничителя не даёт: единственный предел в обработчике — `maxSockets`, по умолчанию 50 на клиент, сверх него запросы встают в очередь без предела ([CLIENTS.md](https://github.com/aws/aws-sdk-js-v3/blob/main/supplemental-docs/CLIENTS.md)). Сроки задаются явно, все три: `connectionTimeout`, `requestTimeout` и `socketTimeout` по умолчанию равны 0, то есть отключены, а `requestTimeout` при срабатывании только пишет предупреждение и становится ошибкой лишь с `throwOnRequestTimeout: true` (исходники `@smithy/node-http-handler` 4.12.1, установленного вместе с `@aws-sdk/client-s3` 3.1132.0, и ветки main, прочитаны 2026-09-15; поведение проверяется на закреплённой версии). Чтение `GetObject` занимает сокет до конца потока или его закрытия: получение заголовков скачивание не завершает ([потоковые ответы](https://docs.aws.amazon.com/sdk-for-javascript/v3/developer-guide/migrate-s3.html)). Выдача изображений идёт через backend (ADR-0010), поэтому при обрыве соединения клиентом поток `Body` уничтожается явно; иначе сокет остаётся занятым.
   **Общий срок операции задаёт модуль хранения** (замечание владельца 2026-09-15, P1): три настройки SDK полное время передачи не ограничивают. `requestTimeout` снимается с получением ответа, а `socketTimeout` ограничивает простой — поступающие порции тела его не нарушают. Наблюдение владельца и повтор 15 сентября на `@aws-sdk/client-s3` 3.1132.0 и `@smithy/node-http-handler` 4.12.1: при `requestTimeout = 150 мс` и `socketTimeout = 150 мс` заголовки пришли через 20–80 мс, тело из десяти порций по 50 мс дочитано через 523–535 мс без ошибки. Срок отсчитывается от постановки операции в ожидание до полного чтения либо закрытия тела, включая разбор ответа `COPY`. По истечении модуль отменяет именно этот запрос и закрывает его потоки; занятый слот освобождается после их фактического завершения, а не по истечении срока. Средство отмены — `abortSignal` в параметрах `send` и `Body.destroy()` для уже полученного потока: в том же наблюдении сигнал, поданный через 150 мс во время чтения тела, завершил операцию через 154 мс ошибкой `aborted`, а `destroy()` — через 217 мс. Три настройки SDK остаются дополнительными ограничениями.
2. **Повторами управляет backend.** `maxAttempts: 1` отключает внутренние повторы ([`maxAttempts`](https://docs.aws.amazon.com/sdk-for-javascript/v3/developer-guide/migrate-client-constructors.html)). Повтор выполняет обработчик Rated по правилам своего задания и оставшемуся времени. Для повторного `PUT` открывается новый поток тех же сохранённых байтов: тело HTTP-запроса повторно открыть нельзя, поэтому загрузка клиента сохраняется backend до `PUT`. Так число попыток и их сроки не складываются из двух механизмов.
   **Временная копия у backend** (замечание владельца 2026-09-15, P3) — тело загрузки клиента и подготовленный предпросмотр до подтверждения `PUT` — это копия клиентских данных со своими правилами, как рабочие файлы генератора (ADR-0010 «Файлы», ADR-0014 §3). Она учитывается в ограничениях памяти или диска; живёт, пока разрешены повторы `PUT` — у загрузки до ответа на `POST /uploads` (ADR-0012 §7), у предпросмотра до фиксации готовности (ADR-0014 §2); освобождается после успеха, окончательной ошибки или отмены владельцем операции — обработчиком запроса или задачи, после фактического окончания использующих её операций. Копия на диске лежит в каталоге запуска процесса; остатки после падения backend убирает сборщик остатков при запуске и периодически (строка «Временная копия для `PUT`» в ADR-0014 §2). Без этого реализация с временными файлами оставила бы клиентские данные вне описанного механизма удаления.
3. **Принятые правила целостности сохраняются.** Оба режима дополнительных контрольных сумм — `WHEN_REQUIRED` ([справочник AWS](https://docs.aws.amazon.com/sdkref/latest/guide/feature-dataintegrity.html)); под ним клиент не добавляет к `PutObject` ничего, если `ChecksumAlgorithm` не передан (исходники SDK, `getChecksumAlgorithmForRequest`). Для `PUT` передаются `ContentMD5`, `ContentLength` и `ContentType` подготовленного файла; Yandex Object Storage проверяет `Content-MD5` и при несовпадении отвечает ошибкой ([PutObject](https://yandex.cloud/en/docs/storage/s3/api-ref/object/upload)). Проверка SHA-256 по дескриптору остаётся обязанностью Rated. Наблюдение 15 сентября на `@aws-sdk/client-s3` 3.1132.0 без сети, тело из буфера: с умолчаниями `PutObject` отправляет и `Content-MD5`, и `x-amz-checksum-crc32`; с настройками выше — только `Content-MD5`, `Content-Length`, `Content-Type`, а `X-Amz-Content-SHA256` равен хешу тела, в отличие от boto3 с `UNSIGNED-PAYLOAD` (§6). Для потокового тела не наблюдалось.
4. **Завершение запроса и подтверждение операции различаются.** Копирование подтверждено после успешного разбора полного ответа. В S3 ответ `CopyObject` с HTTP 200 может содержать ошибку ([контракт CopyObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CopyObject.html)); в SDK за это отвечает `throw200ExceptionsMiddleware`: тело 2xx читается целиком, пустое тело у `CopyObject` — исключение `InternalError`, тело с `</Error>` в конце — статус 503. Наблюдение 15 сентября на 3.1132.0: оба случая дают исключение с `httpStatusCode` 503; при `maxAttempts: 1` оно доходит до обработчика Rated. Потеря ответа оставляет исход записи неизвестным и обрабатывается принятыми правилами повторов (ADR-0011 §4: шаги до фиксации повторяемы, ключ выводится из `job_id`). Yandex не блокирует объект на запись и принимает параллельные копирования в один ключ — это допущение ADR-0011 §4 «Очистка объектов без принятой версии».
5. **Общий контракт проверяется на обоих хранилищах** — Yandex Object Storage и локальном MinIO по ADR-0010 «Файлы»; строка о локальном хранилище в §7 остаётся открытой. Проверяются чтение, запись, серверное копирование, удаление и полный обход префикса; отдельно — неверная контрольная сумма, обрыв передачи и потеря подтверждения. Проверяется закреплённая конфигурация. Документированная поддержка SDK Яндексом эти проверки не заменяет.

Рассмотренные альтернативы: AWS SDK for JavaScript v2 — поддержка прекращена 8 сентября 2025 года ([объявление](https://aws.amazon.com/blogs/developer/announcing-end-of-support-for-aws-sdk-for-javascript-v2/)); `minio` JS SDK — Yandex его не документирует; прямой HTTP с подписью SigV4 — своя реализация подписи и обработки ошибки внутри ответа 200.

### Обработка изображений в backend

**Принято владельцем проекта 15 сентября 2026 года** вместе с условиями ниже. Backend обрабатывает изображения через sharp: prebuilt-сборка с libvips 8.18.6 и выше, Node 20.9 и выше (sharp 0.35.4, `package.json`). Основание — исследование от 11 сентября ([второе мнение по стеку](2026-09-11-stack-second-opinion.md), §4.5): самые строгие умолчания для недоверенного ввода — `failOn: 'warning'`, `metadata()` до декодирования, `limitInputPixels`, плитка знака одной опцией `composite`. FFmpeg отклонён: второй процесс со своим контрактом и неустановленные EXIF и ICC; остаётся кандидатом только при появлении видео.

| Операция | Для чего нужна Rated |
| --- | --- |
| Проверка загрузки | `POST /uploads`: тип по содержимому, размеры, число пикселей, декодируемость — синхронно в запросе (ADR-0012 §7, ADR-0007) |
| Очистка принятой загрузки | Принятый файл сохраняется перекодированным: без метаданных (EXIF, координаты, прочие блоки), повёрнутым по ориентации EXIF (решение владельца 2026-09-15) |
| Предпросмотр | Ориентация, масштаб, водяной знак в пикселях, кодирование — фоновая задача из оригинала в клиентской области (ADR-0003, ADR-0014 §2) |

**Условия применения.**

1. **Проверка — полное декодирование, не заголовок.** ADR-0012 §7 требует декодировать. Сначала `metadata()` для дешёвого отказа по типу и размерам, затем операция вывода с `failOn: 'warning'` — умолчание sharp, оставить явно.
2. **Пределы — параметр Rated, не умолчания библиотеки.** `limitInputPixels` по умолчанию 268402689 и доверяет размерам из метаданных; число пикселей и байтов задаются параметром уровня 4 и проверяются на обеих сторонах.
3. **Список форматов — явный перечень, одинаковый у backend и генератора**, а не «что декодирует загрузчик»: сборки libvips у sharp и у pyvips-binary разные. **HEIC в первом выпуске не принимается: `415 unsupported_media_type`** (решение владельца 2026-09-15). Prebuilt sharp HEIC не декодирует; сборка libvips с HEVC на обеих сторонах отклонена. Состав перечня — параметр уровня 4.
4. **Очистка загрузки — перекодирование.** Sharp не переписывает файл без перекодирования, поэтому принятая загрузка — новый файл: метаданные удалены (умолчание вывода sharp), поворот по EXIF применён к пикселям (`autoOrient()` первым в конвейере), `width` и `height` в ответе `201` и в записи — размеры сохранённого файла. Для JPEG это повторное сжатие с потерями; параметр качества — уровень 4. Генератор и мастер получают очищенную копию; дескриптор исходника в `SubmitJob` (ADR-0011 §1) считается по ней. Следствие перекодирования выведено мной.
5. **Параллельность ограничивает модуль.** Sharp выполняется в пуле libuv: по умолчанию четыре потока, общих с файловыми операциями, DNS и сжатием ([производительность sharp](https://sharp.pixelplumbing.com/performance/)). Число одновременных проверок и предпросмотров ограничивает модуль по образцу модуля хранения; `UV_THREADPOOL_SIZE` и `sharp.cache` (умолчания: 50 МБ, 20 файлов, 100 операций) задаются явно.
6. **Вход — временная копия, выход — буфер.** Вход — временная копия для `PUT` (§3, клиент хранилища, условие 2); результат `toBuffer` даёт `ContentMD5`, `ContentLength` и `ContentType` для `PUT`.
7. **Одна версия libvips на обеих сторонах.** Минор закреплён общим для sharp и pyvips-binary; тестовая обвязка сравнивает версии, которые sharp и pyvips сообщают во время выполнения.

Не проверено: метаданные предпросмотра — sharp по умолчанию удаляет их на выходе, так что предпросмотр EXIF не несёт; ICC-профиль при этом тоже удаляется, а выход приводится к sRGB — сохранение профиля (`keepIccProfile()`) решается при выборе параметров предпросмотра.

## 4. Генератор: Python

Генератор работает отдельным приложением со своей базой и собственными правами. Backend и генератор обмениваются сообщениями и не читают таблицы друг друга. Совпадение СУБД не означает совместное владение данными.

Python выбран для непосредственного использования библиотек работы с моделями и провайдерами, включая возможность встроить LiteLLM SDK. Это преимущество относится к обязанностям генератора и не требует перевода backend на Python.

Генератор отвечает за:

- надёжное сохранение задания до подтверждения сообщения очереди;
- захват работы с арендой и восстановление по сохранённому состоянию;
- подготовку запроса и вызовы провайдеров;
- создание записи `ProviderCall` в состоянии `pending` **до** каждого платного вызова — в одной транзакции с проверкой барьера стирания и остатка времени до `deadline_at` (ADR-0011 §2, §5; ADR-0013 §7);
- сверку неизвестного исхода и соблюдение предельного срока;
- получение и передачу файла результата;
- стирание клиентского текста и защиту от его повторной записи;
- сохранение результата вместе с записью на отправку.

**LiteLLM остаётся кандидатом на встроенный роутер.** Python принят независимо от окончательного выбора роутера. LiteLLM не утверждён как обязательная или единственная интеграция со всеми провайдерами. Для возможностей, которые он не покрывает, допускается использование SDK провайдера или прямого HTTP-запроса.

Каждый маршрут проверяется как сочетание провайдера, модели и операции: генерация, доработка по исходнику, проверка состояния и получение расхода. Работа с маской отложена во вторую итерацию ([second-iteration.md](../design/second-iteration.md)) и в проверку маршрутов первого выпуска не входит. Наличие Python SDK само по себе не подтверждает поддержку всего маршрута.

Встроенные повторы и переключения между провайдерами в LiteLLM и SDK провайдеров выключены: скрытый повтор платного вызова внутри библиотеки нельзя записать заранее. Каждая новая попытка платного вызова модели получает отдельный `ProviderCall` до отправки. Проверка состояния внешней операции и скачивание её результата относятся к существующему вызову и не создают новую попытку генерации. Повторы и переключения платных вызовов выполняет только код Rated по правилам ADR-0011. Потеря ответа не разрешает новый платный вызов. Сырое тело ошибки провайдера, в том числе текст из исключений библиотеки, в `ProviderCall` не попадает: хранятся код ошибки, HTTP status и очищенное сообщение (ADR-0011 §6).

### Внутренний стек генератора

**Принято владельцем проекта 14 сентября 2026 года** вместе с условиями ниже.

| Компонент | Назначение в Rated |
| --- | --- |
| **SQLAlchemy Core** + драйвер **Psycopg 3** | Построение запросов и управление транзакциями PostgreSQL генератора; асинхронное подключение `postgresql+psycopg` |
| **Alembic** | Миграции только базы генератора; база backend остаётся у backend |
| **Pydantic** | Настройки (`pydantic-settings`) и представление проверенных данных моделями, сгенерированными из общих схем; проверку входящих сообщений выполняет `jsonschema` (условия ниже, уточнение 2026-09-15) |
| **`asyncio`** | Одновременное ожидание провайдеров, очереди и базы внутри процесса; восстановление после перезапуска держат PostgreSQL и ADR-0014 |

Веб-фреймворк не выбран: обмен с backend идёт сообщениями (ADR-0011). Принятие Python не означает принятия FastAPI, Django или Celery.

**Условия для базы.**

- Повторяется только взаимоблокировка `40P01` (ADR-0013 «Повтор транзакций»): один общий помощник распознаёт её по `DBAPIError.orig` — `orig.diag.sqlstate == "40P01"` или класс `psycopg.errors.lookup("40P01")`. Остальные ошибки не повторяются.
- Транзакция и взятое из пула соединение не удерживаются через `await` внешней операции — вызова провайдера, записи в Object Storage, отправки в очередь, проверки файла. Порядок: проверили условия и записали `ProviderCall` → зафиксировали → внешний вызов → отдельной транзакцией сохранили ответ (ADR-0013 §7).
- Получение соединения выполняется асинхронно с ограничением времени ожидания. Размер пула определяется одновременными операциями базы и потребностями фоновых задач, включая своевременное продление аренды. Число соединений не обязано равняться числу выполняющихся генераций: во время ожидания провайдера соединение освобождено ([пул SQLAlchemy для asyncio](https://docs.sqlalchemy.org/en/20/core/pooling.html#sqlalchemy.pool.AsyncAdaptedQueuePool)).

**Условия для `asyncio`.**

- Синхронная работа — синхронные SDK, Boto3, хеширование и разбор изображений — выполняется вне цикла событий. Выносится вся единица синхронной работы вместе с её собственными ресурсами, а не только блокирующий вызов. Асинхронные соединения SQLAlchemy в потоки не передаются.
- Пулы потоков выделенные и ограниченные по назначению (пул очереди — §6); место в пуле освобождается по фактическому завершению вызова в потоке, а не по отмене ожидания в `asyncio`.
- Продление аренды — отдельная задача. Продление или любая запись исполнителя, обновившая ноль строк, означает потерю аренды: исполнитель прекращает запись (ADR-0013 §7). Уже отправленный платный вызов остаётся в `pending` и разбирается восстановлением (ADR-0011 §2). Основание: заблокированный цикл не продлевает аренду, и восстановление превращает рабочий вызов в ложный `outcome_unknown`.

**Условия для миграций.**

- Автоматически созданная миграция — заготовка: агент проверяет и дополняет её, автогенерация Alembic обнаруживает не все изменения ([документация](https://alembic.sqlalchemy.org/en/latest/autogenerate.html)).
- В CI миграции применяются к чистой PostgreSQL, затем выполняется `alembic check`. Обнаруженное расхождение останавливает сборку. `alembic check` сравнивает описание таблиц с подключённой базой и наследует ограничения автогенерации; содержимое файлов миграций он не проверяет. Ограничения и объекты, не охваченные автогенерацией, проверяются отдельно ([документация](https://alembic.sqlalchemy.org/en/latest/autogenerate.html#running-alembic-check-to-test-for-new-upgrade-operations)).
- Миграции запускаются отдельным шагом развёртывания, а не при старте процесса: экземпляров генератора может быть несколько (ADR-0014 §5).

**Условия для проверки сообщений и документов** (уточнены 2026-09-15 по решению владельца: общие схемы JSON Schema 2020-12, ADR-0011 §6; проба — [отчёт](2026-09-15-message-schemas-probe.md)).

- Исходное сообщение проверяется по общей схеме валидатором **`jsonschema`** (4.26) — `Draft202012Validator` с реестром схем по `$id` (`referencing`) и **явно включённой проверкой форматов** (`format_checker=Draft202012Validator.FORMAT_CHECKER`). Формат `date-time` проверяется только при установленном **`rfc3339-validator`** — обязательная зависимость генератора, не опция: форму строки отсекает шаблон профиля в схеме, но календарно невозможную дату (30 февраля) без проверяющего механизма формата пропускают оба (измерено; [документация](https://python-jsonschema.readthedocs.io/en/stable/validate/#validating-formats)).
- Приём в два шага: конверт (`message_type`, `contract_version`, `job_id`, у Result — `revision`) проверяется по схеме конверта до проверки версии; неизвестная `contract_version` уходит в таблицу карантина, а не превращается в ошибку проверки; известная — тело проверяется по схеме версии (ADR-0011 §6).
- Тело сообщения открыто: новое необязательное поле версию не меняет и в документ `input` не переносится — отображение копирует только известные ключи (ADR-0013 §2).
- Документ `input` в `jsonb` проверяется по закрытой схеме своей версии с корнем «до» или «после» стирания; у каждого поля — слово классификации, которое код стирания читает из сырого файла схемы (ADR-0013 §2, §6).
- Временные метки сообщений — строки RFC 3339 с обязательным смещением; отправители формируют UTC с `Z`, числа, числовые строки и даты без смещения отклоняются (контракт ADR-0011 §6, решение владельца 2026-09-14). Это обеспечивает проверка формата и профиля по схеме, а не модель: на Pydantic 2.13.5 `AwareDatetime` при `strict=True` отклоняет число и дату без пояса, но принимает строку `"1757939400"` как Unix-время (измерено на сгенерированной модели; наблюдение владельца); без строгого режима, в котором модели теперь генерируются, она принимает и число как Unix-время. Ворота в обоих режимах — схема. Для UUID строгий режим в JSON не действует ([строгий режим](https://pydantic.dev/docs/validation/latest/concepts/strict_mode/)).
- Модели Pydantic — не источник схемы и не ворота. Они генерируются из общих схем **`datamodel-code-generator`** (0.81): `--output-model-type pydantic_v2.BaseModel --field-extra-keys <слово классификации> --output-datetime-class AwareDatetime --formatters ruff-format --disable-timestamp --http-local-ref-path <зеркало> --no-allow-remote-refs`; зеркало `$id`-ссылок пересоздаётся перед каждой генерацией; **Ruff** закреплён в зависимостях (`--formatters ruff-format` без него падает). `extra="forbid"` у документа выводится из `unevaluatedProperties: false`, сообщения остаются с `extra="ignore"`. Измерено, чего модель не гарантирует: запрет поля через `false`, `if`/`then`, закрытость вложенных объектов документа, форму «после стирания», карантин неизвестной версии.
- **Модель не строже схемы** (замечание владельца 2026-09-15, P3): `--strict-types` не задаётся — JSON не различает `7` и `7.0`, схема принимает `7.0` как `integer`, строгая модель отклоняла. Всё, что приняла схема, модель обязана принять; проверяется на всём корпусе фикстур.
- **Сериализация из модели** — только `model_dump(mode="json", exclude_unset=True)`, и результат снова проходит ту же схему (проверяется на всём корпусе). Вызов по умолчанию восстанавливает стёртые ключи документа как `null`, и остаток перестаёт проходить корень «после стирания» (замечание владельца 2026-09-15, P3) — запрещён. Поле, участвующее в условии схемы (`revision` конверта), объявляется в `properties`, иначе генератор его не переносит и сериализация его теряет.
- Проверки пробы и будущие проверки контракта в CI завершаются ненулевым кодом при любом несовпадении, ошибке линтера классификации, нарушении цепочки «схема → модель → сериализация → схема» и ошибке генерации (замечание владельца 2026-09-15, P4).

### Обработка изображений в генераторе

**Принято владельцем проекта 15 сентября 2026 года.** Генератор проверяет результат провайдера через pyvips 3.2.0 с `pyvips[binary]` — wheel pyvips-binary 8.18.6, тот же libvips, что у sharp в backend. Задача генератора — только проверка: декодировать результат, установить тип по содержимому и размеры (ADR-0011 §6, решение S-6). Обработки изображений у генератора в первом выпуске нет; подготовка исходника для модели решается при проверке маршрутов первого выпуска (§7).

Основание выбора — не скорость, а решение S-6 и условие 6 клиента хранилища (§6): одно правило определения типа на обеих сторонах, проверяемое общим набором файлов. Одна семья декодеров сокращает расхождения на граничных файлах, которые превращались бы в `result_file_mismatch`; Pillow была бы второй семьёй. Совпадение версии libvips расхождений не исключает: состав и версии кодеков у сборок sharp и pyvips-binary разные (условие 6 ниже; §3, условие 3), и совместимость подтверждает только общий набор проверочных файлов (замечание владельца 2026-09-15, P2). Цена Pillow по исследованию 11 сентября: плагин WebP выделяет холст до проверки на «бомбу», `MAX_IMAGE_PIXELS` 89478485 с ошибкой при двукратном превышении, HEIC только через pillow-heif. Формат Pillow 12.2.0 определяет по содержимому, а не по расширению: расширение имени файла лишь подгружает подходящий плагин первым, распознавание идёт проверкой первых 16 байт функцией `accept` плагина, для буфера без имени загружаются общие плагины, затем перебираются остальные ([исходник `Image.open`](https://github.com/python-pillow/Pillow/blob/12.2.0/src/PIL/Image.py#L3646), замечание владельца 2026-09-15, P2).

**Условия применения.**

1. **Строгость — в каждом вызове, проверка — полное чтение пикселей** (замечание владельца 2026-09-15, P1). Загрузчики libvips по умолчанию терпимы (`fail_on none`, [документация libvips](https://www.libvips.org/API/current/ctor.Image.jpegload.html)); `fail_on="warning"` передаётся в каждый вызов загрузчика. Открытия недостаточно: `new_from_buffer` читает только заголовок, пиксели не читаются, пока конвейер не подключён к выводу ([отложенное выполнение pyvips](https://libvips.github.io/pyvips/intro.html)). Проверено владельцем на pyvips 3.2.0 / libvips 8.18.6: обрезанный JPEG с `fail_on="warning"` открывается и возвращает размеры 256 × 192, ошибку `premature end of JPEG image` поднимает только операция, читающая пиксели (в пробе — `avg()`). Порядок проверки: заголовок и пределы (условие 3) → полное декодирование операцией, потребляющей все пиксели → дескриптор и передача результата. Проверочная операция ничего не записывает, исходные байты сохраняются без перекодирования (условие 4). У backend этот шаг выполняет операция вывода (§3, условие 1).
2. **Тип — по загрузчику, который libvips выбрал по содержимому**, не по расширению и не по заголовку провайдера (ADR-0011 §6). `media_type` дескриптора — из явного перечня форматов, общего с backend (§3, условие 3); файл вне перечня — отказ, даже если libvips его декодирует.
3. **Пределы — параметр Rated.** Размеры проверяются по заголовку до декодирования и по факту после полного чтения пикселей (условие 1); число пикселей и байтов — тот же параметр, что у backend.
4. **Ориентация не применяется.** Результат провайдера передаётся байтами без перекодирования (§6, условие 4); размеры дескриптора — как в файле. `new_from_buffer` тег ориентации не применяет, `thumbnail` применяет — для проверки нужен первый.
5. **Вся операция вне цикла `asyncio`** по условиям §4: загрузка буфера, полное чтение пикселей и вычисление размеров — одна единица работы в выделенном пуле. Поведение GIL в pyvips не проверялось; условие о пуле покрывает корректность независимо от него.
6. **Одна версия libvips с backend** (§3, условие 7): минор закреплён общим, версия сверяется обвязкой во время выполнения. Состав кодеков wheel pyvips-binary отличается от prebuilt sharp: в списке лицензий libvips-packaging есть libheif и aom, декодера HEVC нет — вывод по списку, не проверка; на перечень форматов он не влияет, HEIC отклоняет backend.

## 5. Сессии в PostgreSQL

**Хранение сессий в PostgreSQL принято владельцем проекта 13 сентября 2026 года.** Redis для хранения сессий в первом выпуске не вводится.

В cookie браузера находится случайный секрет. Backend хранит его хеш, принадлежность сессии, срок действия и сведения, необходимые для отзыва. Проверка срока выполняется при обращении: фоновое удаление просроченных записей не определяет действительность сессии.

Гостевая сессия связана с эскизами и учётом попыток. При входе присоединение гостевых данных и создание сеанса входа выполняются одной транзакцией PostgreSQL. Это сохраняет согласованность без дополнительного протокола между двумя хранилищами.

Все экземпляры backend используют общее хранилище сессий. Привязка клиента к одному экземпляру backend не требуется.

Введение Redis для иной задачи потребует отдельного основания. Оно не следует автоматически из выбора NestJS, наличия фоновых процессов или использования очереди.

## 6. Сообщения, файлы и самостоятельное размещение базы

### Доставка сообщений

Для двух направлений обмена используется Yandex Message Queue. Запись на отправку сохраняется в базе отправителя вместе с соответствующим изменением состояния; этот механизм далее называется outbox.

Очередь отвечает за доставку. После сохранения задания и подтверждения сообщения генератор сам отвечает за выполнение и восстановление. Повторная доставка является штатным случаем и не должна создавать повторное задание или списание.

Обновлённый Result может уточнять технический учёт по ревизии и идентификаторам вызовов, сохраняя уже завершённый клиентский итог. Подтверждение брокером приёма Result не означает, что backend уже принял результат.

Тип очередей, параметры повторов и срок хранения требуют настройки. Карантин сообщений неизвестной версии — таблица в базе получателя, а не очередь недоставленных сообщений брокера: сообщение в брокере нельзя стереть по `EraseGeneration` (ADR-0011 §5–6, ADR-0014). Максимальный срок хранения сообщений Yandex Message Queue — 14 дней. Требования к допустимому простою и восстановлению должны укладываться в эту границу; формула необходимого срока и последствия его превышения сохраняются по ADR-0011.

### Клиент очереди в генераторе

**Принято владельцем проекта 14 сентября 2026 года.** Генератор обращается к Yandex Message Queue через Boto3. Синхронные вызовы выполняются вне цикла `asyncio` в выделенном пуле потоков с ограничением числа работающих и ожидающих операций. Длительный опрос не блокирует отправку и подтверждение сообщений. Таймауты и повторы клиента задаются явно; отмена ожидания не считается отменой выполняющегося запроса. Совместимость используемых операций проверяется на Yandex Message Queue до выпуска.

Пул очереди отделён от загрузки изображений и блокирующих SDK провайдеров. Подтверждение полученного сообщения выполняется только после фиксации в PostgreSQL (ADR-0011 §2, §4). `aiobotocore` остаётся допустимой альтернативой; преимуществ для Rated, оправдывающих отдельную проверку его совместимости с Yandex Message Queue, не установлено. [Инструменты Message Queue](https://yandex.cloud/en/docs/message-queue/instruments/), [параметры клиента botocore](https://docs.aws.amazon.com/botocore/latest/reference/config.html).

### Файлы

Оригиналы и предпросмотры хранятся в Yandex Object Storage. PostgreSQL хранит состояние файлов, их идентификаторы и связи с заданиями и версиями.

Сохраняется разделение клиентской области и временных областей `transfer/input/` и `transfer/output/`. Права backend и генератора определяются назначением каждой области. Генератор не получает доступ к клиентской области и право удаления временных файлов.

Принятие оригинала и готовность предпросмотра остаются разными событиями. Ошибка предпросмотра не запускает повторную платную генерацию.

### Клиент Object Storage в генераторе

**Принято владельцем проекта 14 сентября 2026 года.** Генератор обращается к Yandex Object Storage через Boto3 с отдельным клиентом и отдельным пулом потоков для файлов — не общими с очередью. Yandex документирует Boto3 для Object Storage ([документация](https://yandex.cloud/en/docs/storage/tools/boto)). Клиент хранилища для backend на TypeScript — `@aws-sdk/client-s3`, §3 (решение 15 сентября 2026 года).

| Операция | Назначение |
| --- | --- |
| `get_object` | Прочитать исходник из `transfer/input/` |
| `put_object` | Записать готовый результат в `transfer/output/` |

Удаление, копирование в клиентскую область и доступ к клиентским файлам остаются у backend (ADR-0010). В первом выпуске результат загружается одним запросом `put_object`, без `upload_file` и составной загрузки: у них отдельные операции и очистка незавершённых загрузок. Лимит размера файла Rated должен укладываться в предел одного запроса Object Storage — 5 ГБ ([лимиты](https://yandex.cloud/en/docs/storage/concepts/limits)).

**Конфигурация клиента.** Версии `boto3` и `botocore` закрепляются; совместимость проверяется именно с этой конфигурацией:

```python
request_checksum_calculation="when_required"
response_checksum_validation="when_required"
```

**Целостность тела `PUT`** (решение владельца 2026-09-14). В `put_object` передаётся `ContentMD5`, рассчитанный по отправляемым байтам; Yandex Object Storage проверяет эту сумму и при несовпадении отвечает `BadDigest` ([ответы Object Storage](https://yandex.cloud/en/docs/storage/s3/api-ref/response-codes), [PutObject](https://yandex.cloud/en/docs/storage/s3/api-ref/object/upload)). SHA-256 дескриптора сохраняет свою роль — идентичность результата между сторонами. Настройки `when_required` остаются; комбинация проверяется на обоих хранилищах. Наблюдение 14 сентября на boto3 1.43.93 без сети: с этими настройками и `ContentMD5` клиент отправляет `Content-MD5`, `Content-Length` и `X-Amz-Content-SHA256: UNSIGNED-PAYLOAD` — тело не подписано, целостность тела проверяет только MD5.

Эти настройки управляют дополнительными контрольными суммами SDK. Они не заменяют проверку размера и SHA-256 по контракту ADR-0011 и сами по себе не гарантируют конкретное значение `X-Amz-Content-SHA256`: подпись тела настраивается отдельно ([конфигурация botocore](https://docs.aws.amazon.com/botocore/latest/reference/config.html)). Поддержку или неподдержку Yandex Object Storage контрольных сумм в конце запроса (CRC32 trailers) документ не утверждает. Наблюдение 14 сентября на boto3/botocore 1.43.93 без сети: по умолчанию `put_object` отправляет тело в `aws-chunked` с `x-amz-trailer: x-amz-checksum-crc32`, с настройками выше — обычный `Content-Length`.

**Условия применения.**

1. **Вся передача выполняется вне цикла `asyncio`.** Для скачивания недостаточно вынести в поток только `get_object`: он возвращает потоковое тело. Чтение порциями, подсчёт размера и хеша, запись во временный файл и закрытие ответа выполняются внутри той же рабочей операции ([потоковое тело ответа](https://docs.aws.amazon.com/botocore/latest/reference/response.html)).
2. **Память и временное место ограничены.** Размер проверяется по мере чтения, а не только по заявленным заголовкам. Незавершённый файл не передаётся модели.
3. **Файлы не занимают потоки очереди.** Пул хранения имеет собственные ограничения работающих и ожидающих операций; отмена ожидания освобождает ёмкость только после фактического завершения вызова.
4. **Повтор загрузки использует те же байты и тот же ключ.** Перед первым `put_object` в Job фиксируются `call_id`, SHA-256, размер и тип результата; каждый повтор сверяет подготовленные байты с ними, несовпадающее содержимое в тот же ключ не отправляется. Передаются исходные байты изображения провайдера без перекодирования; повторно полученные у провайдера байты тоже сверяются по хешу. Потерянный ответ на `PUT` — повтор передачи в пределах разрешённого этапа, без новой платной генерации. Генератор не перечитывает `transfer/output/`: такого права у него нет. Успешный Result публикуется после подтверждённой загрузки. Несовпадение повторно полученных байтов с дескриптором — неудачная попытка получения, повтор до `deadline_at`. Доказанная невосстановимость — `result_payload_unavailable`, исчерпание времени передачи — `result_delivery_deadline_exceeded`; при обоих кодах Result несёт кандидата результата из дескриптора, если он сохранён (ADR-0011 §2). Тип результата устанавливается декодированием изображения через pyvips (§4, решение владельца 2026-09-15), `ContentType` при `put_object` равен `media_type` дескриптора; расширение и заголовок провайдера формат не подтверждают (ADR-0011 §6, решение владельца 2026-09-14).
5. **Локальные файлы — копии клиентских данных.** Рабочий каталог — `process_instance_id / job_id / lease_generation`, `process_instance_id` уникален для каждого запуска. Файлы удаляются после последнего необходимого использования: ненужные — сразу, файл результата начатого вызова — после `result_stored_at` либо окончательного прекращения передачи; сразу при барьере стирания каталог не удаляется. Удаляет владелец каталога, при завершении задачи, ошибке или потере аренды — после фактического окончания использующих файлы операций; неудавшееся удаление повторяется, ожидание зависшей операции ограничено. Остатки подтверждённо завершившихся процессов убирает сборщик при запуске и периодически; каталог прежнего исполнителя не переиспользуется (ADR-0010 «Файлы», ADR-0014 §3, решения владельца 2026-09-14).
6. **Совместимость проверяется конкретными операциями.** Чтение исходника, загрузка результата с `ContentMD5`, передача размера, типа и контрольных сумм, определение типа общим набором файлов с ожидаемыми результатами проверяются на Yandex Object Storage и локальном хранилище. Отдельно проверяются запреты доступа, обрыв передачи и потеря ответа. Наличие общего S3 API эту проверку не заменяет. Записанный генератором объект проверяет тестовая обвязка с отдельными правами: у генератора нет `GET` на `transfer/output/`.

### PostgreSQL под собственным управлением

Установку, обновление, резервное копирование и восстановление PostgreSQL обеспечивает команда проекта. Управляемая услуга PostgreSQL облачного провайдера в принятый вариант не входит.

Backend и генератор имеют отдельные базы и роли. Это не определяет число серверов или кластеров: физическое размещение выбирается отдельно.

К готовности первого выпуска относятся резервные копии вне сервера базы и проверка восстановления. Способ развёртывания, репликация, допустимая потеря данных и время восстановления остаются эксплуатационными решениями.

## 8. Следствия для AI-driven разработки

Следующие положения определяют критерии реализации выбранного стека, а не выбор дополнительных продуктов:

- агент получает единый установленный способ выполнения транзакций, захвата работы и обработки повторов;
- изменения схемы сопровождаются миграциями и проверкой соответствия типов;
- сообщения проверяются на обеих сторонах независимо от языка реализации;
- критические сценарии проверяются на настоящем PostgreSQL, включая параллельные действия и повторы;
- проверки охватывают сохранение резерва, однократное списание, восстановление после сбоя и невозможность вернуть стёртый текст;
- изменение считается готовым после проверки поведения и соответствия ADR.

Первый рабочий сценарий реализации: принятие запроса клиента → резервирование попытки → доставка задания → вызов провайдера → принятие оригинала → подготовка предпросмотра. Это часть приложения Rated, а не сравнительный прототип стеков.
