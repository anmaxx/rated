- **Связи:** [ADR-0009](../adr/0009-system-composition.md) состав,

## 1. Метод и как читать

Документ владельца задал форму: языки backend, генератора и движка медиа
выбираются независимо, кандидаты не ранжируются, владелец компонует сам.
Это исследование держит ту же форму в разделах 3–5 и добавляет то, чего
владелец просил в этот раз: отдельное мнение с основаниями (раздел 6).

Порядок работы:

1. Из ADR-0009…0014 выписаны обязательства к стеку по десяти границам
   (около 400 пунктов со ссылками на разделы и строки ADR), затем сжаты
   до 40 проверок «да / нет / с оговоркой», которые реально отделяют одного
   кандидата от другого (раздел 2). Пункты, которые закрывает любой
   SQL-фреймворк, в список не вошли.
2. Десять независимых исследователей (Tavily MCP и Context7 MCP по
   официальной документации и исходному коду) прошли по этим проверкам:
   пять экосистем из документа владельца, роутер и API провайдеров, движки
   медиа, хранилище с очередью и сериализацией, фронт мастера и админки
   с артефактом контракта, и отдельно — фактические утверждения самого
   документа владельца.
3. Для опорных утверждений (меняющих вердикт кандидата по границе)
   задумывались две независимые линзы: скептик по первоисточнику и проверка
   привязки к обязательству ADR. Отработала только вторая, и только для
   Rust и Go; вместо первой восемь ключевых фактов перепроверены мной
   по первоисточникам. Что именно проверено и чем — раздел 8.
4. Критик полноты назвал пробелы; по ним прошёл добор.

Пометки: **[док.]** — в официальной документации или коде на указанную
версию/дату; **[вывод]** — моё следствие, в источниках не записано;
**[спорно]** — линзы разошлись; **[не установлено]** — не найдено, и это
само по себе результат. Вердикты по обязательству: *подходит*, *нужна
доработка* (обходная схема или свой код), *противоречит* (нельзя
исполнить без замены компонента), *не установлено*.

Все находки с адресами первоисточников, версиями и видом источника —
в приложении [«Источники по границам»](2026-09-11-stack-second-opinion-sources.md)
(одна строка на находку, идентификаторы вида `ts-11`, `D08` используются
и здесь).

Что исследование не делает: не измеряет производительность, память,
стоимость эксплуатации и скорость команды; не проверяет поведение
на зафиксированных версиях зависимостей — версий ещё нет; не заменяет
платные прогоны провайдеров.

## 2. Обязательства ADR по границам: различающие проверки

Полный список с номерами строк ADR — рабочий материал исследования;
здесь только то, что отделяет кандидатов. Коды (B1, A1, …) используются
в разделах 3–6.

### Граница 1. Backend: HTTP API и прикладные транзакции

- **B1.** Одна транзакция из нескольких последовательных запросов; явные
  `FOR UPDATE` / `FOR SHARE` / `FOR UPDATE SKIP LOCKED`; `RETURNING`; число
  затронутых строк после каждого `UPDATE` (ADR-0013 §1, §3–4, §7).
- **B2.** `READ COMMITTED` без скрытого повышения; никаких скрытых
  автоповторов в драйвере, пуле или ORM; SQLSTATE `40P01` виден коду;
  повтор — целой транзакцией в приложении (ADR-0013 «Повтор транзакций»).
- **B3.** Порядок запросов в транзакции задаёт код: ORM, переупорядочивающая
  INSERT/UPDATE при flush, допустима только с явным управлением
  (ADR-0013 «Сводка: транзакции» — владелец → эскиз → загрузка → задание →
  версия → файл).
- **B4.** Частичные уникальные индексы в миграциях; `INSERT … ON CONFLICT
  DO NOTHING` + чтение; условные `UPDATE … WHERE`; `jsonb` целиком, без
  запросов по содержимому (ADR-0013 §2, §5).
- **B5.** Префикс `/api/v1/`; единый конверт; один обработчик ошибок,
  оборачивающий и ошибки фреймворка (413, 415, битый JSON); `429`
  с `Retry-After`; лимитер по IP и по сессии (ADR-0012 §1, §3, §9).
- **B6.** Multipart с лимитом и синхронным декодированием в обработчике;
  потоковая выдача байтов через backend; `If-None-Match` → `304` только
  **после** авторизации (ADR-0012 §6–7).
- **B7.** `Idempotency-Key` в заголовке; хеш по канонической форме тела
  **по схеме запроса** (ADR-0012 §4; ADR-0013 §4).
- **B8.** Ответ клиенту строго после commit; обработчик не публикует
  в брокер — только outbox-строка в той же транзакции (ADR-0011 §1).

### Граница 2. Фоновые процессы backend

- **F1.** Несколько периодических циклов в одном процессе, безопасных
  в N экземплярах: `FOR UPDATE SKIP LOCKED` по индексируемым колонкам, без
  singleton-планировщика, лидера и LISTEN/NOTIFY (ADR-0014 §1, §5).
- **F2.** Захват → внешний вызов без открытой транзакции → короткая
  фиксирующая транзакция с `WHERE lease_generation = :mine` (ADR-0014 §1–2).
- **F3.** Библиотека очередей задач со своей таблицей или Redis — не
  механизм ADR-0014; допустима только как таймер тиков (ADR-0014
  «Отклонённые»).
- **F4.** Потребитель брокера: ручной ack после commit, настраиваемая
  предвыборка; издатель: подтверждение брокера до удаления outbox-строки
  (ADR-0014 §2, §5; ADR-0011 §1).
- **F5.** Клиент почты и уведомлений отдаёт три исхода: успех, ошибка,
  неизвестно (ADR-0014 §2).

### Граница 3. Генератор

- **G1.** B1–B4 для своей базы и роли; многопроцессный доступ; SQLite
  отвергнут (ADR-0013 §1, §7).
- **G2.** `ProviderCall` в `pending` под `FOR UPDATE` Job до сетевого
  вызова; вызов вне транзакции; записи после — с проверкой поколения
  аренды и барьера стирания (ADR-0013 §7; ADR-0014 §1, §3).
- **G3.** Подготовленный запрос сохраняется между `prepare` и `generate`;
  Result — полный снимок из строки Job в транзакции публикации
  (ADR-0011 §2; ADR-0013 §7).
- **G4.** Скачивание результата, декодирование для проверки, `sha256`,
  `PUT` в `transfer/output/<job_id>/…` с перезаписью (ADR-0011 §4, §6).
- **G5.** HTTP-клиент и логирование не сохраняют тела по умолчанию;
  метаданные провайдера по allowlist (ADR-0010; ADR-0011 §6).

### Граница 4. Роутер и адаптеры моделей

- **R1.** По всей цепочке до HTTP-клиента нет скрытых автоповторов для
  запросов, создающих платный вызов, и нет автопереключения провайдера
  (задание по роутеру; ADR-0011 §3; ADR-0006).
- **R2.** Адаптер отдаёт `external_request_id`, HTTP status, код ошибки,
  очищенное сообщение; доступ к исходному ответу без сохранения тела
  (ADR-0011 §6).
- **R3.** Способ сверки — свойство маршрута: асинхронная операция
  с идентификатором и опросом (сверка есть) или синхронный ответ без
  поиска (сверки не существует) (ADR-0011 §3).
- **R4.** Маршруты текст → текст, текст → изображение, изображение +
  текст → изображение; negative prompt объявленно; у Яндекса — `b64_json`
  (ADR-0010; ADR-0009; ADR-0004).
- **R5.** Usage и стоимость: единицы, сумма, валюта либо «неизвестно»;
  прайс-лист с `tariff_version` у генератора (ADR-0011 §6).
- **R6.** Ключи при инициализации; политика провайдера по данным
  описана и управляема (ADR-0009; model-router.md).

### Граница 5. Движок обработки медиа

- **M1.** Формат по содержимому; размеры и пиксели **до** полного
  декодирования; устойчивость к повреждённым файлам; различимые причины
  отказа (ADR-0012 §7).
- **M2.** Масштабирование, водяной знак, перекодирование; EXIF-ориентация;
  ICC и прозрачность; результат пригоден для перезаписи по ключу
  (ADR-0014 §2; ADR-0003).
- **M3.** Поставка: нативные зависимости, контейнер, ресурсы; для CLI —
  аргументы, таймаут, код завершения, stderr, проверка выхода.

### Граница 6. Объектное хранилище

- **S1.** Клиент с настраиваемым endpoint и path-style: `PUT`
  с `Content-Type`, потоковый `GET`, `HEAD`, серверный `CopyObject`,
  `ListObjectsV2` с пагинацией, `DeleteObjects`; `404` отличим от `5xx`;
  известны умолчания повторов (ADR-0010; ADR-0011 §1, §4; ADR-0014 §4).
- **S2.** Yandex Object Storage: `CopyObject` и лимиты, multipart, lifecycle
  по префиксу и его периодичность, политики по префиксам; MinIO: ILM
  и статус проекта; альтернативы для локального прогона (ADR-0010; ADR-0013 §1).
- **S3.** Раздельные учётные данные backend и генератора с правами по
  префиксам (ADR-0010 «Файлы»).

### Граница 7. Очередь, outbox, сериализация

- **Q1.** Формат сериализации в ADR не зафиксирован: конверт читается
  отдельно от тела; тело терпимо к неизвестным необязательным полям;
  неизвестная версия — карантин (ADR-0011 §6).
- **Q2.** Валидатор JSON Schema 2020-12 с `additionalProperties: false`
  и пометкой полей «техническое / стираемое» (ADR-0013 §2, §6).
- **Q3.** Канонизация для хеша идемпотентности — **по схеме запроса**;
  RFC 8785 канонизирует «любой JSON» и этого не делает — только нижний
  слой (ADR-0013 §4).
- **Q4.** Требования к брокеру (уровень 5, справочно): хранение до
  потребления, срок ≥ `deadline_at` + окно сверки + запас; at-least-once;
  ручной ack; предвыборка; повтор ключа не отвергается (ADR-0011).

### Граница 8. Сессии, аутентификация, права

- **A1.** Серверные сессии в **собственной** таблице; запись сеанса входа
  создаётся внутри прикладной транзакции вместе с присоединением гостя;
  `Set-Cookie` после commit. Библиотека, фиксирующая сессию в middleware
  после обработчика или в `REQUIRES_NEW`, требует обходной схемы
  (ADR-0012 §5; ADR-0013 §4).
- **A2.** Cookie без `Domain`, `Secure`, `HttpOnly`, `Path=/`,
  `SameSite=Lax`; секрет хешем; абсолютный срок у гостя и скользящий
  с потолком у входа; сессия не создаётся автоматически (ADR-0012 §2).
- **A3.** CORS с фиксированным origin, `credentials`, expose `Retry-After,
  ETag`; проверка `Origin` на всех не-GET, включая multipart без preflight
  (ADR-0012 §3).
- **A4.** Хеш пароля; одноразовый токен через `UPDATE … WHERE used_at IS
  NULL`; письмо через задание доставки (ADR-0013 §4; ADR-0014 §2).
- **A5.** Три различимые причины `401`; чужой ресурс — `404` (ADR-0012 §9).

### Граница 9. Фронт мастера и администратора, дизайн-система

- **U1.** Вторая React-сборка в той же дизайн-системе, отдаваемая
  backend'ом со своего поддомена; готовые admin-панели не подходят
  (ADR-0009, уточнение 2026-09-11).
- **U2.** Каркас админки допускает полностью свой UI поверх data provider
  и адаптер к нашему конверту.
- **U3.** Дизайн-система как общий пакет для двух сборок; сейчас —
  сгенерированный бандл внешнего проекта [вывод из репозитория].
- **U4.** Глубокие ссылки SPA при статической публикации в Object Storage
  (ADR-0009 «Следствия»).

### Граница 10. Артефакт контракта

- **C1.** Два версионированных контракта — HTTP и сообщения; генерация
  типов для языков backend, генератора и TypeScript фронта; конверт
  неизменяем, тела версионируются (ADR-0011 §6; ADR-0012 §1).
- **C2.** Замкнутые перечни; nullable и условно-обязательные поля;
  размеченные объединения (ADR-0011 §6; ADR-0012 §6, §8).
- **C3.** Одна схема запроса служит валидации, канонизации
  и классификации полей (ADR-0013 §2, §4).

## 3. Утверждения документа владельца: что подтвердилось

Из документа выписано 35 фактических утверждений о технологиях (разделы
3–7, 9–10, 12; разделы 8 и 11 вне области). Итог проверки по первоисточникам
на 2026-09-11: подтверждено 34, опровергнуто 0, неточных 0, не удалось
проверить 1 — состав зависимостей Keyframe (`server/Cargo.toml` недоступен
без авторизации). Ссылки документа на устаревшие ветки не найдены: ветка
`8.x` Adonis Session — ветка по умолчанию, формулировка Django 5.2
совпадает со `stable` и `dev`, `tonic-web` 0.14.6 — последняя.

Опорные утверждения документа и то, что добавила проверка (две последние
строки — допущения ADR-0004/0010, проверенные тем же способом):

| Утверждение документа | Статус | Что добавилось [док.] |
| --- | --- | --- |
| Adonis Session `8.x`: `commit()` после обработчика (§9) | подтверждено | `initiate(false)` → `await next()` → `commit()`; то же у `@fastify/session` (хук `onSend`) и `express-session`; см. границу 8 |
| Spring Session JDBC: `REQUIRES_NEW` по умолчанию (§9) | подтверждено | переопределяется бином `springSessionTransactionOperations`; фильтр фиксирует сессию в `finally` после обработчика |
| Django `ATOMIC_REQUESTS`: middleware вне транзакции (§9) | подтверждено | `SessionStore.save()` сам открывает вложенный `atomic`, поэтому запись сеанса можно создать из view внутри прикладной транзакции |
| Vercel AI SDK `generateImage`: есть `maxRetries` (§6) | подтверждено | по умолчанию 2; повтор на сетевых ошибках, таймаутах, 408/409/429/5xx |
| Spring AI документирует повторы image-клиента (§6) | подтверждено | `spring.ai.retry.max-attempts` = 10; на ветке `main` поверх официального `openai-java` с собственными 3 повторами — два слоя |
| Quarkus `concurrentExecution = SKIP` в пределах экземпляра (§10) | подтверждено | «not intended to work across the cluster» |
| Sharp и govips используют один libvips (§7) | подтверждено | версии libvips у них могут различаться: sharp несёт свою, govips линкуется с системной |
| LiteLLM — SDK и Proxy (§6) | подтверждено | у SDK нет адаптеров Yandex и NanoGPT: оба только как `openai/<model>` + `api_base` |
| API Яндекса отдаёт только `b64_json` (из ADR-0004, в документе не сформулировано) | подтверждено | `url` и `response_format` — «CURRENTLY NOT SUPPORTED»; специализированный Image Generation API помечен «available until September 7, 2026» (проверено мной по странице `concepts/api`); «Queries to AI Studio models are not idempotent» |
| Lifecycle Яндекса раз в сутки (из ADR-0010, в документе не сформулировано) | подтверждено | «раз в сутки по состоянию на 00:00 UTC, операция выполняется в течение нескольких часов»; `Days` ≥ 1 |

Три вещи, которых в документе нет и которые меняют картину (подробно
в разделах 4–5): асинхронный маршрут изображений Яндекса помечен доступным
только до 2026-09-07, а документированный текущий путь синхронный — на
документированных путях сверки нет ни у одного маршрута; MinIO
заархивирован; ролей Object Storage по префиксу не существует.

## 4. Технологии по границам ответственности

Внутри границы кандидаты перечислены без ранжирования. Формат строки:
технология (версия или дата) — вердикт по пункту брифа — условие
интеграции. Источник — официальная документация или код на 2026-09-11,
если не помечено иначе.

### 4.1. Backend: HTTP API и прикладные транзакции

**Слой данных (B1–B4).** Различает не язык, а наличие unit-of-work,
скрытых повторов и доступ к SQLSTATE.

- **SQLx 0.9 (Rust)** — B1–B3 *подходит* [док.]: явная `Transaction`,
  голый `BEGIN` без смены изоляции, `rows_affected()`, SQLSTATE через
  `DatabaseError::code()`; блокировки пишутся в SQL. Условие: живая база
  или каталог `.sqlx` на сборке для `query!`. Отсутствие автоповторов —
  [вывод] из API пула.
- **Diesel 2.3 (Rust)** — B1 *подходит* (`for_update().skip_locked()`,
  `for_share()`, `RETURNING`); B2 *нужна доработка* [код]:
  `DatabaseErrorInformation` не отдаёт SQLSTATE (проверено мной по
  `result.rs`), `40P01` попадает в `DatabaseErrorKind::Unknown` — правило
  «повторять только взаимоблокировку» держится лишь на тексте сообщения.
- **pg 8.23 + Kysely 0.29 (TS)** — B1–B3 *подходит* [код]: транзакция на
  одном клиенте пула, `forUpdate/forShare/skipLocked/noWait`, `returning`,
  `numUpdatedRows` (bigint), SQLSTATE в `err.code`, изоляция только по
  явному вызову, повторов в драйвере и билдере нет; порядок SQL = порядок
  кода.
- **Lucid 22 (AdonisJS)** — те же примитивы без unit-of-work; [не
  установлено], возвращает ли `.update()` число строк (это Knex).
  **MikroORM 7** — B3 *нужна доработка*: unit-of-work переупорядочивает
  и батчит при `flush()`. **NestJS 12** — слой данных не входит, вердикт
  по B1–B3 определяется выбранным драйвером.
- **pgx v5 (Go)** — B1–B2 *подходит* [код]: `begin` без изоляции,
  `CommandTag.RowsAffected()`, `PgError.Code`, цикла повторов нет
  ([вывод] по коду `Begin/Tx`). `database/sql` повторяет только
  `ErrBadConn` до двух раз и не внутри транзакции. **sqlc** — `WithTx`,
  `:execrows`, сырой SQL; разбор `SKIP LOCKED` парсером — проверить
  генерацией. **GoFrame gdb ≥ 2.10** — `LockUpdateSkipLocked()` (PR #4607,
  январь 2026), `LockShared()` диалектный — проверить, что даёт `FOR SHARE`
  на PostgreSQL; `PropagationRequiresNew` на пути входа запретить.
  **Beego ORM** — только `ForUpdate()`, остальное `Raw()`; сайт
  документации недоступен (README: «New Doc Website — unavailable»).
- **jOOQ 3.21 (JVM)** — B1–B3 *подходит* [док.]: `forUpdate().skipLocked()`,
  `forShare()`, `returningResult`, `execute()` → число строк, `sqlState()`;
  исполнение немедленное. **pgjdbc** — `autosave=never` по умолчанию,
  ничего не повторяет. **Spring** — `40P01` →
  `DeadlockLoserDataAccessException`, исходный `SQLException` в `cause`.
- **Exposed 1.5 (Kotlin)** — B2 *нужна доработка* [код]:
  `DatabaseConfig.defaultMaxAttempts = 3` (проверено мной) — блок
  `transaction { }` повторяется при любом `SQLException`; ставить 1.
  `insertReturning/updateReturning` есть; `FOR SHARE`/`SKIP LOCKED` в DSL
  [не установлено].
- **Hibernate ORM 7 / JPA** — B3 *нужна доработка* [док.]: `ActionQueue`
  при flush всегда исполняет INSERT → UPDATE → DELETE независимо от порядка
  вызовов; порядок захвата держится только явным `flush()` после каждого
  шага или native SQL. **Micronaut Data** — `FOR UPDATE` суффиксом метода,
  остальное `@Query`.
- **psycopg 3 (Python)** — *подходит* [док.]: `rowcount`, `sqlstate`
  и `DeadlockDetected`, пул без повторов операторов. **asyncpg** — *нужна
  доработка*: `execute()` возвращает строку-тег `'UPDATE 1'`, не число.
  **SQLAlchemy 2.0** — Core *подходит* (`with_for_update(read=True)` =
  `FOR SHARE`, `skip_locked`, `returning`, `rowcount`); ORM `Session` — B3
  *нужна доработка* [док.]: autoflush и порядок flush «by the unit of work
  dependency solver», не по порядку `add()`. **Django ORM 5.2** — B1
  *нужна доработка*: `select_for_update(skip_locked=, of=, no_key=)` есть,
  `FOR SHARE` нет (тикет #10088 открыт с 2009), `UPDATE … RETURNING` нет —
  сырой SQL внутри `atomic()`; `READ COMMITTED` по умолчанию, повторов нет.

**HTTP-слой (B5–B6).** Различает единый обработчик ошибок фреймворка,
лимит тела с `413` и место проверки `If-None-Match`.

- **Fastify 5.12** — *подходит* [код]: ошибки разбора тела имеют коды
  и статусы (`FST_ERR_CTP_BODY_TOO_LARGE` 413, `FST_ERR_CTP_INVALID_MEDIA_TYPE`
  415, `FST_ERR_CTP_INVALID_JSON_BODY` 400) — единый `setErrorHandler`
  (проверить на версии, что ошибки парсера проходят через него;
  в `Errors.md` описания двух JSON-ошибок перепутаны — верить `lib/errors.js`);
  `@fastify/rate-limit` 11 — ключ по IP или по сессии, `retry-after`, два
  лимита на маршрут = два `preHandler`; `@fastify/multipart` 10 —
  `limits.fileSize` → 413, `toBuffer()` в обработчике; `@fastify/etag` 6 —
  хук `onSend` после авторизации, но только для `string`/`Buffer`: для
  потока из хранилища `ETag` и `304` — руками в обработчике.
- **Axum 0.8** — *подходит с оговоркой* [док.]: `DefaultBodyLimit`,
  `Multipart` потоково; единый конверт — не глобальный обработчик,
  а оболочки `#[from_request(via(...), rejection(...))]` на каждый
  экстрактор плюс `fallback`; `tower_governor` 0.8 — лимит по IP или по
  своему ключу с `retry-after`, состояние в памяти процесса; готового
  ETag-слоя в `tower-http` 0.7 нет — что для B6 плюс; потоковая выдача
  `Body::from_stream` над `ByteStream`.
- **Echo v5** — *подходит* [док.]: `HTTPErrorHandler` единый,
  `ErrStatusRequestEntityTooLarge`/`ErrUnsupportedMediaType`, `BodyLimit`;
  встроенный лимитер в памяти процесса; `http.ServeContent` требует
  `io.ReadSeeker` — для потока `ETag` руками. **Gin** — *нужна доработка*:
  `MaxMultipartMemory` — порог буферизации, не лимит тела; единого
  обработчика ошибок нет.
- **Spring MVC** — *подходит* [док.]: `ResponseEntityExceptionHandler`
  покрывает 413/415/невалидный JSON одним `@ControllerAdvice`; условие —
  Tomcat `maxSwallowSize` (2 МиБ) ≥ лимита загрузки, иначе клиент не увидит
  413; `ShallowEtagHeaderFilter` отдаёт 304 после авторизации, но буферизует
  всё тело — на маршруте предпросмотра `ETag` в обработчике; лимитера по
  IP и сессии в MVC нет (Bucket4j не проверялся).
- **Starlette 1.6 / FastAPI** — *подходит* [док.]: `max_body_size`
  (1.6.0, 2026-08-08) и `RequestBodyLimitMiddleware` дают 413 с учётом
  multipart; `Request.form(max_part_size=…)`; конверт через переопределение
  обработчиков; `ETag` только в обработчике. **Django 5.2** — *нужна
  доработка*: `DATA_UPLOAD_MAX_MEMORY_SIZE` не покрывает файлы,
  `RequestDataTooBig` даёт 400, не 413 — свой upload handler или проверка
  `Content-Length`; `@condition(etag_func)` срабатывает до view — авторизация
  внутри `etag_func`, `ConditionalGetMiddleware` глобально не ставить.

B7–B8 (ключ идемпотентности в заголовке, ответ после commit, outbox
вместо публикации) — код приложения; различающих библиотечных фактов ни
в одной экосистеме нет.

### 4.2. Фоновые процессы backend

- **Таймеры тиков (F1) — подходят везде:** `tokio::time::interval`
  (задать `MissedTickBehavior::Delay|Skip`, чтобы не догонять пропущенные
  тики); `setInterval`/`node-cron` 4 (без `distributed: true` — это
  singleton, который ADR не требует); `@nestjs/schedule` 12 (`CronJob`
  в каждом экземпляре); `time.Ticker`/`robfig/cron` v3; `@Scheduled`
  (по умолчанию один поток — `pool.size` ≥ числа циклов); Quarkus Scheduler
  (`SKIP` локально); APScheduler 3 (`MemoryJobStore`).
- **Не механизм ADR-0014 (F3) — противоречат как владельцы состояния:**
  apalis (свои таблицы; допустим только `apalis-cron` как таймер), BullMQ
  (Redis), pg-boss (своя схема), Quartz с JDBC-JobStore, Celery
  (`acks_late = False` — ack до выполнения; единственный `beat`). **River**
  противоречит даже как таймер: периодика только у лидера через
  `river_leader` и LISTEN/NOTIFY.
- **Соединение на время I/O (F2):** `pgxpool.Tx.Commit` возвращает
  соединение сразу; `sqlx::Transaction` владеет соединением до `commit()`;
  `psycopg_pool` — три отдельных `with`. Для `@Transactional` Spring/Quarkus
  и `transaction { }` Exposed — условие «внешний I/O строго вне блока»
  [не установлено], удерживают ли они соединение на время вызова.
- **Клиент брокера (F4, справочно):** lapin 4.11 (`basic_qos`, ручной
  ack, `confirm_select`); amqplib 2.0 (`prefetch`, `noAck: false`,
  confirm-канал); aio-pika (publisher confirms по умолчанию; не использовать
  `message.process()` — он подтверждает автоматически); amqp091-go
  (`Qos`, `Confirm`, `DeferredConfirmation.Wait`); Spring AMQP (`MANUAL`,
  `prefetchCount` по умолчанию 250 — задать малым); `@aws-sdk/client-sqs`
  (`MaxNumberOfMessages`, ack = `DeleteMessage`).
- **Почта (F5):** lettre (`is_transient/is_permanent/is_timeout`), go-mail
  (`ErrSMTPDataClose` — стадия после `DATA`), `smtplib`
  (`SMTPServerDisconnected`) — трёхзначный исход «неизвестно» везде выводит
  приложение из стадии разрыва; nodemailer и `JavaMailSender` [не
  установлено].

### 4.3. Генератор

Наследует B1–B4 своей базы (те же вердикты, что в 4.1) и G2–G3 как
дисциплину кода; различающие факты — в логировании и передаче байтов.

- **G5, логирование тел по умолчанию:** SQLx пишет SQL на `DEBUG`
  (`log_statements`; попадают ли bind-параметры — проверить); httpx на
  `DEBUG` пишет заголовки ответа, тел — нет; openai-python на `main`
  логирует только `method`/`retries_taken`; LiteLLM без callback'ов наружу
  ничего не шлёт (`log_raw_request_response = False`), флаг
  `litellm.telemetry = True` без найденного потребителя [не установлено];
  Spring AI `log-prompt = false`; go-mail `SetDebugLog` пишет всю
  переписку — выключен; `tower-http TraceLayer` тел не пишет.
- **G4, скачивание и `PUT`:** aws-sdk-go-v2 требует `ContentLength` для
  потока без seek (иначе «request stream is not seekable») — `sha256`
  через `TeeReader` только при известной длине или через временный файл;
  Rust `ByteStream` и Node `Upload` потоковые. Проверка типа и размера
  результата — движками из 4.5.
- **G1, форма процесса:** `NestFactory.createApplicationContext` даёт
  контейнер без HTTP для исполнителей; в остальных экосистемах — обычный
  процесс с циклами из 4.2.

### 4.4. Роутер и адаптеры моделей

Это граница, где исследование разошлось с ожиданиями сильнее всего:
ни библиотечный роутер, ни официальный SDK по умолчанию не выполняют R1,
а сверки (R3) нет ни у одного маршрута изображений.

**Библиотечные роутеры**

- **LiteLLM Python SDK** — R4 *нужна доработка* [док.]: провайдеры
  `image_generation` — OpenAI, Azure, Google AI Studio, Vertex, Bedrock,
  Black Forest Labs, Recraft, OpenRouter, Xinference, Nscale; Yandex
  и NanoGPT только как `openai/<model>` + `api_base` (для Яндекса —
  `extra_headers` с `OpenAI-Project`). R1 *нужна доработка* [код]:
  в `OpenAIChatCompletion.image_generation` стоит
  `max_retries = data.pop("max_retries", 2)` — два скрытых повтора
  OpenAI-клиента на каждый вызов; передавать `max_retries=0` (доходит ли
  kwarg через `optional_params` — проверить на версии). Собственный цикл
  `litellm.num_retries` на `image_generation` не действует [код].
  **Router** — по умолчанию `num_retries = openai.DEFAULT_MAX_RETRIES` (2),
  ставит клиенту `max_retries = 0` и повторяет сам на «здоровые»
  деплойменты; `fallbacks = None`. Условие: `Router(num_retries=0)`.
  R2: заголовки ответа в `_hidden_params` «only supported for openai» —
  для чужого `api_base` [не установлено]. R5: `usage` в `ImageResponse`
  заполнен нулями, не `None`; стоимость для `openai/<custom>` не считается.
  R6: ключи per-call или модульные переменные; `success_callback = []`.
- **Vercel AI SDK `ai` 7.0 (TS)** — R1 *нужна доработка* [код]:
  `generateImage` `maxRetries` = 2; `isRetryable` истинно для 408/409/429/5xx
  и для сетевых ошибок (`ECONNRESET`, `ETIMEDOUT`, `UND_ERR_*_TIMEOUT`) —
  после разрыва запрос уходит повторно; второй триггер — «unclassified empty
  responses». R4 *подходит*: `@ai-sdk/openai-compatible` даёт `imageModel()`
  с `/images/generations` и multipart `/images/edits` (маска поддержана),
  читает `data[].b64_json`. R2 *подходит*: `responses[].headers`,
  `providerMetadata`; `usage` — только число картинок.
- **Spring AI (JVM)** — R1 *нужна доработка* [док.+код]:
  `spring.ai.retry.max-attempts` = 10 (backoff 2 с × 5, до 3 мин) для
  image-клиента; на `main` `OpenAiImageModel` поверх `openai-java`
  с `DEFAULT_MAX_RETRIES = 3` — два слоя; условие
  `spring.ai.retry.max-attempts=1` и `spring.ai.openai.max-retries=0`.
  R4: реализации `ImageModel` — OpenAI, StabilityAI, Google GenAI;
  `/images/edits` и заголовки ответа [не установлено].
- **Официальные OpenAI SDK** (Python, Node, Java, Go; .NET — 3) —
  R1 *нужна доработка* [док.]: по умолчанию 2 повтора на connection errors,
  408, 409, 429, ≥500; Python и Node явно повторяют таймауты (10 мин
  по умолчанию); `DEFAULT_MAX_RETRIES = 2` проверено мной по
  `_constants.py`. Условие: `max_retries=0` при инициализации и явный
  таймаут под `deadline_at`. R2 *подходит*: `_request_id` из `x-request-id`,
  `with_raw_response`/`WithResponseInto`; тел не логирует. R6 *подходит*:
  ключ и `project` при инициализации. Для Rust официального SDK нет;
  `async-openai` 0.42 по умолчанию повторяет 429/5xx/соединение до трёх раз
  через `OpenAIRetryLayer` — отключение только заменой сервиса.
- **Нижний слой HTTP:** Go `net/http` `Transport` повторяет POST при
  сетевой ошибке, если стоит заголовок `Idempotency-Key`/`X-Idempotency-Key`
  и тело воспроизводимо — адаптеры не должны его ставить на платные вызовы
  (ставит ли `openai-go` — [не установлено]); reqwest 0.13 по умолчанию
  повторяет только протокольные NACK до приёма запроса — зафиксировать
  `retry::never()`; httpx повторяет только установление соединения.

**Провайдеры**

- **Yandex AI Studio, изображения** — R3: *сверки не существует* [док.]:
  специализированный Image Generation API (`ImageGenerationAsync`,
  `Operation` с `id`, результат по `GET` операции, хранение 12 ч) помечен
  «available until September 7, 2026» вместе с `yandex-art-2.0`;
  текущий документированный путь — OpenAI-совместимый синхронный
  `POST https://ai.api.cloud.yandex.net/v1/images/generations`
  с `aliceai-image-art-3.0`, ответ только `b64_json`. R4: `/v1/images/edits`
  — «CURRENTLY NOT SUPPORTED» (совпадает с ADR-0004: правки недоступны);
  negative prompt не поддержан ни в старом (`weight` — «Currently not
  supported»), ни в новом API; `n`, `quality`, `style`, `response_format`,
  `stream` — не поддержаны. R5: тариф 2,23 ₽ с НДС за запрос, «запросы не
  идемпотентны» — `cost_kind = estimated` по прайс-листу с `tariff_version`;
  стоимости в ответе нет. R6 *нужна доработка*: логирование данных включено
  по умолчанию, отключается заголовком `x-data-logging-enabled: false`
  на каждом вызове (пример на странице дан для старого API — действие
  на Images API проверить). Текстовые модели для `prepare` — через
  OpenAI-совместимые Completions/Responses с `Api-Key` и `project`.
  SDK `yandex-ai-studio-sdk`: `RetryPolicy` `max_attempts=5` на gRPC-пути —
  для OpenAI-совместимого пути не нужен. Заголовок `x-request-id` в ответах
  AI Studio [не установлено].
- **NanoGPT, изображения** — R3: *сверки не существует* [док.]:
  `POST https://nano-gpt.com/api/v1/images/generations` синхронный,
  в ответе `data[].url | b64_json`, `cost`, `paymentSource`,
  `remainingBalance`; идентификатора задания и метода проверки статуса для
  изображений нет (только у Midjourney и видео). R4 *подходит*:
  изображение + текст → изображение через `imageDataUrl`/`maskDataUrl`,
  `/images/edits`, `input_references`; флаги `capabilities.image_to_image`
  у моделей; negative prompt для изображений не документирован. R5
  *подходит*: `cost` в теле (`cost_kind = actual`; валюта = `paymentSource`
  — проверить для изображений), публичный прайс по модели. R2: `X-Request-ID`
  «when present», OpenAI-совместимый конверт ошибки, 429 с `Retry-After`.
  R6: privacy policy — «does not log or retain prompt and response content»,
  но «providers need request content»: текст и изображение клиента уходят
  третьей стороне вне Yandex Cloud — вопрос ADR-0004, не SDK. Оплата —
  карты Stripe (USD/EUR/GBP) и криптовалюты; Россия в документации не
  рассматривается [не установлено].
- **Все маршруты изображений** — R2 [вывод]: клиентского идентификатора
  запроса до отправки нет ни у одного; `external_request_id` известен
  только из ответа и `null` при его потере — гарантия ADR-0011 §6
  «известен до отправки» недостижима ни у одного кандидата.

Следствие для ADR-0011 §3 [вывод]: на документированных путях у обоих
маршрутов изображений действует ветка «достоверной сверки не существует»
— потерянный ответ означает `provider_outcome_unresolved`, окно сверки
маршрута равно нулю, а неидемпотентность запросов Яндекса означает, что
любой скрытый повтор — второе списание. Оговорка: страница `concepts/api`
даёт срок доступности старого API, а не факт отключения; вызов после
2026-09-07 не выполнялся (платный), и ru/en how-to расходятся. Если
маршрут `ImageGenerationAsync` ещё жив, он единственный со сверкой (окно
≤ 12 ч по сроку хранения результата) — это первое, что проверить в
программе роутера. Это не пробел ADR: ADR-0011 ветку без сверки
предусматривает. Меняется вес требования R1: оно становится единственной
защитой от двойной оплаты.

### 4.5. Движок обработки медиа

Владелец операции — backend (проверка загрузки, предпросмотр со знаком)
и генератор (проверка результата провайдера). Различают умолчания для
недоверенного ввода и поставка нативного кода.

- **sharp 0.35 (libvips, Node)** — M1 *подходит* [док.]: `metadata()`
  читает заголовок без декодирования (`format`, `mediaType`, `width/height`,
  `orientation`, `hasAlpha`, `hasProfile`); `limitInputPixels` (по умолчанию
  ≈ 268 Мпикс, «assumes dimensions from metadata can be trusted»);
  `failOn: 'warning'` по умолчанию — самый строгий, «невалидные метаданные
  всегда прерывают обработку». M2 *нужна доработка* по двум пунктам:
  по умолчанию выход конвертируется в sRGB и все метаданные удаляются
  (ICC — `keepIccProfile()`), и HEIC не декодируется prebuilt-сборкой
  (нужен глобальный libvips с libheif); `autoOrient()` первым в конвейере;
  `composite([{input, tile: true, gravity}])` — плитка знака одной опцией,
  знак не больше базы. M3: prebuilt для Linux x64 (glibc ≥ 2.28 /
  musl ≥ 1.2.5) и ARM64, Node ≥ 20.9; версия sharp фиксирует libvips
  и libwebp — CVE-обновления через обновление sharp.
- **libvips напрямую (pyvips 3.2, govips, `vips` CLI)** — M1 *нужна
  доработка* [док.]: загрузчики по умолчанию permissive
  (`fail_on = none`) — строгость задавать в каждом вызове; заголовок
  читается при открытии, `access=sequential` и shrink-on-load у `jpegload`;
  `VIPS_MAX_COORD` настраиваем с 8.16, `heifload` ограничен 16384×16384.
  M2: `thumbnail` авто-поворачивает, `new_from_file` + `resize` — нет

### 4.6. Объектное хранилище

- **Yandex Object Storage** — S1 *подходит* [док., страницы от июня —
  августа 2026]: `CopyObject` до 5 ГБ одной операцией (больше —
  `UploadPartCopy`), результирующий объект не блокируется — при
  параллельных копированиях побеждает последняя запущенная; `ListObjectsV2`
  по 1000 ключей через `continuation-token`; `DeleteObjects` до 1000
  ключей, отсутствующие помечаются `Deleted`, **обязателен `Content-MD5`**;
  `HeadObject`; коды `404 NoSuchKey`, `429`, `500 InternalError`,
  `503 SlowDown` различимы; endpoint `storage.yandexcloud.net`, оба стиля
  адресации; FAQ: strong consistency для `PUT`/`DELETE` объектов,
  о листинге не сказано. S2: lifecycle по префиксу, `Days` ≥ 1, суточный
  проход в 00:00 UTC «в течение нескольких часов» — эффективно до N+2
  суток; `Content-Type` при `PutObject` в документации не описан [не
  установлено] — в прогон. Хостинг: `IndexDocument`/`ErrorDocument`,
  документация советует `index.html` страницей ошибки для SPA; HTTP-статус
  `ErrorDocument` [не установлено].
- **Права по префиксам (S3)** — *нужна доработка* [док., проверено мной]:
  роли `storage.viewer/uploader/editor` выдаются «на облако, каталог или
  бакет», не на префикс; ограничение по префиксу — только bucket policy
  (ресурс `<bucket>/prefix/*`, `Deny` проверяется первым, условие
  `s3:x-amz-copy-source` ограничивает источник копирования) либо раскладка
  по бакетам. Это меняет способ исполнения ADR-0010 «Файлы»: два сервисных
  аккаунта плюс политика с явными `Deny` для генератора на `client/*`, или
  бакеты `client` и `transfer` раздельно (раскладка по бакетам — уровень
  инфраструктуры по ADR-0010).
- **MinIO community edition** — *нужна доработка*, решение владельца
  [код, проверено мной]: репозиторий `minio/minio` архивирован
  (`archived: true`, последний push 2026-04-24), README «no longer
  maintained», последний бинарный релиз 2025-10-15, AGPL-3.0; ILM по
  префиксу с суточной гранулярностью подтверждён исходником, режима
  коротких сроков нет. ADR-0010 и ADR-0013 называют MinIO по имени.
- **Альтернативы для локального прогона:** Garage 2.4.1 (2026-09-08) —
  нужные операции, lifecycle только `Expiration` с обязательным
  `Filter/Prefix`, без версионирования; RustFS (матрица по s3tests от
  2026-08-09) — молодой проект, lifecycle в отдельном малом гейте;
  SeaweedFS — операции и lifecycle воркером «default daily», но тяжелее
  по компонентам. **LocalStack** — *противоречит* для проверки lifecycle
  [код]: правило принимается и считается в заголовок `x-amz-expiration`,
  объекты не удаляются.
- **Клиенты S3 по языкам** — S1 *подходит с одной общей оговоркой*:
  все AWS SDK 2025 года включили контрольные суммы CRC32 по умолчанию
  (aws-sdk-s3 Rust ≥ 1.69.0, `@aws-sdk/client-s3` ≥ 3.731.0, aws-sdk-go-v2
  s3 ≥ 1.73.0; Java v2 — режим по умолчанию проверить), и AWS сам называет
  это потенциально несовместимым со сторонними S3; для `DeleteObjects`
  Яндекс требует `Content-MD5`. Условие: `WhenRequired` для запроса
  и ответа и прогон `PUT/GET/COPY/DeleteObjects` на обоих хранилищах
  (ADR-линза по go-29: вердикт «не установлено» до прогона). Умолчания
  повторов: Rust/JS/Go — 3 попытки standard; boto3 — `legacy` 5 попыток
  (задать `standard`); Java v2 — `LEGACY` 3 повтора. Различимость 404:
  Rust `NoSuchKey/NotFound` через `ServiceError`; Go `errors.As`
  (`types.NoSuchKey`, `types.NotFound`); boto3 `head_object` даёт код `'404'`,
  `get_object` — `NoSuchKey` (issue #2442); Java `NoSuchKeyException` для
  `getObject`, для `headObject` [не установлено]. Path-style: Rust
  `force_path_style`, JS `forcePathStyle`, Go `UsePathStyle`, Java
  `forcePathStyle` (с 2.18 при `endpointOverride` по умолчанию
  virtual-hosted), boto3 `addressing_style: 'path'`.

### 4.7. Очередь, outbox, сериализация

- **Конверт (Q1):** в Yandex Message Queue конверт помещается
  в пользовательские атрибуты (≤ 10 на сообщение, тело ≤ 256 КБ); для
  Kafka и AMQP — заголовки записи (общая практика, по первоисточникам не
  проверялось). Карантин обязан читать `job_id` и тип из атрибутов, поэтому
  конверт стоит дублировать и в теле. Protobuf/Avro — «не выбрано».
  *Поправка 2026-09-15 (замечание владельца, п. 5):* прежнее основание
  «без схемы конверт из тела не разобрать» снято — стабильный конверт
  с непрозрачным телом технически возможен; основание для Rated — JSON
  подходит как формат, а задачи, оправдывающей дополнительное кодирование,
  нет.
- **Валидаторы JSON Schema 2020-12 (Q2):** **Ajv 8** — отдельный класс
  `Ajv2020`; strict mode отвергает неизвестные ключевые слова — собственное
  слово классификации регистрировать `addKeyword`/`addVocabulary`;
  `removeAdditional` и `useDefaults` держать выключенными (второе
  восстановило бы стёртые поля). **python-jsonschema 4.26** — неизвестные
  слова игнорирует, расширяется `validators.extend`. **santhosh-tekuri
  v6 (Go)** — словари (`Vocabulary`, `RegisterVocabulary`); **gojsonschema**
  — только draft-04…07 (на 11.09 ADR формат схем не фиксировал, вердикт
  был «не установлено»; *поправка 2026-09-15:* ADR-0011 §6 фиксирует
  2020-12 — не подходит).
  **networknt 3.x (JVM)** — собственный диалект с ключевым словом,
  неизвестные — аннотации. **jsonschema 0.52 (Rust)** — `Draft202012`,
  `with_keyword`. Режим «после стирания» ни одна библиотека не даёт —
  вторая производная схема или своё ключевое слово с флагом [вывод].
- **Закрытая схема против совместимости вперёд** — *нужна доработка*
  [вывод, спецификация]: ADR-0013 §2 требует отклонять неизвестные поля
  документа, ADR-0011 §6 — принимать новые необязательные поля сообщения
  без смены `contract_version`; одна схема этого не совмещает. Решение —
  два варианта из одного источника: закрытый (HTTP-запрос, хранимый
  документ) и открытый (транспорт очереди). `additionalProperties: false`
  действует только в своём объекте — ставить в каждой ветви `oneOf`;
  композицию через `allOf` закрывать `unevaluatedProperties: false`.
- **RFC 8785 / JCS (Q3)** — везде *только нижний слой* [док.]: стандарт
  сортирует ключи, убирает пробелы, числа по ES6 (double, ±2^53), строки
  как есть, `null` сохраняет, схемы не знает. Библиотеки: `rfc8785` 0.1.4
  (Python, Trail of Bits), `canonicalize` 5.0.0 (JS), `gowebpki/jcs` 1.0.1
  (Go, по байтам), `java-json-canonicalization` 1.1 (не обновлялась
  с 2018), `serde_json_canonicalizer` 0.3.2 (Rust). Порядок: валидация →
  нормализация по схеме (снять отсутствующие/`null` необязательные,
  сохранить `""`/`0`/`false`/`[]`) → JCS → `sha256`. Открытый вопрос
  владельцу: поле-объединение `subject`, где `null` — значение контракта,
  а не «не задано»; правило ADR-0013 §4 на него не отвечает.
- **Брокер (Q4, справочно, уровень 5):** **Yandex Message Queue** —
  at-least-once у стандартных очередей, срок хранения 60 с … **14 дней**
  (проверено мной), visibility ≤ 12 ч, ≤ 256 КБ; FIFO-дедупликация по
  `MessageDeduplicationId` в окне 5 минут поглотит повтор `EraseGeneration`
  с тем же id — id дедупликации должен быть id попытки, не
  `(message_type, job_id)`. Сумма `deadline_at` + окно сверки + запас +
  недоступность обязана быть ≤ 14 дней. **YDB Topics** — «важный читатель»:
  сообщения не удаляются до подтверждения — единственный вариант
  «хранение до потребления» без потолка (лимиты Yandex Cloud
  на serverless YDB [не установлено]). **Managed Kafka** — retention по
  времени/размеру без потолка, но не «до потребления». **Managed
  RabbitMQ** — в документации Yandex Cloud отсутствует (страница 404,
  только образ Marketplace).

### 4.8. Сессии, аутентификация, права

Один результат на все пять экосистем: **ни одна библиотека сессий не
создаёт запись сеанса внутри прикладной транзакции** (A1), и ни одна не
хранит секрет хешем с двумя режимами срока (A2). Обходная схема везде
одна — собственная таблица (`kind`, `secret_hash`, `user_id`,
`expires_at`, абсолютный потолок) и `Set-Cookie` из обработчика после
`commit`.

- **TS:** `@adonisjs/session` 8.1 — `initiate` → `next()` → `commit()`
  (проверено мной по `session_middleware.ts`), `DatabaseStore` пишет через
  собственный клиент Lucid; `@adonisjs/auth` 10 `SessionGuard` строки сеанса
  в БД не создаёт; cookie без `Domain`, `sameSite: 'lax'` есть, но один
  `age` на всё и cookie на каждый ответ с middleware. `@fastify/session`
  11.1 — `store.set` в `onSend`; умолчания `saveUninitialized = true`,
  `rolling = true` — сессия на любой запрос (A2 *противоречит* в штатном
  режиме, обход настройкой). `express-session` 1.19 — то же.
- **Python:** Django 5.2 — `SessionMiddleware` сохраняет в `process_response`
  вне транзакции view, но `db.SessionStore.save()` открывает вложенный
  `atomic`, поэтому запись сеанса можно создать из view внутри своей
  транзакции и поставить cookie руками; умолчания cookie — `Domain=None`,
  `Lax`, `HttpOnly`; `SESSION_COOKIE_SECURE=False` — включить; один срок
  на сессию. Starlette `SessionMiddleware` — подписанная cookie, не серверная
  таблица (*противоречит* как хранилище; `Response.set_cookie` без `Domain`
  подходит).
- **Go:** SCS v2.9 — `LoadAndSave` фиксирует при первой записи ответа через
  собственный `*sql.DB`; `HashTokenInStore = false` по умолчанию; cookie
  `Domain ""`, `Lax`, `HttpOnly`; `Secure=false` — включить. GoFrame
  `gsession` — `Close()` после обработчика, хранилища PostgreSQL нет. Beego
  — при `SessionOn` сессия создаётся на любой запрос без cookie (штатный
  режим противоречит A2; ADR-линза: «нужна доработка», обход —
  маршрутный `SessionOn` и своя реализация). `gorilla/sessions` —
  `CookieStore` отвергнут ADR-0012.
- **JVM:** Spring Session JDBC — `REQUIRES_NEW` и `commitSession()`
  в `finally` фильтра; штатная схема хранит `SESSION_ID` открыто, только
  скользящий срок; `DefaultCookieSerializer` по умолчанию `Lax`, `HttpOnly`,
  без `Domain` (`Secure` и `Path` задать явно). Spring Security: request
  cache создаёт `HttpSession` даже при `NEVER` — `NullRequestCache`
  и `STATELESS`. Ktor Sessions — запись в `SessionStorage` на этапе ответа
  (`Sessions.kt` не извлёкся — подтвердить на версии). Javalin/Jetty 12 —
  `JDBCSessionDataStore` пишет при выходе последнего запроса. Micronaut
  Session — только in-memory и Redis. Quarkus — серверных сессий нет,
  form-auth в зашифрованной cookie.
- **Rust:** tower-sessions 0.15 — `save()` после обработчика; `PostgresStore`
  хранит `id` открытым текстом; cookie `with_domain(None)`, `SameSite`
  по умолчанию **Strict** — задать `Lax`; `Expiry::OnInactivity` без
  потолка. Обход — `axum-extra` `CookieJar`, возвращаемый из обработчика
  после `commit`.
- **CORS и проверка `Origin` (A3)** — везде *нужна доработка*: заголовки
  (фиксированный origin, `credentials`, expose `Retry-After, ETag`)
  выставляют все middleware — Starlette `CORSMiddleware`, django-cors-headers,
  `@fastify/cors` 11, tower-http `CorsLayer`, Echo `middleware.CORS`,
  GoFrame `CORSOptions`, Spring `CorsConfiguration`, Ktor CORS; но ни один
  не отвергает не-preflight запрос без `Origin` или с чужим `Origin`
  (`gin-contrib/cors` отвергает чужой с 403, но пропускает отсутствие).
  Django `CsrfViewMiddleware` проверяет `Origin`, но требует CSRF-токен,
  отвергнутый ADR-0012. Проверка «обязательный `Origin` на всех не-GET/HEAD,
  включая multipart без preflight, иначе `403 origin_rejected`» — свой
  middleware во всех экосистемах.
- **Хеш пароля (A4):** argon2-cffi 25.1 (Argon2id, RFC 9106), node-argon2
  0.45 или встроенный `crypto.argon2` (Node ≥ 24.7, низкоуровневый KDF),
  `x/crypto/argon2` (только KDF — соль и PHC-строка свои), Spring
  `Argon2PasswordEncoder` (Bouncy Castle), `argon2` 0.6 (Rust, в
  `spawn_blocking`). Одноразовый токен через `UPDATE … WHERE used_at IS NULL`
  — прикладной SQL везде.
- **Три причины `401` и `404` для чужого ресурса (A5)** — прикладная
  логика во всех экосистемах; библиотечных ограничений не найдено.

  курсорная пагинация обязательна только для клиентского API.
- **U4, глубокие ссылки на Object Storage** — *не установлено* до
  эмпирики [док.]: `ErrorDocument = index.html` — рекомендуемый Яндексом
  приём для SPA, `RoutingRules` — HTTP-редиректы (≤ 50), бакет публичный,
  HTTPS требует имя бакета = FQDN; с каким статусом отдаётся
  `ErrorDocument` (200 или 404), документация не говорит — проверить
  `curl -I` на бакете до фиксации.

### 4.10. Артефакт контракта

- **OpenAPI 3.1.1** — C1 *подходит* [спецификация]: Schema Object —
  надмножество JSON Schema 2020-12, неизвестные ключевые слова — аннотации
  (внутри Schema Object без префикса `x-`); тела HTTP и тела сообщений
  очереди могут ссылаться на одни `$defs`. C2: `discriminator` для
  `source.kind` с `mapping`; `subject` (`{version_id}` | `{upload_id}` |
  `null`) общего свойства не имеет — чистый `oneOf` из трёх схем.
- **TypeSpec 1.16** — *подходит с условиями*: эмитит OpenAPI 3.1 (по
  умолчанию 3.0 — задать) и JSON Schema из одного источника; `union` по
  умолчанию `anyOf` — нужен `@oneOf`; `@discriminated` по умолчанию даёт
  конверт `{kind, value}` — нужен `envelope: "none"`; `contract_version`
  очереди — целое, а `@versioned` даёт именованные версии.
- **Генераторы типов** — различаются на объединениях и `null`:
  `openapi-typescript` 7.13 — 3.0/3.1, `discriminator` *подходит*;
  `json-schema-to-typescript` 16 — модель draft-04, `oneOf` как `anyOf`,
  игнорирует `prefixItems`/`$dynamicRef` — *нужна доработка*;
  `datamodel-code-generator` 0.79 — Pydantic v2, `extra=forbid`,
  `discriminator`, 3.1 *подходит*; `openapi-python-client` 0.29 —
  `discriminator` [не установлено]; `oapi-codegen` 2.8 — 3.1 «initial»,
  объединения обёртками `As/From` — *нужна доработка*;
  `openapi-generator` 7.25 — 3.1 «beta support», открытые баги по
  `discriminator` — *нужна доработка*; `progenitor` 0.15 — только 3.0.x —
  *противоречит* для 3.1-артефакта; `typify` 0.8 — `oneOf` → `enum`,
  `additionalProperties:false` → `deny_unknown_fields`, драфты [не
  установлено]; `utoipa` 5 — code-first 3.1; `quicktype` 26
  и `jsonschema2pojo` — поддержка 2020-12/`discriminator` [не установлено].
- **C3, единый источник:** contract-first — схема в репозитории, из неё
  типы всех сторон, валидатор и канонизатор читают её в рантайме;
  code-first (FastAPI ≥ 0.99 с `json_schema_extra`, springdoc 3.1 по
  умолчанию, utoipa) — источник истины в типах одного языка, экспорт
  должен быть доступен коду канонизации и стирания в машинном виде.
  Контракт очереди при разных языках сторон не может быть code-first одной
  стороны [вывод]. Правило Q3 для объединений применяется только после
  выбора ветви (по `kind` или по наличию ключа). *Поправка 2026-09-15
  (замечание владельца, п. 5):* требование ADR — доступность классификации
  полей во время стирания, и сырой файл схемы не единственный способ её
  обеспечить: `datamodel-code-generator` переносит аннотации поля через
  `--field-extra-keys` в `json_schema_extra` (измерено в пробе
  [2026-09-15](2026-09-15-message-schemas-probe.md) §4). Принято владельцем
  2026-09-15: contract-first, JSON Schema 2020-12 файлами в репозитории без
  расширения на HTTP/OpenAPI (ADR-0011 §6).

## 5. Сквозные находки, которых нет в документе владельца

1. **Сессии — своя таблица в любой экосистеме.** Документ показал три
   случая (Adonis, Spring Session, Django); исследование — все двенадцать
   проверенных библиотек. Библиотека сессий как хранилище не нужна нигде;
   нужны cookie-примитивы фреймворка и своя таблица. Это уравнивает
   экосистемы по A1–A2.
2. **Проверка `Origin` — свой middleware везде.** Ни один CORS-middleware
   не отвергает не-preflight запрос с отсутствующим или чужим `Origin`.
3. **Скрытые повторы — у всех библиотечных роутеров и всех официальных
   OpenAI SDK по умолчанию;** плюс Exposed (транзакции), async-openai,
   Yandex SDK на gRPC-пути, Go `net/http` при `Idempotency-Key`. AWS SDK
   повторяют 3 раза — для `PUT/COPY/DELETE` по ключу это безвредно
   (ADR-0014 §1), но учитывается в таймаутах аренды.
4. **Сверки нет ни у одного документированного маршрута изображений.**
   Асинхронный API Яндекса помечен доступным до 2026-09-07 (отключение
   не проверялось), текущий путь синхронный, NanoGPT синхронный. Ветка
   ADR-0011 §3 «достоверной сверки не существует» в v1 единственная [вывод]; `external_request_id` до
   отправки неизвестен нигде; поздние сведения о расходе не приходят.
   Запросы Яндекса неидемпотентны — R1 становится единственной защитой
   от двойной оплаты.
5. **Яндекс логирует данные по умолчанию** — заголовок
   `x-data-logging-enabled: false` на каждый вызов; правок (`edits`)
   у Яндекса нет — маршрут «изображение + текст → изображение» в наборе
   кандидатов только у NanoGPT, то есть с передачей клиентских данных за
   пределы Yandex Cloud (вопрос ADR-0004).
6. **Канонизация: JCS есть везде, нормализация по схеме — свой код везде;**
   поле-объединение с `null` (`subject`) правилом ADR-0013 §4 не покрыто.
7. **Закрытая и открытая схема не совмещаются** — два варианта из одного
   источника (ADR-0013 §2 против ADR-0011 §6).
8. **AWS SDK с января 2025 шлют CRC32 по умолчанию, Яндекс требует
   `Content-MD5` для `DeleteObjects`** — `WhenRequired` и прогон на обоих
   хранилищах. **Роли Object Storage не знают префиксов** — bucket policy
   с `Deny` или раздельные бакеты.
9. **MinIO заархивирован** (2026-04-24; релизы прекращены 2025-10-15);
   ADR-0010/0013 называют его по имени. LocalStack lifecycle не исполняет.
   Кандидаты: Garage, RustFS, SeaweedFS.
10. **Yandex Message Queue: потолок хранения 14 дней и FIFO-дедупликация
    на 5 минут;** YDB Topics — единственный вариант «до потребления»;
    управляемого RabbitMQ в Yandex Cloud нет.
11. **Медиа:** Pillow выделяет холст WebP до проверки «бомбы»; HEIC нигде
    без дополнительной нативной сборки; политика цвета (ICC/sRGB) везде
    явная; ImageMagick пишет дату в PNG — ломает повторяемость по `sha256`;
    у FFmpeg CLI ошибки декодирования по умолчанию не останавливают
    обработку (`-xerror`).
12. **Слои данных с ловушками:** unit-of-work переупорядочивает
    (SQLAlchemy ORM, Hibernate, MikroORM); Exposed повторяет транзакции
    трижды; Diesel не отдаёт SQLSTATE; Django без `FOR SHARE`
    и `RETURNING`; asyncpg отдаёт тег вместо числа строк.
13. **Дизайн-система в виде IIFE-бандла не импортируема второй сборкой** —
    уточнение ADR-0009 о фирменном дизайне кабинетов требует изменения
    в upstream-проекте DS (ESM, `react` как peer).
14. **Мелочи поставки, которые ломают контракт молча:** Tomcat
    `maxSwallowSize` (клиент не увидит 413), Spring Security request cache
    (создаёт сессии), sharp/libvips `failOn` по умолчанию разный у обёртки
    и у прямых привязок, `MissedTickBehavior::Burst` у Tokio догоняет тики.

## 6. Моё видение

Это мнение, не задано владельцем и не решение. Выбор по каждой границе
независим, как требует документ владельца; основания — только пункты
брифа, которые выбранный кандидат закрывает, а альтернативы — нет или
дороже. Рядом — второй кандидат и его цена.

### Backend — TypeScript: Fastify 5 + pg/Kysely + Ajv 2020 + sharp

Почему именно так:

- **B5–B6 с наименьшим объёмом своего кода:** типизированные ошибки
  парсера с кодами и статусами, `@fastify/rate-limit` с `retry-after`
  и ключом по сессии, `@fastify/multipart` с 413 в обработчике, `@fastify/etag`
  в `onSend`. У Axum это оболочки на каждый экстрактор, у Gin — своя
  middleware ошибок, у Django — 400 вместо 413 и свой upload handler,
  у Spring — `maxSwallowSize` и буферизующий ETag-фильтр.
- **B1–B3 без ORM-ловушек:** Kysely исполняет немедленно, отдаёт
  `numUpdatedRows` и SQLSTATE, знает `forShare/skipLocked/returning`;
  порядок захвата = порядок кода. Это же дают SQLx, pgx и jOOQ — здесь
  TS не лучше, но и не хуже.
- **Граница 5 принадлежит backend, и sharp — движок с наиболее строгими
  умолчаниями для недоверенного ввода:** `failOn: 'warning'`,
  `metadata()` до декодирования, `limitInputPixels`, плитка знака одной
  опцией, AVIF в prebuilt. У прямых привязок libvips строгость задаётся
  в каждом вызове, у Pillow — дыра с WebP, у Go stdlib — ни лимита, ни EXIF,
  у ImageIO — ни лимита, ни WebP на запись, у image-rs — нет lossy WebP.
- **Ajv — референсный валидатор 2020-12 с `addKeyword`:** одна схема
  для валидации, классификации полей и канонизации в том же процессе,
  что и `canonicalize`; `openapi-typescript` — самый зрелый генератор
  3.1 с `discriminator`.
- **Три фронтовые сборки и так на TS/React** (ADR-0009: кабинет мастера
  и админка в фирменной DS). Один язык на все стороны — один генератор
  типов, один валидатор, одна дисциплина контракта. Документ владельца
  прав, что общих TS-типов сегодня нет; они появляются только при этом
  выборе.

Цена: сессии и проверка `Origin` свои (как везде); NestJS не нужен —
слой данных всё равно свой, а модульность даёт и Fastify; HEIC вне
prebuilt sharp — решается списком форматов на шаге 4; проверить на
версии, что ошибки парсера проходят через `setErrorHandler` и что два
`preHandler`-лимитера не делят счётчик.

Второй кандидат — **Go: Echo v5 + pgx + sqlc.** Сильнейшие примитивы БД,
единый `HTTPErrorHandler`, поставка одним бинарником. Цена: медиа —
govips через cgo (libvips из образа, `Startup/Close`, потеря sequential
при повороте) или ffmpeg-процесс с `-xerror`; генерация типов из 3.1
«initial», объединения обёртками; третий язык рядом с TS фронтов
(документ владельца §12: каждый язык — сборка, зависимости, CVE).
Python (FastAPI + psycopg 3 + Pillow) — цена: WebP до проверки бомбы,
только SQLAlchemy Core, Starlette ≥ 1.6. JVM (Spring) — много
«отключить»: Spring Session, request cache, Hibernate flush, Exposed
retries, `maxSwallowSize`. Rust (Axum + SQLx) — самый большой объём своего
кода при тех же гарантиях: гарантии языка, как верно пишет документ,
порядок блокировок не заменяют.

### Генератор — тот же язык, собственные адаптеры поверх официального OpenAI SDK

- Библиотечные роутеры ничего не добавляют для наших провайдеров: LiteLLM
  видит Yandex и NanoGPT только как `openai/<custom>`, прячет два повтора,
  отдаёт `usage` нулями и не считает стоимость; Vercel AI SDK даёт
  `openai-compatible` с `edits`, но с теми же повторами и без стоимости;
  Spring AI — два слоя повторов. Официальный OpenAI SDK с `maxRetries: 0`,
  явным таймаутом, `project` и `default_headers` покрывает оба провайдера
  и текстовые модели Яндекса для `prepare`.
- Собственный роутер — таблица маршрутов с полями контракта ADR-0011:
  сверка = нет на документированных путях (проверить старый async-маршрут),
  число платных вызовов на задание, повторяемые ошибки
  (только до отправки), negative prompt = нет, `image + text` = только
  NanoGPT, тариф с `tariff_version`, политика данных (заголовок Яндекса,
  передача NanoGPT третьим сторонам).
- Тот же язык, что backend: один контракт, один валидатор, один S3-адаптер
  (снимает вопрос «одного общего адаптера» ADR-0010), sharp для `verify`
  результата. Python как второй кандидат оправдан только одним: если во
  второй итерации появится локальная генерация по маске (PyTorch), она
  всё равно будет отдельным исполнителем-процессом — и добавить его можно
  без смены языка генератора.

### Движок медиа — libvips через sharp; FFmpeg не нужен

Для стилей FFmpeg — второй процесс, свой контракт (`-xerror`, таймаут
снаружи) и неустановленные EXIF/ICC; libvips делает всё в процессе с
известными умолчаниями. FFmpeg остаётся кандидатом, если появится видео.

### Кабинет мастера и админка — React + TS, ra-core поверх DS-пакета

`ra-core` (MIT, headless) даёт контроллеры списков, форм и `authProvider`
без MUI; адаптер data provider к конверту пишется в любом случае. Второй
кандидат — TanStack Router/Query/Table: меньше абстракций, больше своего
кода на CRUD справочников и журнала. Обязательное условие для обоих —
ESM-сборка дизайн-системы в upstream-проекте.

### Артефакт контракта — contract-first, OpenAPI 3.1 + JSON Schema 2020-12

Один источник (YAML или TypeSpec с `@oneOf`/`envelope: "none"`), общие
`$defs` для HTTP и сообщений, из него — закрытый и открытый варианты,
`openapi-typescript` для TS, Ajv в рантайме; при другом языке генератора —
`datamodel-code-generator` (Python) или `oapi-codegen` (Go) с прогоном
объединений.

### Хранилище — AWS SDK с `WhenRequired`; локально не MinIO

Клиент `@aws-sdk/client-s3` с `forcePathStyle` и контрольными суммами
`WhenRequired`, набор операций прогоняется на Яндексе и локальном
хранилище. Локально — Garage 2.4 (или RustFS) вместо заархивированного
MinIO; это трогает ADR-0010/0013 и требует решения владельца. Бакеты
`client` и `transfer` раздельно упростят роли двух сервисных аккаунтов
(уровень 5).

### Брокер — не решаю; требования Q4 проверить так

Yandex Message Queue проходит только при сумме сроков ≤ 14 дней
и `MessageDeduplicationId` = id попытки; YDB Topics с «важным читателем»
— буквально «до потребления»; Kafka — без потолка, но не «до потребления».

## 7. Что проверить до ADR и что решить владельцу

Проверки на зафиксированных версиях (порядок — по весу для решения):

1. Fastify: ошибки content-type parser проходят через `setErrorHandler`;
   два `preHandler`-лимитера (IP и сессия) не делят счётчик; `bodyLimit`
   действует на multipart-поток вместе с `limits.fileSize`.
2. Kysely: `numUpdatedRows` для `UPDATE … WHERE lease_generation = :mine`
   и `INSERT … ON CONFLICT DO NOTHING RETURNING`.
3. `@aws-sdk/client-s3` с `WhenRequired`: `PUT` с `Content-Type` → `HEAD`
   отдаёт тот же тип; `DeleteObjects` с `Content-MD5` на Яндексе
   и локально; `ListObjectsV2` сразу после `PUT`/`DELETE`; коды `NoSuchKey`
   у `HEAD` на обоих хранилищах.
4. Яндекс Images API: действие `x-data-logging-enabled` для
   `aliceai-image-art-3.0`; наличие `x-request-id`; поведение при потере
   ответа (запрос неидемпотентен) — на одном платном вызове по программе
   проверки роутера.
5. Object Storage hosting: статус `ErrorDocument` (`curl -I`).
6. Ajv 2020 с `addKeyword` для слова классификации; генерация обоих
   вариантов схемы (закрытый/открытый) из одного источника;
   `openapi-typescript` на `source`/`subject`.
7. sharp: `metadata()` для WebP/AVIF с ложным заголовком и `failOn`;
   `composite` с плиткой на предпросмотре; решение по HEIC.
8. Garage 2.4: правило `Expiration` с `Filter/Prefix` реально удаляет,
   период воркера; коды 404/5xx.
9. Yandex Message Queue: сумма `deadline_at` + окно сверки (= 0) + запас
   + допустимая недоступность ≤ 14 дней — численно на шаге 4.

Решения владельца, которые исследование не принимает:

- **MinIO** в ADR-0010/0013: заморозить образ 2025-10-15 и записать это,
  или заменить на Garage/RustFS (уточнение ADR по правилу README).
- **Сверка на документированных путях отсутствует у обоих маршрутов v1**
  (если `ImageGenerationAsync` жив — проверить первым): оставить механизм
  ADR-0011 §3 как есть с окном 0, или зафиксировать в контракте маршрута
  «сверки нет» явно.
- **NanoGPT как единственный маршрут `image + text`** — передача
  клиентского текста и изображения за пределы Yandex Cloud против
  ADR-0004; и оплата (карты Stripe в USD/EUR/GBP, криптовалюта).
- **Канонизация `subject: null`** — значение контракта или «не задано».
- **Права хранилища** — bucket policy с `Deny` или два бакета.
- **HEIC** в списке форматов загрузки (шаг 4) — определяет вторую нативную
  зависимость у любого движка.
- **Изменение в upstream-проекте дизайн-системы** (ESM-сборка) как
  предпосылка кабинетов в фирменном дизайне.

## 8. Как это проверялось и где границы

- Десять исследователей отработали полностью: Context7 был доступен всем,
  1043 вызова инструментов, ~4,4 млн токенов; каждая находка несёт URL,
  версию или дату и вид источника — полный перечень в приложении
  «Источники по границам»; в разделах 4–5 сохранены версии и даты.
- Проверка двумя линзами задумывалась для каждого опорного утверждения;
  из-за лимита сессии отработали только линзы «соответствие ADR» для Rust
  и Go: 14 вердиктов, 3 опровергнуты по привязке (не по фактам), и текст
  это учитывает: Beego — «нужна доработка», а не «противоречит»; CRC32
  у aws-sdk-go-v2 — «не установлено» до прогона; gojsonschema — «не
  установлено», пока формат схем не выбран. Линза «первоисточник» не
  отработала ни по одной области; остальные вердикты — с одной линзой
  исследователя.
- Вместо неё восемь опорных утверждений перепроверены мной по
  первоисточникам 2026-09-11: срок Image Generation API Яндекса
  (`concepts/api`), потолок хранения Message Queue 14 дней, роли Object
  Storage только на бакет, архив MinIO (GitHub API), Exposed
  `defaultMaxAttempts = 3` (`DatabaseConfig.kt`), отсутствие SQLSTATE
