# Проба общих схем сообщений: JSON Schema 2020-12 на TypeScript и Python

Дата: 2026-09-15. Статус: результат пробы, решения владельца не заменяет.
Исходники пробы лежат рядом: `docs/research/2026-09-15-message-schemas-probe/`
(схемы, корпус фикстур, два раннера, скрипты генерации, закреплённые версии,
`run-all.sh`). Дополнено 2026-09-15 по шести замечаниям владельца к коммиту
`4ed93b2` — §12; числа ниже приведены к состоянию после исправлений.

Проба выполняет шаг, который владелец назвал следующим 2026-09-15: «проверить
выбранную цепочку на реальных схемах трёх сообщений и документа до/после
стирания», после чего фиксируются генераторы, версии и параметры запуска.

## 1. Итог

Измерено:

- Схемы `SubmitJob`, `EraseGeneration`, `Result` (конверт вне версии, тело
  версии 1, открытая форма) и документа `input` версии 1 с двумя корнями
  (`#before`, `#after`, закрытая форма) написаны по ADR-0011 §6 и ADR-0013 §2/§6.
- Общий корпус из 65 фикстур с ожидаемым исходом (принять / отклонить /
  карантин) прошёл на обеих сторонах полностью: Ajv2020 + ajv-formats — 65/65,
  `jsonschema.Draft202012Validator` с проверкой форматов — 65/65 (таблица в §5).
  Цепочка «схема → модель Pydantic → сериализация → схема» проверена на всех
  19 принятых схемой фикстурах без нарушений (§4, §12 P3).
- Наблюдение владельца воспроизведено на сгенерированной модели:
  `AwareDatetime` при `strict=True` принимает строку `"1757939400"`; общая схема
  с проверкой формата её отклоняет на обеих сторонах (M03).
- Найдена одна форма записи схем, которую переваривают все четыре инструмента
  (два валидатора и два генератора). Четыре других варианта записи ломают хотя
  бы один из генераторов; каждая поломка записана в §3.

Не измерено (открыто): см. §9. Имена полей, которых нет в тексте ADR
дословно, — предварительные, список в §10.

## 2. Что проверялось

| Сторона | Проверка сообщения по общей схеме | Представление в коде |
| --- | --- | --- |
| Backend (Node 26.5.0) | `Ajv2020` 8.20.0 + `ajv-formats` 3.0.1, строгий режим | типы из `json-schema-to-typescript` 16.0.0 |
| Генератор (Python 3.14.6) | `jsonschema` 4.26.0 + `referencing` 0.37.0 + `rfc3339-validator` 0.1.4 | модели из `datamodel-code-generator` 0.81.0, Pydantic 2.13.5 |

Приём сообщения на обеих сторонах двухшаговый: конверт → известна ли
`contract_version` → тело по схеме `messages/v<N>/<тип>.json`. Карантин — не
исход валидации, а ветка кода после успешного конверта (M15).

Стирание — отдельная функция на каждой стороне, читающая слово классификации
`ratedFieldClass` из сырой схемы (не из сгенерированных моделей): обходит
`properties` корня `fields`, ключ класса `content` удаляет, класса `technical`
сохраняет целиком, без класса — спускается внутрь (тогда линтер требует класс
у каждого вложенного свойства). Отображение `SubmitJob` → документ `input`
генератора — явное копирование по ключам, отдельно от валидации (P01).

## 3. Форма схем, к которой сошлась проба

Правила ниже — не вкус, каждое снимает измеренную поломку.

| Правило | Что ломалось без него (измерено) |
| --- | --- |
| Межфайловые `$ref` — абсолютные, по `$id`: `https://ratedtattoo.ru/schemas/common.json#/$defs/timestamp` | Относительные `../../common.json`: `datamodel-code-generator` разрешает цепочку относительных ссылок через файл конверта в несуществующий `messages/common.json`; `json-schema-to-typescript` разрешает вложенные относительные ссылки относительно `cwd`, а не файла (`probe/common.json` not found), с `--cwd` и без, со слэшем на конце и без. Валидаторы обе формы принимают |
| Ссылки внутри своего файла — локальные `#/$defs/x` | Абсолютная ссылка на свой же файл (`…/result.json#/$defs/provider_call`): `datamodel-code-generator` наращивает путь (`messages/v1/messages/v1/messages/v1/result.json`) |
| Композиция только через `allOf: [{"$ref": …}]` плюс собственные ключевые слова; `$ref` с соседями не используется | `$ref` + соседние `properties`/`required`: `json-schema-to-typescript` теряет `required` из ссылки, а при соседних `properties` — все свойства ссылки (корень `after` превращался в два поля `never`); `datamodel-code-generator` падает «can not resolve classes», если у ссылки есть внутренние `#/$defs` |
| Корневой `$ref` на конверт заменён на `allOf` | С корневым `$ref` `json-schema-to-typescript` не находит `#/$defs/provider_call` того же файла («Token $defs does not exist») |
| Закрытие на каждом уровне объекта: `unevaluatedProperties: false` рядом с `allOf` у корня и у каждого вложенного объекта документа | `unevaluatedProperties: false` у корня вложенные объекты не закрывает (замечание владельца, п. 2); подтверждено D03/D04/D11: без закрытия на уровне `studio_rules` неизвестный ключ проходил бы |
| Два корня документа в одном файле: `$defs/before`, `$defs/after` с `$anchor`; общий `$defs/fields` несёт классификацию | `after` = `fields` + `properties: {description: false, negative_prompt: false}` — присутствие стёртого поля отклоняется, восстановление пустой строкой тоже (D07, D08) |
| Ajv: `type: "object"` рядом с `required`/`properties`/`unevaluatedProperties` в каждой подсхеме, включая `if`/`then` | `strictTypes` в строгом режиме иначе отказывает компилировать |
| Объединения типов только вида `[T, "null"]`; исключение `assembled_request` (`string`/`array`/`object`/`null` по ADR-0011 §6) требует `allowUnionTypes` | `strictTypes` отвергает объединения шире пары с `null` |

Один и тот же `$defs/studio_rules` из `common.json` открыт в теле сообщения
(D13 принимает лишний ключ) и закрыт в документе (D03 отклоняет): две оси
версий, две формы, один источник — цель из предложения владельцу выполнена без
дублирования определений.

## 4. Граница ответственности: схема против сгенерированной модели

Модели сгенерированы из тех же файлов (`datamodel-code-generator`, параметры в
§7) и проверены на тех же данных. Строки, где модель слабее схемы, — то, что
владелец назвал в п. 1: сгенерированная модель не гарантирует всех ограничений.

| Случай | Общая схема (обе стороны) | Модель Pydantic (сгенерированная) |
| --- | --- | --- |
| `created_at: "1757939400"` (M03) | отклоняет | **принимает** и делает дату 2025-09-15 12:30 UTC — воспроизведение наблюдения владельца |
| `created_at: 1757939400` число (M04) | отклоняет | со `--strict-types` отклоняла (`datetime_type`); без него (§12 P3) **принимает** как Unix-время |
| `created_at` без смещения (M05) | отклоняет | отклоняет (`timezone_aware`) |
| `mode: "refine"` при `"mode": false` (M12) | отклоняет | **принимает**: `false` стал `Any \| None` |
| `contract_version: 99` (M15) | карантин | отклоняет (`Literal[1]`) — карантин моделью невыразим, конверт нужно разбирать отдельно |
| `source.size: "1024"` (M13) | отклоняет | со `--strict-types` отклоняла (`int_type`); без него (§12 P3) **принимает** числовую строку — ворота остаются за схемой |
| `result_candidate` без `call_id` (M24) | отклоняет | отклоняет |
| `provider_calls[0].finished_at: "1757939400"` | отклоняет | **принимает** |
| `cost_kind: estimated` без `tariff_version` (M30) | отклоняет | **принимает**: `if`/`then` в модель не переносится |
| документ: неизвестный ключ верхнего уровня (D02) | отклоняет | отклоняет (`extra="forbid"` выведен из `unevaluatedProperties: false`) |
| документ: неизвестный ключ внутри `studio_rules` (D03) | отклоняет | **принимает**: вложенный `allOf` + `unevaluatedProperties` свёрнут в открытый `common.StudioRules` |
| после стирания `description` присутствует (D07, D08) | отклоняет | **принимает**: `false` стал `Any \| None = None` |
| классификация полей | в сыром файле | перенесена: `json_schema_extra={"ratedFieldClass": …}` у всех восьми полей `Before` (измерено через `model_fields`) |
| `seed: 7.0` (D14; JSON не различает 7 и 7.0) | принимает как `integer` | с `--strict-types int` **отклоняла** (`int_type`) — модель была строже схемы; `--strict-types` снят (§12 P3) |
| `revision` у Result после `model_dump` | обязателен | **терялся**: поле было объявлено только в `then` конверта, генератор `if`/`then` не переносит; исправлено объявлением в `properties` (§12 P3) |
| стёртый документ → `After` → `model_dump(mode="json")` по умолчанию | корень `after` отклоняет остаток | **восстанавливает** `description: null`, `negative_prompt: null` (воспроизведено); с `exclude_unset=True` ключи не возвращаются, остаток проходит `after` |
| сериализация принятого сообщения | проходит схему снова (все 19 принятых фикстур) | представление меняется: `.123Z` → `.123000Z`, неизвестные поля отброшены — схема принимает |

Типы TypeScript (`json-schema-to-typescript` 16.0.0 через API, §7): открытые
(`[k: string]: unknown`) даже у закрытого документа, `required` рядом с `allOf`
теряется (`Inputbefore = Fields`, `description?:`), `false` становится
`never`, конверт приходит пересечением `ADR00116 & {…}`. Документация
(§11) подтверждает для 16.0.0: `unevaluatedProperties` игнорируется,
`if`/`then` игнорируется, `$anchor` даёт ошибку, разрешение ссылок по `$id`
не поддерживается; для ветки master после 16.0.0 заявлено, что соседи `$ref`
(`properties`, `required`) пересекаются с целью ссылки (#613) — на 16.0.0 это
не так, измерено. Для компилятора это удобство, не проверка — что и
утверждает таблица владельца.

Пояснения к строкам, которые иначе читаются как противоречие ADR:

- M11, M26 — **следствие открытой формы тела**, которое надо принять
  осознанно: схема не отличает лишний `kind` в `source` или `call_id` на
  верхнем уровне `Result` от будущего необязательного поля. Требование
  владельца (п. 4) выполняется иначе: фикстуры M02/M21 проверяют, что эти поля
  **не требуются**, а P01 — что принятое сообщение с лишними полями сохраняется
  без них (п. 3). Отклонять их можно только явным `false`, как `mode` (M12).
- M12 — `"mode": false` кодирует решение B-28 «`mode` в `SubmitJob` нет».
  Это предложение: список явно запрещённых имён — новое правило контракта,
  решение за владельцем (§9).
- M16 — отклонение при сломанном конверте: обработка некорректного сообщения
  известной версии в контракте открыта (стек §7); проба лишь показывает, что
  конверт проверяется первым.
- E01/E02 — исход теста стирания определяет только результат стирания:
  остаток по корню `after`, повторное стирание без изменений, сохранность
  технической части; исход проверки входа по `before` пишется справочно.
  Измерено для E02: `after=reject`, вход тоже `before=reject`. Стирание не
  бросает исключение на неизвестном вложенном ключе: `studio_rules` класса
  `technical` сохраняется целиком, и остаток не проходит `after` (D11). На
  неизвестном ключе верхнего уровня функция стирания бросает исключение, а не
  решает за схему.

## 6. Ответы на пять уточнений владельца

1. **Валидатор исходного сообщения в Python выбран явно**:
   `Draft202012Validator(…, format_checker=Draft202012Validator.FORMAT_CHECKER,
   registry=…)`. Измерено: `date-time` попадает в перечень проверяемых форматов
   только при установленном `rfc3339-validator`; без `format_checker`
   календарно невозможная дата M45 (30 февраля) проходит — `pattern` профиля
   ловит форму, но не календарь. Поэтому `rfc3339-validator` — обязательная
   зависимость генератора, а не опция. Одинаковость проверки на двух сторонах
   даёт не библиотечный `format`, а общий профиль в схеме (§12 P1). Границу ответственности из таблицы
   владельца проба подтверждает: решение «принять / отклонить» даёт схема, модель
   Pydantic — представление после проверки (§4).
2. **Правила до и после стирания** — два корня одной версии (`#before`,
   `#after`), обработчик выбирает корень по `schema_version` и признаку стирания
   строки; новая `schema_version` для стирания не нужна. Тест владельца целиком
   — E01: до → стирание → проверка остатка по `#after` → повторное стирание даёт
   тот же результат → техническая часть (включая `studio_rules.text`) равна
   исходной без ключей класса `content`. Закрытие вложенных объектов — на каждом
   уровне (D03, D04, D11), одного `unevaluatedProperties: false` у корня
   недостаточно.
3. **Неизвестное поле сообщения в документ не переносится**: P01 принимает
   сообщение с `ext_note`, `parameters.ext_flag` и `source.kind`, отображение
   копирует только известные ключи, документ проходит `#before`. У Ajv
   `coerceTypes`, `useDefaults`, `removeAdditional` выставлены `false` явно; M13
   подтверждает, что `"1024"` в число не приводится.
4. **Примеры приведены к контракту**: у `source` нет `kind` (M02), `subject` в
   схемах нет, `call_id` обязателен внутри `provider_calls[]` (M23) и
   `result_candidate` (M24, M25), на верхнем уровне `Result` не требуется (M21).
   Взаимодействие сборок — C01/C02: копия v1 с необязательным `ext_note`
   принимает старые сообщения, старая схема принимает новые, `contract_version`
   не менялась.
5. **Две формулировки исследования 2026-09-11 поправить**: `--field-extra-keys
   ratedFieldClass` действительно переносит классификацию в `json_schema_extra`
   каждого поля (§4), так что «классификация обязательно теряется» неверно;
   требование ADR — доступность классификации при стирании, и сырой файл схемы
   — способ, выбранный пробой, а не единственный. Отказ от Protobuf в отчёте
   обосновывается не невозможностью стабильного конверта с непрозрачным телом,
   а тем, что формат JSON подходит и задачи, оправдывающей дополнительное
   кодирование, нет.

## 7. Параметры запуска и версии (для фиксации)

Backend, Ajv:

```js
new Ajv2020({
  strict: true,
  strictRequired: false,   // измерено на финальной форме: с true падает только корень #before —
                           // `required: [description]` рядом с allOf, свойство объявлено за $ref; сообщения и #after компилируются
  allowUnionTypes: true,   // только ради assembled_request
  allErrors: true,
  coerceTypes: false, useDefaults: false, removeAdditional: false,
  validateFormats: true,
});
addFormats(ajv);
ajv.addKeyword("$anchor");   // Ajv 8.20 разрешает $anchor в resolve.js, но в словарях его нет
ajv.addKeyword({ keyword: "ratedFieldClass", metaSchema: { enum: ["content", "technical"] } });
for (const s of schemas) ajv.addSchema(s);   // регистрация по $id
ajv.getSchema("https://ratedtattoo.ru/schemas/documents/input/v1.json#after");
```

Измерено: без `addKeyword("ratedFieldClass")` строгий режим падает
«unknown keyword: ratedFieldClass» — пункт из памяти закрыт.

Генератор, jsonschema:

```python
registry = Registry().with_resources((s["$id"], Resource.from_contents(s, default_specification=DRAFT202012)) for s in schemas)
Draft202012Validator({"$ref": "https://ratedtattoo.ru/schemas/documents/input/v1.json#after"},
                     registry=registry, format_checker=Draft202012Validator.FORMAT_CHECKER)
```

Слово `ratedFieldClass` `jsonschema` молча игнорирует (строгого режима нет);
обязательность слова проверяет отдельный линтер (есть в обоих раннерах).

Модели Pydantic:

```
datamodel-codegen --input schemas --input-file-type jsonschema --output <pkg> \
  --output-model-type pydantic_v2.BaseModel --field-extra-keys ratedFieldClass \
  --output-datetime-class AwareDatetime --target-python-version 3.12 \
  --formatters ruff-format --disable-timestamp \
  --http-local-ref-path <зеркало> --no-allow-remote-refs
```

`<зеркало>/ratedtattoo.ru/schemas/…` — копия каталога схем, **пересоздаваемая
перед каждой генерацией** (`run-all.sh`; §12 P5); так абсолютные `$ref` по
`$id` разрешаются локально без сети. `--strict-types` **не задаётся**: модель
не должна быть строже схемы, а JSON не различает `7` и `7.0` (§12 P3).
`--extra-fields` не задаётся: `forbid` выводится из `unevaluatedProperties:
false`, сообщения остаются с `ignore` по умолчанию. `--formatters
ruff-format` требует Ruff — закреплён в `py/requirements.txt` (§12 P6).
`--disable-timestamp` — чтобы перегенерация в CI сравнивалась с закоммиченным
кодом. Python 3.14 генератор принял.

Сериализация из модели обратно в JSON — только `model_dump(mode="json",
exclude_unset=True)`: вызов по умолчанию восстанавливает стёртые ключи как
`null` (§12 P3).

Типы TypeScript: через API `compile(schema, name, { $refOptions: { resolve:
{ rated: { order: 1, canRead: /^https:\/\/ratedtattoo\.ru\/schemas\//, read: … } } } })`;
резолвер читает `$id`-ссылки **прямо из актуального `schemas/`**, без
зеркала (§12 P5). CLI `json2ts` на финальной форме идёт в сеть
(измерено: «Error downloading https://ratedtattoo.ru/schemas/common.json»),
отображения URL на локальный каталог у него нет. Корни документа — через обёртку `{"$ref": "…/v1.json#/$defs/before"}`
(`$anchor` генератор не понимает).

Закреплённые версии: `node/versions.txt` и `py/requirements.txt` в каталоге пробы.

Воспроизведение: `./run-all.sh` из каталога пробы (`set -euo pipefail`,
порядок шагов в `README.md`). Прогнан после исправлений §12, итоговые строки:

```

python: 65/65 совпали с ожиданием; lint: ok; date-time checker: True; без format_checker M45 (30 февраля) проходит: True
```

## 8. Следствия для фиксации (после «да» владельца)

- ADR-0011 §6: формат общих схем (JSON Schema 2020-12, файлы в репозитории),
  каталог `messages/envelope.json` + `messages/v<N>/`, правила записи из §3,
  двухшаговый приём (конверт → версия → тело), общий профиль времени и UUID
  в схеме плюс проверка формата на обеих сторонах, межполевые зависимости
  Result в схеме (§12); при согласии — список явно запрещённых имён (`mode`).
- ADR-0013 §2: документ `input` — файл `documents/input/v<M>.json` с общим
  `$defs/fields` и корнями `#before`/`#after`; слово классификации
  `ratedFieldClass` (`content` / `technical`) на каждом свойстве, правило для
  контейнеров (§2 этого отчёта); закрытие на каждом уровне. §6: стирание по
  сырой схеме, проверка остатка по `#after`, тест E01 в общем наборе.
- Стек: §3 валидатор backend Ajv2020 с параметрами §7 (вместо class-validator
  в NestJS); §4 `jsonschema` + `rfc3339-validator` как обязательные зависимости,
  модели `datamodel-code-generator` с параметрами §7; строка 168 — Pydantic не
  источник и не ворота; §7 строка 272 — закрыть.
- Исследование 2026-09-11 §4.7/§4.10 — две поправки из §6 п. 5.
- Проверка совместимости в CI: общий корпус фикстур прогоняется обоими
  раннерами; дрейф сгенерированных артефактов — перегенерация и `git diff
  --exit-code` (измерено: повторная генерация отличается только строкой
  `timestamp` в шапке, для проверки дрейфа нужен `--disable-timestamp`); схемы — против метасхемы 2020-12 в строгом режиме Ajv; линтер
  слова классификации. Место каталога контрактов в репозитории — решение §9.

## 9. Открытые решения владельца

1. Список явно запрещённых имён в теле (`"mode": false` по B-28) — вводить ли.
2. Открытая форма не отличает лишний `kind`/`subject`/верхний `call_id` от
   будущего поля (M11, M26): принять как следствие или закрыть тела и менять
   версию на каждое поле.
3. Два корня документа в одном файле (`$anchor`) или два файла.
4. Имя слова классификации `ratedFieldClass` и правило контейнеров: класс у
   контейнера действует на всё поддерево; контейнер без класса обязан быть
   объектом, у которого классифицировано каждое свойство.
5. `common.json` — своя ось версий или менять вместе с обеими осями.
6. Где живут контракты в репозитории (например, `contracts/`) и как обе
   стороны получают копию (пакет, подмодуль, копирование при сборке).
7. Типы TypeScript слабее схем (открытые, теряют `required`): принять как
   удобство или искать другой генератор (не проверялся).
8. `assembled_request` как объединение `string`/`array`/`object`/`null`
   (ADR-0011 §6 допускает строку и массив сообщений) или один тип.
9. Добавочная секунда `:60` — отклонять (как в пробе) или принимать с
   явным правилом преобразования (§12 P1).
10. Верхний регистр UUID и `result` при `state ≠ succeeded` — отклонять
    (как в пробе) или допустить (§10).

Не измерено: `discriminator`/`oneOf` в генераторах (в пробе не понадобились:
`external_request_id`, `amount` и подобные записаны как `["string","null"]`);
`AsyncAPI`; поведение на Python 3.12/3.13; `datamodel-code-generator` с
`--extra-fields forbid` для вложенных `allOf` (в пробе вложенное закрытие в
модель не перенеслось — §4, D03).

## 10. Предварительные имена (в тексте ADR дословно отсутствуют)

`parameters.model_settings` (`model`, `seed`); `size.value`, `size.unit`
(перечень `mm`/`cm`); `studio_rules.version` как строка; в `provider_calls[]`:
`provider`, `model`, `attempt`, `state` (`running`/`succeeded`/`failed`/
`outcome_unknown`), `started_at`, `finished_at`, `error` (`provider_error_code`,
`http_status`, `error_message` ≤ 1000), `usage` (`units`, `amount`, `currency`,
`cost_kind`, `tariff_version`), `metadata`; `negative_prompt` обязателен в
`SubmitJob`; `result_candidate.call_id`. Всё это — для подтверждения, а не
контракт.

Ограничения сильнее текста ADR, введённые пробой ради конкретности фикстур
(каждое — для подтверждения или снятия, не решение):

- `minimum: 1` у `size` дескриптора, `attempt`, `sequence`, `revision`,
  `contract_version`; `minimum: 0` у `seed`; `exclusiveMinimum: 0` у
  `size.value`;
- `minLength: 1` у `key`, `prompt`, `style`, `placement`, `studio_rules.version`,
  `model_settings.model`;
- только строчные шестнадцатеричные символы в `sha256`, только строчные буквы в
  `media_type`; `format: uuid` у `job_id` и `call_id`;
- `maxLength: 1000` у `error_message`; перечень `mm`/`cm` у `size.unit`;
  перечень состояний вызова `running`/`succeeded`/`failed`/`outcome_unknown`;
- `"mode": false` (§9 п. 1); `tariff_version` обязателен при `estimated`
  (ADR-0011 §6 говорит «при `estimated`», обязательность — моё чтение).
- Профиль времени (§12 P1): секунды `00`–`59` — добавочная секунда `:60`
  отклоняется (RFC 3339 её допускает; предложение: отправители — свой код,
  `datetime` Python и `AwareDatetime` значение `60` не представляют);
  смещение только с двоеточием; `T`/`t`, `Z`/`z` по RFC 3339 §5.6.
- Профиль UUID (§12 P1): только нижний регистр, без `urn:uuid:` (RFC 9562 §4
  предписывает нижний регистр на выходе; на входе стандарт допускает оба).
- Зависимости Result (§12 P2): `result` запрещён при `state ≠ succeeded`
  («`result` при успехе» ADR-0011 §6 прочитано как «только при успехе»);
  `reason_code` — `null` при `succeeded`, строка при `failed`/`cancelled`;
  `result_candidate` только при двух причинах из ADR-0011 §6;
  `content_erased_at` ⇒ все `assembled_request` — `null`. `revision`
  запрещён у команд (`else` конверта).
